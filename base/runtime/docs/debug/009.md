# 009 std::terminate from a noexcept barrier shows a shorter backtrace than an uncaught throw

Symptom: `25_eh_term_noexcept` failed its first run: the backtrace at std::terminate did not name `noexcept_thrower`, the function that threw.

Cause (not a bug): the exception leaves a `noexcept` function, so the compiler gives that call a landing pad that runs `__clang_call_terminate`. Phase 1 therefore finds a handler (the terminate pad) in `noexcept_barrier`, and phase 2 unwinds the thrower's frame before landing there, exactly as libgcc / libc++abi do. An uncaught exception, in contrast, finds no handler in phase 1, so nothing is unwound and std::terminate (called by the guest's `__cxa_throw`) still sees the whole call chain (`24_eh_term_uncaught` names the thrower).

Fix: the expectation of `25_eh_term_noexcept` in `tests/lift/CMakeLists.txt` lists the frames that must be present (`noexcept_barrier` and its callers).

Consequence for the port: a noexcept violation is reported from the barrier, not from the throw site. The runtime log line "uncaught C++ exception" is only produced for the no-handler case.
