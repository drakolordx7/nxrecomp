# 202 Audio timing on a simulated device: what was measured, and the starvation that needed a lock fix

Method (`audio_timing.sh` (local test script), `run_timing_batch*.sh`): the real game runs headless on the title screen and front end for 75 s with `[audio] sink = paced` (a simulated output device that drains at the sample rate, `src/services/audio_paced.cpp`) and `wav_dump`. The sink's summary line comes from the end-of-run state report. The queue low is taken after the first half second, so the start-up fill does not count. This machine has no active output endpoint, so a real XAudio2 device could not be used.

| Run | Load | Result |
|---|---|---|
| Idle, device clock exact | none | 65.9 s of audio, 0 dropped, 0 underruns |
| Device 1500 ppm fast / slow | 24 busy processes | 69.8 s and 58.6 s of audio (the game started later under load), 0 dropped, 0 underruns, both followed the device |
| Render rate: idle 110 fps, under load 33 fps | as above | the same real-time audio length, no gaps: the renderer does not depend on the render rate |
| Compile load (a clean rebuild of the runtime in the background), first version of the pacing | 24 cores of clang | 5 underruns in 70 s once, 1 in 75 s another time |
| Same load, MMCSS and 1 ms timer added, WAV capture written on the renderer thread | | 0, 1, 0 underruns in three runs; the one underrun was a single 148 ms DSP frame, most likely the file write (the disk was busy with the same compile; not proven) |
| Final: WAV capture on its own thread, the update thread boosted while it holds the renderer's lock, 40 ms queue target | compile load | three runs of 71 s: 0 dropped, 0 underruns each; lowest queue 1800, 1590 and 1794 frames (33 to 37 ms against the 40 ms target), highest 2158 (45 ms); no slow-frame warning in the log |

What the starvation was. The renderer's frame (`SendCommands`) takes the renderer's lock; the game's `RequestUpdateAudioRenderer` runs on the main thread (one call per game update) and holds the same lock. Under load the main thread can be descheduled inside the update, and a 5 ms frame waits for it. The update handler raises the thread's priority while it holds the lock. The WAV tee used to write the file on the renderer thread, so a stalled disk delayed a frame; it now queues the frames and a thread of its own writes them (`close()` waits for the queue).

Not covered: a real sound card. The XAudio2 sink computes its queue from `SamplesPlayed`; that code only compiles on this machine.
