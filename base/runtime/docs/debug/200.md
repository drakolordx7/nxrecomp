# 200 Movies: what the game does with movie::, and four things that went wrong on the way to bit-exact frames

The black screen behind the title was the game waiting for a movie. The library behind the 41 `movie::` imports lives in subsdk0 and drives NVDEC through nvdrv ioctls that answer with zeros; the game's player never got a frame. `src/media/movie_mf.cpp` answers the imports on Media Foundation (S9.md). The first run of the real files through the HLE entry points (every frame md5-compared with ffmpeg) found these:

1. **Audio came back empty (0 bytes) for the first movie with sound, video was fine.** The worker thread started reading as soon as the first track was selected. Media Foundation's source reader starts a stream late when it is selected after the reader has begun: the audio stream read end-of-stream at once. The game selects the video track and then the audio track (a few ms apart). Fix: the worker starts with the first request for data (`GetTrackIndexForAvailableData`, `GetSampleTime` or `Read`), by which time every track is selected. A selection after that logs a warning.
2. **Chroma was shifted.** The source reader hands out 1600x900 NV12 as 1600x912: the decoder pads the picture to whole macroblocks and the chroma plane starts after the padded luma plane (buffer length 2,188,800 instead of 2,160,000). Reading the chroma at `pitch * height` gave garbage. Fix: padded height = buffer length * 2 / 3 / pitch, copy out the tight layout. After this every frame equals ffmpeg's decode byte for byte.
3. **Timestamps were off by one frame and the AAC priming was in the audio.** The MP4 files have an edit list (video: media time of one frame, so the first frame with its composition offset shows at 0; audio: media time 1024 samples, the AAC priming). ffmpeg applies it, Media Foundation does not (video started at 16.67 ms, audio carried 21.3 ms of priming). Fix: the handler parses `mvhd`, `mdhd`, `hdlr` and `elst`, shifts the times, drops the frames the edit list cuts and cuts the priming samples. Timestamps now equal ffprobe's within 2 us and the PCM length equals ffmpeg's.
4. **`GetOutputBufferSize(size, second)`: the second value is an alignment, not a buffer count.** It is passed to `NMovie::CBlockAllocator` (main+0x32b124), which rounds the block size up to a multiple of it and hands it to `CMemory::Alloc` as the alignment. It must be a power of two; the handler answers 16. (The smo-recomp handler answers 1 for the same call.)

Also seen, no action: the video decoder and the audio decoder pass four null event pointers to `RegisterClientEvents`; the game polls (`AcquireInputBufferIndex` returns 0x1011 when nothing is free and the game yields). `GetOutputFormat` is read per frame; its `nv12-colorspace` key selects the colour matrix of the game's shader (2 = BT.709 limited for these files).
