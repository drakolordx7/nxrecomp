# 180 kernel_sync hangs under CPU load: hand-overs wait for the host scheduler, not a lost wake-up

Symptom: under CTest (and sometimes when run directly) `kernel_sync` stops in `exclusion_twice_after_reset`, `condvar_pingpong_round_trips`, `mutex_mutual_exclusion` or `producer_consumer_exactly_once` with "did not finish within 20 s". Which test it is varies from run to run; the same binary passes in about 6 s when the machine is quiet. Other tests of the group fail their sleep-based expectations on the same runs (`mutex_wait_bit_protocol`, `mutex_handoff_follows_priority`).

What it is not:
- Not the testtools merge. `src/kernel/kernel_sync.cpp`, `thread.cpp` (apart from the `ideal == -1` case) and `tests/test_kernel_sync.cpp` are unchanged since d64e7b5. The only change on the time path is the `tt::virtual_tick` / `virtual_sleep` check in `time.cpp`, which returns false unless `[test] deterministic` is on, and nothing in the group turns it on.
- Not a CTest difference. CTest starts the same exe with the same argument and working directory, normal priority class, no `NXRT_*` variables. A run from a shell fails the same way when the machine is busy.
- Not a lost wake-up. A debugger dump of a hung process shows the main thread in `thread_join`, two guest threads in `SleepConditionVariableSRW` inside `arbitrate_lock`, and no other guest thread. A ring log written under the kernel lock (every arbitrate_lock / unlock_mutex / wait / signal with the mutex word) ends with a normal hand-over: the last `unlock_mutex` named the next owner, the lock word held that owner's tag, and `wake_thread` had been called for it. The woken thread had simply not been scheduled yet, and the ring kept growing slowly until the watchdog fired.

Cause: a contended guest mutex is handed straight to the first waiter, as on Horizon, so every contended unlock is a host thread switch, and the ping-pong and the 8-thread mutex tests need tens of thousands of them. The console core model pins each guest thread to one host processor (the top of the affinity mask: on this machine processors 19, 21 and 23, which are E-cores) and turns Windows' wake-up priority boost off. A woken thread therefore cannot run until the scheduler takes its one processor from whatever else is running there. With CPU-bound normal-priority processes on those processors (a parallel build, another program's test run) each switch costs a scheduler quantum, and 20000 round trips take minutes. The lowest guest band (`THREAD_PRIORITY_LOWEST`) ranks equal to a normal-priority process, so even `ABOVE_NORMAL` is not enough.

Measurements (24 spinner processes at normal priority, `condvar_pingpong_round_trips` alone): 108 ms with no load; watchdog after 30 s at normal class; 204 ms in the above-normal class; 81 ms with `NXRT_SCHED_CONSOLE_CORES=0`. The whole group at above-normal class still hung 3 runs in 4 (mutex_mutual_exclusion, which uses the lowest bands); at the high class it passed 6 of 6.

Fix: the kernel is unchanged (the pinning and the unboosted wake-up are the point of the console model). `tests/test_kernel_sync.cpp` raises the process to the high priority class in `begin()` and restores it in `end()`, so the guest threads, even in the lowest band, rank above normal load for exactly the time the kernel is under test. The ping-pong body moved into `run_pingpong` so the old test and the new one share it.

Regression test: `kernel_sync.handoffs_survive_cpu_contention` starts six child processes (`--child kernel_sync_hog`, normal priority, pinned to the three host processors of the console cores, ended by a job object), waits until all of them report running, then runs the ping-pong and the 8-thread mutex. Without the priority class it hits the 20 s watchdog 3 times out of 3 on a quiet machine; with it the test takes about 0.5 s.

Results with the fix, 24 normal-priority spinner processes running: `nxrt_tests kernel_sync` 20 of 20, `ctest -R ^kernel_sync$ --repeat until-fail:20` 20 of 20; whole suite on the quiet machine 63 of 63.

Not covered: other groups that start guest threads (kernel_threads passed 3 of 3 under the same load) and the sleep-as-barrier waits in a few kernel_sync tests (a 50 ms sleep to let a thread queue). They passed under the high class; a kernel-side "waiters queued" probe would remove the sleeps if they ever flake again.
