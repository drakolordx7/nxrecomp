# 223 Importing a memory pool into Vulkan takes 10 to 80 ms on the render thread

The first draw that reads a memory pool imports it as Vulkan memory (`VK_EXT_external_memory_host`). In a 40 s title run: 38 imports on the render thread, 965 ms in total, single ones of 70 to 85 ms (frame trace zone `pool.import`). `vkGetMemoryHostPointerPropertiesEXT` and `vkAllocateMemory` each take 7 ms at the median and up to 46 and 199 ms; the driver checks the pages of the pointer. The cost looks like the page-run walk of debug note 220, but that was not confirmed inside the driver.

Change (`nvn_gpu_pool.cpp`): when a buffer is created over a pool (`nvnBufferInitialize`) the pool is queued for import on a background thread (`[nvn] pool_prefetch`). The render thread that needs a pool still queued imports it itself at once; one in flight is waited for. Pools without buffers (textures, shader code, render targets) are never imported ahead; the first version imported every pool, 135 in a title run of which 38 were ever read by the GPU, and kept the render thread waiting behind that queue (2.7 s of waits).

Result: of 83 pools queued at the title 38 are used; 13 of those imports still happen on the render thread (336 ms instead of 965 ms), 11 waits for one in flight (300 ms). Most pools are used in the frame after they are created, so the lead time is short. A larger win would be one import of the committed heap in a few big chunks (the driver then checks once), but that pins GiBs and was not tried without a level to measure.
