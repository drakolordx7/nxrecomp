# 101: Eden GDB stub behaviour the harness relies on

**Symptom.** Needed a way to read guest memory of the real game, to make traces comparable with ours.

**Cause / facts.** Eden v0.2.1 (`src/core/debugger`) starts a GDB server when `Debugging` `use_gdbstub=true` (port `gdbstub_port`, default 6543). A client that connects pauses every game thread; they run again only after `vCont;c`. Supported: `QStartNoAckMode`, `m` (memory), `g` (registers), `Z0` software breakpoints, `vCont` c and s, `qRcmd`. A `monitor get info` reply is one packet of hex-encoded text, not `O` packets. It lists the layout and the modules: `nnrtld`, the main module (named `GameFramework.nss`), `multimedia`, `nnSdk`.

**Use.** `tools/test/edengdb.py` is the client. Its `read_state` follows `src/testtools/tt_probe.cpp` field by field (same offsets). A frame trace breaks on `CGameArchitectureSupport::Update` (main + 0x3c81c8) and, to learn the `CStateManager`, on `CPlayerMP1::ProcessInput` (x2).
