# 220 MapMemory takes 215 ms: VirtualQuery over the heap view walks every page

Symptom: the title screen stalled for 100 to 250 ms every few seconds and the first seconds of a run were slow. A stack sampler (`[prof] stall_ms`) that dumps every thread when no frame was presented for 40 ms showed the game's main thread, and the loader threads, inside `svc_map_memory` → `mem::is_mapped` / `mem::protect`.

Measurement (frame trace, `[prof] trace`, zones inside the SVC): a 1 MiB MapMemory (the SDK maps a thread stack out of the heap) took 215 to 225 ms, a 128 KiB one 150 to 215 ms, whatever the size. Split by step: the range checks in `is_mapped` 74 ms, the protect of the source 148 ms (it queries twice). On a loaded machine single calls reached 600 ms to 1.5 s. About 45 calls in the first 20 seconds, eight of them back to back during start-up.

Cause: the heap is a pagefile-backed section (`SEC_RESERVE`) with a 6 GiB primary view, about 3 GiB of it committed. `VirtualQuery` returns the whole run of pages with identical attributes, and on a section view the kernel finds the end of that run by walking the page table entries: about 75 ms for 3 GiB, per query, taking the address space lock shared. `is_mapped` (a query), `protect` (two queries plus the VirtualProtect) and every SVC that checks a guest pointer pay it. The size of the mapped range does not matter; the size of the heap does.

Fix (`src/mem/memory.cpp`): a per-page table of the heap section (0 never committed, 1 committed but no-access, 2 committed and accessible), kept by `heap_commit`, `heap_decommit` and `protect`. `is_mapped` and `protect` answer ranges inside the heap view from it; `protect` then makes one VirtualProtect call for the range. Everything outside the heap view still uses `VirtualQuery`. `[memory] fast_query = false` switches back, for before/after runs. The same query is behind the pointer checks of the exception unwinder (`eh/unwind.cpp`) and the audio and hid services, which gain as well.

Result: MapMemory 12 ms for the first call that commits the destination, 1 ms and less after; in a 40 s title run two calls above 1 ms instead of about 45 above 140 ms. Tests: `memory.heap_*` (five cases, including a differential check of 200 random ranges against VirtualQuery) and the existing memory and svc_memory groups.
