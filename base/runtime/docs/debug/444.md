# 444 magmoor_workstation crash in BoxInFrustumPlanes: seen once, only after a 250 s load

Symptom (sweep of 2026-10-22, `work/sweep_out/runs/run026`): host exception 0xC0000005, reading address 0x190, on the graphics thread (`guest-88`), 0.2 s after the script logged that the area had arrived.

What the crash is: `CFrustumPlanes::BoxInFrustumPlanes` was handed the box address 0x190. The caller is `CModConSceneNodeMP1::ProcessRenderQuery`, which asks `CModConSceneNode::GetBounds` for the box. That function returns `*(node + 0x80) + 400`, so the pointer at +0x80 of a scene node was null while the node was still in the scene list and flagged as visible. The call chain is the shadow decal manager (`CShadowDecalManager::SubmitNewStreamOutRequests` -> `CScene::ProcessRenderQueryFromList`) in the render job. A node was queried while its content was missing, either not yet set after a warp or already torn down by the previous area.

What the run around it says: the earlier area (magmoor_lava_lake) loaded in 18 s. This one took 250 s (the log has nothing between 173 s and 425 s but audio counters) and the crash came on the first rendered frame after it. The sweep ran two games at once while other builds were running on the machine. Note 422 shows that such a machine starves the guest's lowest priority threads (loads of 250 s and more) and that a starvation guard fixes the stalls. A load that long moves the order in which the main and graphics threads run; the node lists are meant to be changed only through the graphics command queue.

Status: not reproduced on a quiet machine, so not fixed here. It is tied to the starvation case of note 422: recheck after the stab branch is merged, and if it comes back under load, look at who clears `+0x80` of a scene node (the destructor path of `CModConSceneNode`) against the render job that still holds the node list. Addresses in the lifted main: `CModConSceneNodeMP1::ProcessRenderQuery` 0xfba8b8, `CModConSceneNode::GetBounds` 0x1b6458, `CFrustumPlanes::BoxInFrustumPlanes` 0x130998.
