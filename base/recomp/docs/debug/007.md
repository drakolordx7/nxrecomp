# 007 Indirect tail calls were lifted as a dispatch over every instruction of the function

**Symptom.** On the real game 5,077 of the 5,958 non-PLT `br xN` of `main` (1,448 of 2,070 in `sdk`, 190 of 525 in `subsdk0`) matched no jump-table pattern and took smo's fallback: `jt = xN; goto L_dispatch`, with a `switch` listing every instruction address of the function. 4,907 functions of `main` (174,329 instructions) carried such a switch; all labels stay live, so the compiler could not remove anything.

**Cause.** The fallback assumed that an unresolved `br` is an unknown computed jump inside the function. In clang output every one of them is an indirect tail call: `ldr x8, [x0]; ldr x5, [x8, #0x68]; br x5` (virtual call), `ldp x4, x1, [x0, #0x20]; br x4` (member-pointer thunk), `ldr x6, [x9, x8, lsl #3]` from a static function-pointer table, or `br x2` of a parameter. Computed jumps inside a function are always `add anchor, entry << n` jump tables, which `jumptables.py` resolves.

**Fix.** `jumptables.resolve` also fills `env.tailbr`: an unresolved `br` whose register comes from a load (`ldr`, `ldp`, `ldur`), a register copy of one, or a parameter is an indirect tail call and is emitted as `{ call_indirect(c, xN); return; }`. A load from an adrp-based table counts only when no table entry points into the same function. A `br` fed by `add`/`adr`, or by a reload from the stack frame, keeps the dispatch fallback (the first version treated the `ldr x8, [sp, #8]; br x8` of `-O0` switches as a tail call and broke `02_switch_O0` in the end-to-end oracle). Result on the game: 1 fallback dispatch in `main`, 4 in `sdk`, 1 in `subsdk0` (before: 5,077 / 1,449 / 190), all calls through a pointer spilled across a call. Oracles unchanged.
