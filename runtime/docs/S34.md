# S34: long sessions, and frame rate headroom at high refresh

Branch `soak` (worktree `runtime-wt/soak`), cut from main at cc9cb73. Two questions: does the game stay healthy through a two to three hour session, and where does the frame time go when the target is 144 frames per second and more.

## Result in short

* A soak run of the old build ended after 71 minutes, when the memory guard stopped the game at 8 GB. Whenever the game made a new render target that a draw reads while it writes it (the bloom composite), the runtime made a full-size copy for the new texture and never released the old ones. That came to about 450 copies an hour and 3 to 4 GB of video memory an hour. Fixed: unused copies are now released after 600 submissions. Two smaller problems are fixed too. Exited guest threads stayed in a list with their Windows thread handle open, and the memory guard counted video memory as host memory.
* The fixed build ran for 2 hours (201 area changes, a shuffled tour of the 275 areas). Private commit stayed flat at about 4.5 GB (peak 5.0), video memory at 2.5 GB (peak 3.0) and handles at about 1,070. Exited-thread objects were gone. Frame time was unchanged in each quarter of the run (p50 8.33 ms at the 120 fps cap, 106 to 114 fps). There was no crash and no hang. The run was stopped by hand at 2 hours (2.5 to 3 were planned).
* No scene on this PC is limited by the CPU at 1080p to 4K internal. Light scenes run at the game's 480 Hz step limit (`max_rate`). The open scenes (Tallon canyon and gully, Chozo ruined fountain, Phendrana shore) are limited by the GPU, and GPU time depends little on the resolution: 9 times the pixels cost 1.7 times the GPU time. See "Frame rate" for the numbers and the likely reason.
* New monitoring tools: about 190 gauges (live Vulkan objects, NVN objects, cache sizes, kernel tables, audio and movie queues) written to a file every 10 s, an external monitor, a report with drift verdicts and graphs, a sampling profiler that needs no administrator rights, per-scene frame traces, and GPU time per pass kind.

The soak script starts a New Game, grants every item, and walks a shuffled tour of all 275 areas by `@warp`. In each area it heals, then does one block: walk and jump, combat with charge shots and missiles, morph ball, pause screen with its tabs and the map, or visor switching. Every 15th stay is longer (more than a minute). The settings are a 120 fps cap, a 1280x720 window, 1920x1080 internal, audio on with the volume at 0, and a screenshot every 12th cycle plus one of each block type in the first 14.

## What the soak found

### The old build, 71 minutes (`work/run_soak/soak_long1`, graph `work/shots_wip/S34_soak_before_mem.png`)

Private commit rose from 0.9 GB to 7.8 GB, and video memory in use (`vma.device_usage_mb`) from 0.2 GB to 5.5 GB. At 8.05 GB the memory guard ended the process (exit code 3, log line "memory: 8.05 GB is over the 8.0 GB limit"). The working set did not grow (3.5 to 5.5 GB, falling). The growth was therefore video memory, which counts as private commit because Windows charges video memory to the process's commit.

| metric (old build) | start | 50 % | end | drift per hour |
|---|---|---|---|---|
| private commit, MiB | 888 | 6,520 | 7,760 | +2,150 |
| video memory in use, MiB | 217 | 4,630 | 5,496 | +1,992 |
| VMA blocks | 11 | 409 | 633 | +361 |
| `nvn.replay.fb_clones` | 0 | 371 | 600 | +372 |
| `kernel.threads` (thread objects) | 10 | 43 | 74 | +50 |
| process handles | 843 | 1,065 | 1,111 | about +70 |

### Mechanism 1: copies of feedback render targets (the memory leak)

`src/gfx/nvn/nvn_replay.cpp`, `g_fb_clone`. Vulkan does not allow a draw to sample the colour attachment it is writing (the bloom composite of some frames), so the replay samples a full-size copy of the image made just before the draw. The copies were kept in a map keyed by the attachment's address and were released only when the same address got a texture of another shape, or at shutdown. Every area load makes new render targets at new addresses, so the old copies stayed: 600 after 71 minutes, 4 to 5 GB of video memory. Fix: each copy remembers the last submission that used it, and every 128 submissions the copies unused for 600 submissions are released (a copy released too early is made again on its next use). In the 2 hour run `nvn.replay.fb_clones` never went above 71 and was usually 0 to 12, and video memory stayed flat (graph `work/shots_wip/S34_soak_after_mem.png`).

### Mechanism 2: the memory guard counted video memory

The guard compares the process's private commit with 8 GB, and Windows includes the video memory the process allocated in that number. A game without leaks at 4K would sit at about 3 GB of host memory plus 5 GB of render targets and textures, and the guard would stop it for no reason. The guard now subtracts the video memory in use reported by the Vulkan memory budget (`memguard_set_discount`; the "footprint" log line shows the host figure). This has not been run for hours at 4K: the 2 hour run was at 1080p internal.

### Mechanism 3: exited guest threads stayed in the kernel's thread list

`src/kernel/thread.cpp`, `g_all` kept every thread object ever created, and each held its open Windows thread handle (about 50 threads an hour in the tour). Fix: thread objects that have exited and that nothing else refers to leave the list when the next thread is created (the destructor closes the handle). In the 2 hour run `kernel.threads` stayed at 11 and handles stayed flat. The two pages of guest memory each thread takes from the bump allocator of the kernel region are not returned. At 8 KB a thread that is not a problem (the region is 4 GB).

### What still grows in the fixed build, and why it is bounded

These counters grow with the content the tour meets and level off once all of the game's programs have been seen: `nvn.pipeline_keys` and `nvn.pipelines` (138 an hour at the end of 2 hours), `nvn.prewarm.*`, `nvn.gpl.covered_programs` and `hot_programs`, `nvn.const_buffers` (0.01 MiB an hour), `mem.vm_blocks` (106 blocks, entries of the guest's address-space map), `nvn.handle_regions` (command list regions). None is large. The soak table of each run lists every metric with first, 10/50/90 % and last value and the drift.

### Other things the soak showed

* `@warp` loads take 3 to 21 seconds without a presented frame on this PC while other games are running. A real door load is streamed and does not do this; warps load synchronously.
* Audio: this PC's session has no output device ("xaudio2: no active output endpoints"), so the paced fallback sink ran. Its gauges (`audio.underruns`, `audio.sink_frames_dropped`) stayed at 0. A run on a machine with a real endpoint is still to do.
* Process CPU: 2 to 4 cores during the tour (texture preparation, pipeline libraries, guest threads), not a drift.

## Frame rate

Method: `scene_run.py` plays New Game, warps to the scene, heals, stands still for 20 s with the frame trace on, window 1280x720, internal resolution set by `render_width` and `render_height`, no frame cap, no vsync, pipeline cache warm. Before = the build with the gauges only (`work/soak/exe_prof`), after = the final build (`work/soak/exe_fix4`); two rounds, alternating. The PC was shared with two to four other game instances (and the soak) the whole time: GPU use of the others 30 to 97 %, system CPU 90 to 100 %. Run to run spread is 30 to 60 %, and the before and after columns do not differ within it. Do not read the fps columns as the capability of the machine; read the GPU time and the shape of the frame.

Scenes: `canyon` Tallon canyon cavern, `gully` Tallon gully, `fountain` Chozo ruined fountain, `shore` Phendrana shorelines, `lava` Magmoor lava lake, `quarry` Phazon Mines main quarry, `hangar` Frigate docking hangar. The Tallon landing site and the Chozo Main Plaza are cutscene scenes when warped to and were dropped. What the numbers say, with the machine load in mind:

* No scene is CPU bound. The sampling profile of the hangar scene shows the game's update thread (`main`) running user code in 29 % of the samples at about 380 frames per second, the render submit thread (`guest-88`) 8 to 54 %, and the replay thread (`nvn-render`) 12 %; the rest is waiting. The light scenes (lava, quarry, hangar) end at the game's own 480 Hz step limit (`[time] max_rate`), not at a CPU limit. The open scenes spend 7 to 15 ms of GPU time per frame at every resolution, which at best is 66 to 140 frames per second on this GPU while it is shared.
* The GPU time barely follows the resolution. Tallon canyon at internal 1280x720 / 1920x1080 / 3840x2160: 7.8 / 7.7 / 13.2 ms. Nothing here is fill rate bound.
* Where the GPU time goes (`[prof] gpu_passes`, Tallon canyon, 720p; means on a loaded GPU, so 10 to 30 % too high): four main colour passes with 151 draws 3.9 ms; one depth-only pass with 146 draws and 305,000 indices 2.3 ms (16 µs a draw for about 2,000 vertices); 46 `gap` intervals (copies, barriers, layout changes between passes) 1.0 ms; everything else under 0.3 ms. The other open scenes look the same. At 3840x2160 the colour passes take 5.0 ms and the depth pass 3.1 ms.
* Likely reason, not verified: the game's vertex, index and constant buffers live in memory pools that the runtime imports as host memory (`VK_EXT_external_memory_host`), so the GPU reads them over PCIe on every draw. The per-draw upload buffers are already in device-local memory behind the resizable BAR (this PC has it; checked with a log of where `Upload` buffers land). `nvidia-smi dmon` during the scenes showed 1.4 to 4.8 GB/s received from the host, against 0.03 GB/s with the game idle (the PC was in a remote desktop session, which adds copies of its own, so only the order of magnitude counts). A device-local copy of the buffers the draws read is the next thing to try. It needs the replay to know the byte ranges a draw reads before the pass begins, so it was not started.
* Full memory barriers between passes (`ALL_COMMANDS` to `ALL_COMMANDS`, 46 to 66 `gap` intervals a frame) cost 0.7 to 1.0 ms in canyon and gully, 10 to 12 % of the GPU time. Narrower barriers need the replay to track which texture each pass wrote; not done.

### CPU side fix

* `dispatch_call` (`src/core/dispatch.cpp`): every indirect call of the guest (virtual calls, function pointers) looked the target up in a hash table of 138,000 functions, 4 MiB, a cache miss each time, and calls to HLE thunks searched the table and failed first. Now thunk addresses are recognised by their range, and each thread has a 1,024 entry direct-mapped cache of the functions it found (a replaced function or `fn_clear` invalidates every thread's cache through an epoch). Sampling profile of the Frigate hangar, share of the `main` and `guest-88` running samples in `dispatch_call` and the table load: 4.9 % before, 3.3 % after (the table load alone 4.0 % to 1.3 %). Canyon, where those threads run little: 4.8 % to 4.1 %. That is 2 to 5 % of two threads' time, which no scene could show in its frame rate on a shared machine. Tests: `soak.dispatch_cache_*` (a replaced function, a second thread, colliding addresses).
* Not done on purpose: the largest guest thread cost is the game's own code. `CVector3f::AsNormalized`, `CMath::InvSqrtF`, `CMath::SqrtF` take 15 % of `main` in the hangar through the recompiler's exact ARM float helpers (`recomp/include/nxrecomp/neon.h`, `fpexact.h`); that is in the recompiler repository and its oracles are locked.
* The game thread's pacing wait (`timestep::wait_until`) spins for the last 0.8 ms before each frame at the 480 Hz limit (20 to 45 % of that thread's running samples in light scenes). It only runs when the frame is faster than 480 Hz, so not at a player's 144 or 240 cap; left alone.

## What is left

* The soak ran 2 hours, not 2 to 3, at 1080p internal; 4K and a real audio device are not covered.
* Saving, loading, "Continue", quitting to the title and movie loops are not in the soak script (health 0 does not kill Samus, and the pause menu's Quit Game needs a reliable tab position). Cutscene movies play once at the start of each run. The title idle script (`work/soak/title_idle.nxs`, `soak_run.py --script`) was written and not run.
* GPU time per frame, for later: a device-local copy of the buffers the draws read, and narrower barriers between passes. Both are replay work; the draw and index counts per pass are in the trace (`gv:` marks).
* One crash seen in a test script, not in play: warping right after the New Game begins (300 frames, then at once) crashed three times in `CParticleStaticRenderState` while the loader thread built a particle (null resource); with 8 s more wait it never happened. A race of the test script with the game's own loading; not investigated further.
* Timing sensitive tests `svc_audio_paced`, `svc_audio_out`, `gfx_nvn_scene_stress` failed once in the full run (a soak and a second game instance running) and passed alone, as known. The other 162 passed in that run.
