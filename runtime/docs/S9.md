## Movies

### What the game does

The game never touches NVDEC itself. `main` imports 41 functions of Nintendo's multimedia library (`movie::Extractor`, `Decoder`, `MediaData`, `Buffer` and three free functions); the library lives in subsdk0 and under it talks to nvdrv's NVDEC and VIC channels, which here answer with zeros (S6b item 7). The game's own movie code wraps the library in `NMovie::IExtractor`, `IVideoDecoder`, `IAudioDecoder`, `IAudioPlayer` and `IVideoPlayer` objects (main offsets 0x326000 to 0x330400), driven by `CMoviePlayer`, `CMovieList` and `CMovieIOWin`.

- The extractor is created on the movie's own "Movie Init Thread" (`NMovie::make_extractor`, main+0x327450): `Extractor(container 1 = mp4, cache 2)`, then `SetDataSource(reader, path)` with a `ClientStreamReader` the game implements over its resource system (`CMovieReader`: Open, ReadAt, Close, GetSize at vtable +0x10 to +0x28), then `GetTrackCount`, one `GetTrackConfiguration` per track and `SelectTrack`. The configuration keys the game reads are `mime`, `durationUs`, `bit-rate`, `width`, `height`, `frame-rate`, `channel-count`, `sample-rate`.
- Each track gets a decoder: video `Decoder(type 1 = H.264, output format 4 = NV12, mode 1)`, audio `Decoder(type 4 = AAC, format 1 = PCM16)`. The decoder is wrapped in a 0x60-byte game object; the game registers four null event pointers, so nothing is signalled and everything is polled.
- The game's feed loop (main+0x328114 to 0x3282e0 and 0x32fd3c to 0x32ff18): `GetTrackIndexForAvailableData`, `AcquireInputBufferIndex`, `GetInputBuffer`, `Extractor::Read`, `GetSampleTime`, `SendInputBufferForDecode(index, offset, size, time, flags)`, `Advance`. Output: `AcquireOutputBufferIndex`, `GetOutputBuffer` into a buffer the game owns, `GetOutputFormat`, `ReleaseOutputBufferIndex`. A result of 0x2000 from `GetSampleTime` or `Read` is the end of the data; a looping movie seeks to 0 after `Advance` and keeps counting loops itself.
- Video frames reach the game as tightly packed NV12 in its own memory: Y plane at `nv12-y-offset` (0), UV plane at `nv12-uv-offset` (width times height), `width`, `height` and `nv12-colorspace` as `MediaData` keys. The game uploads the two planes and converts to RGB in its own shader with a colour matrix picked by the colourspace key (0 and 4 BT.601 limited, 1 BT.601 full, 2 BT.709 limited, 3 BT.709 full). The MPR movies are BT.709 limited. `GetOutputBufferSize(size, alignment)` sizes the game's frame pool: the second value is a power-of-two alignment (16 here), not a count.
- Audio: the decoded PCM goes to a voice of the game's own audio renderer (`AcquireVoiceSlot`, `AppendWaveBuffer`, per-channel `SetVoiceMixVolume`), so movie sound reaches the sink through the same path as every other sound. The decoder must hand out blocks of at most 0x8000 bytes (the game allocates at least that).
- The movie clock is the game's own: `CMoviePlayer::Update(delta)` advances the position by the frame delta and picks frames by timestamp. Video follows the game's timestep, audio plays in real time.

### The host implementation

`src/media/movie_mf.cpp` registers a handler for each of the 41 imports (`hle_register`) and forces the imports to it (`module_override_symbol`), from `nxrt::init` unless `[media] movie = off`. It follows the design worked out for smo-recomp (`nnmovie_mf.c`, GPL-3.0, same library in another game) and differs in these points:

- The game calls the exported wrappers directly, so the handlers take the object pointer and arguments as registers. The 16-byte `Extractor` and `Decoder` objects hold a marker and a pointer to the host object; `MediaData` is one pointer to a key/value map; `Buffer` keeps the 0x40-byte layout of the library.
- Media Foundation's source reader does the demuxing and the decoding. A worker thread per movie reads decoded samples ahead into one bounded queue per track (6 video frames, 64 audio blocks). The game's threads never wait for a decode; `GetTrackIndexForAvailableData`, `GetSampleTime` and `Read` wait (bounded to 8 s) only when a queue is empty. The extractor's current sample is the one with the smallest timestamp among the selected tracks, as in NuMediaExtractor.
- The worker starts reading with the first request for data, not with `SelectTrack`: a stream selected after the reader has begun would start late (the first run of a movie with sound returned no audio at all).
- A "compressed sample" handed to `Read` is a token (magic, reference to the decoded sample, time, bytes to skip). `SendInputBufferForDecode` moves it to the decoder's queue and the decoder copies the decoded NV12 or PCM into the game's buffer in `GetOutputBuffer`. The decoder keeps the two pools of the real library (input indices, output indices) and the back-pressure between them. Audio blocks larger than 0x8000 bytes are split.
- NV12 frames from the source reader are padded to whole macroblocks (1600x900 comes as 1600x912, 2,188,800 bytes); the chroma plane starts after the padded luma plane. The copy reads the padded height from the buffer length and writes the tight layout the game wants.
- Edit lists are honoured. The MP4 files carry an edit list that starts the video one frame in (the first frame has a composition offset) and cuts the 1024-sample AAC priming. Media Foundation ignores it, ffmpeg and the container do not: without it video is 16.7 ms late and audio 21.3 ms. The handler reads the `elst`, `mdhd` and `hdlr` boxes itself, shifts the timestamps, drops frames that start before zero and cuts the priming samples, so the output matches ffprobe's timestamps exactly. Tracks are listed in file order (video first), as the library does.
- The game's reader supplies the file: `SetDataSource` reads the whole movie through `ClientStreamReader::ReadAt` into memory (up to 37 MB, 0.02 s in the log) and hands it to Media Foundation as a byte stream.

## Audio

### What the game asks of the renderer

From the start-up log and the renderer's usage line (`audren-use`, every ~15 s of updates and when the renderer closes): `OpenAudioRenderer` with 48,000 Hz, 240 samples per frame (5 ms), 228 mix buffers, 128 voices, 2 sinks, 68 effects, revision REV9. On the title screen and in the front end: at most 4 voices play at once, every voice runs at 48 kHz (the music and menu sounds are decoded to that rate by the game), the voices are mono, and two effect types are enabled, auxiliary-buffer sends and a biquad filter. No voice is dropped. The game updates the renderer once per game update, from its main thread (`CAudioManager::PostScriptingUpdate` to `CAxalSystem::UpdateSystemVoices`, one `RequestUpdateAudioRenderer`), and the renderer renders its own 5 ms frames from the last state on its own threads, so the sound's timing does not depend on the render rate. A second game thread (`CAxalSystem`'s aux update) waits for the renderer's frame event with a 250 ms timeout.

### The decoder against real samples

The title screen's voices are all DSP-ADPCM at 48 kHz, so the decoder is checked against the game's own samples (`svc_audren_adpcm_real`). `tools\media\csmp_ref.py` is an independent DSP-ADPCM decoder written from the format rule (frame = 8 bytes: coefficient pair and scale, 14 four-bit samples); it parses the CSMP files of `Preload/DuplicateData` (370 files) and writes 60 mono samples (53 at 48 kHz, 4 at 44.1 kHz, 2 at 32 kHz, 1 at 24 kHz), their headers and reference PCM. The test decodes each with `AdpcmHelper::Decode` the way the renderer calls it, in ranges of 240, 1000 and 77 samples with the history carried from one call to the next, and compares sample by sample: 60 of 60 exactly equal for each range, 9,735,852 samples. Changing one coefficient in five headers makes exactly those five fail, so the comparison bites.

The CSMP layout, for anyone reading the files: RFRM wrapper, `FMTA` chunk (the channel count and a layout mask sit at +0x18 of the chunk: 01 04 for a mono centre sample, 02 03 for stereo), `DATA` chunk with a 16-byte prefix, then one 0x60-byte little-endian DSP header per channel (sample count, nibble count, rate, loop data, 16 coefficients at +0x1C, history), then the frames. Multi-channel files (37 of the 370) carry one header per channel and are not covered by this check. No mono file selects a coefficient pair above 7, so the port's handling of an out-of-table pair (it reads zeros and prints to stderr) never matters for the game's mono samples.

### Changes

- Default sink: `[audio] sink = auto` (it was `null`). XAudio2 on the default output device; when XAudio2 or a device is missing the null sink is used and the log says so. A machine without a sound card (this one has no active output endpoint) keeps running.
- `[audio] volume`, `device`, `wav_dump` (the sink options): see CONFIG.md. `wav_dump` writes every frame the game sends, with a header that stays valid if the process is killed; it is the capture switch for the audio checks.
- Timing. The renderer used to pace itself by the host clock alone (5 ms frames, `sleep_for(1 ms)`). A sound card never agrees with the host clock, so the queue slowly filled (frames dropped, a click) or emptied (a gap). Now, when the sink has a clock of its own, `AudioProcessor::Wait` keeps about 40 ms queued: it waits while the queue holds more and renders at once when it holds less. XAudio2 reports its queue exactly (`submitted - SamplesPlayed`). The null sink has no clock and keeps the old host-clock pacing. The two renderer threads join the MMCSS "Pro Audio" task, the timer runs at 1 ms while a renderer is up, and the game thread that calls the update runs at higher priority while it holds the renderer's lock (the renderer's frame waits for that lock; a thread descheduled inside it starved the card once in a while under a heavy load).
- `[audio] sink = paced`: a simulated device that drains at the sample rate (`paced_ppm` skews its clock), counts underruns and records the lowest and highest queue level. It is how the renderer's timing is measured without a sound card; the end-of-run summary carries its line.
- Usage line (`audren-use`) in `AudioRenderSystem`: voices, formats, rates, channel counts and effect types the game really uses.

### Timing

Runs of 75 s on the real game (headless, title screen and front end) with `sink = paced`, WAV capture on or off, summaries in debug note 202:

| Condition | Result |
|---|---|
| Idle machine | 65.9 s of audio, 0 dropped, 0 underruns |
| Device clock 1500 ppm fast and 1500 ppm slow, 24 busy processes (render rate fell from 110 to 33 fps) | 0 dropped, 0 underruns in both; the renderer followed each clock |
| Clean rebuild of the runtime running in the background (the heaviest load found), final code, three runs | 0 dropped, 0 underruns; the queue never fell below 33 ms (target 40 ms), the peak was 45 ms |
| Before the lock priority fix, the same compile load | 1 to 5 underruns per run (one 148 ms stall, probably the WAV file write; the others most likely a main thread descheduled inside the renderer update) |

Audio length equals wall time in every run, so the renderer is paced by the device clock and not by the render rate.

## Decisions

- Movies are answered inside `nxrt::init` (runtime), not in `mpr_main.cpp`: the library is the SDK's, not the game's, and the game-build files stay untouched. `[media] movie = off` restores the lifted library.
- Edit lists are applied by the handler (ffmpeg semantics) instead of passing Media Foundation's raw times.
- Decode-ahead in a worker thread, with bounded queues, instead of decoding in the calling game thread (the game pumps its extractor on the main thread and a 1600x900 software decode takes 7 to 10 ms).
- Software decoding (no hardware MFT): the output is bit-identical to ffmpeg's, which a hardware decoder would not guarantee.

## Gaps

| Gap | Why |
|---|---|
| No movie with sound played inside the game | The 7 AAC movies are in `UIMP1.pak` and reachable only after the loading screen or from the unlocked extras; the loading screen still loses the Vulkan device (S4d). The HLE path is tested with the real files and the game's own call sequence, the audio player's side is the game's code. |
| XAudio2 playback was not heard | No active output endpoint on the development machine (XAudio2 reports 0x80070490). The sink logic is covered by the paced device and the WAV capture; the XAudio2 specific code (queue from `SamplesPlayed`, device choice, volume) compiles and its unit cases skip without a device. |
| Movie speed follows the game's timestep | The movie player advances by the frame delta, which `CGameArchitectureSupport::Update` fixes at 1/60 per rendered frame. At a render rate above 60 fps movies play faster than their sound; the timestep work (Next item 1) has to give movies the real delta. |
| Decoder events | The game passes null events, so event signalling is not implemented (a log warning if a future caller passes real ones). |
| Container types | Only the MP4 path is exercised (container type 1). MKV and WebM are opened through Media Foundation's byte stream hint but untested. |
