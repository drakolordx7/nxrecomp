# S31: the Frigate monitors, the route past the Emergency Evacuation Area, the Parasite Queen

Branch `play4` in `runtime`. The route tools are in the root repository's `` (`frigate.py`, `queen4.py`, `evac4.py`, `bra1b.py`, `hop4.py`, `monsurvey4.py`, `bootw4.sh`, `boote4.sh`, `bootwin4.sh`). Screenshots are in `work/shots_wip/play4_*`. Nothing here comes from the game files except the pictures, and they stay out of the repositories.

## Short answer

The noisy screens in the Emergency Evacuation Area are drawn the way the game asks. No decode, format, swizzle or blend error was found, so there is no fix. The noise is a glitch overlay that the game puts on top of a static layer on the two right-hand monitors of the exit door console. The two left-hand monitors of the same console show clean panels (`play4_monitor_working_left_broken_right.png`). A picture from the Eden emulator at the same spot could not be taken; see "What was not checked".

The route runs from the hangar to the Air Lock, and past a documented warp into the Emergency Evacuation Area. Input drives it as far as Biotech Research Area 1. The Parasite Queen is reached, scanned and shot at, but not killed. The escape, the landing as part of the story, and the first Missile were not reached.

The "New Extras" message, the save question, the save and the reload of slot 1 were all driven with the mouse and work.

## The monitors

### What is drawn

One trace frame at the console (`NXRT_NVN_TRACE_FRAME`, or `@shot nvntrace_NAME` in a live run) shows that the screens are several draws in a row:

| Layer | Fragment shader | Textures | Blend |
|---|---|---|---|
| static | `ef63a4a1` | 2048x1024 sheet of 128x128 noise cells (ASTC 8x5, one cell chosen by a scrolling texture matrix) | source alpha, one, add |
| scanlines plus glitch | `e5d66535` | 512x512 scanline texture (black colour, alpha with thin dark lines) and a 1024x1024 ASTC 5x5 atlas | source alpha, one, add |
| clean panel | `e5d66535` | the same scanline texture and a 2048x2048 ASTC 8x5 atlas of panels | source alpha, one, add |

The fragment shader of the second and third row computes `(texA * tex8.rgb * (1 - texA.b)) * c0 + (texC.rgb * c2 * tex8.a + c3)`, then multiplies by the fog transmittance and adds the fog colour. For the glitch atlas `c2` is 2.0, and for the clean atlas it is 15.0, which matches how bright each texture is. Every texture view has the identity swizzle, the sampler repeats, and the blend factors are the ones above.

### What was checked

| Check | Result |
|---|---|
| ASTC to BC7 transcode of the 1024x1024 atlas against an independent decoder (`texture2ddecoder`) on the game's own ASTC bytes | PSNR 42.7 dB, 0.09 % of the pixels differ by more than 32 levels; the noise is in the decoded data |
| Look of the atlas | four 512x512 quadrants, each with the layout of the clean 2048x2048 atlas, but with every row shifted and the red, green and blue channels shifted differently: glitch artwork, not a damaged decode (`play4_monitor_overlay_atlas_channels.png`) |
| Aliased or stale texture memory | each texture was prepared once with its final data; two cache keys for one texture id were an earlier, half streamed state |
| Swizzle, blend factors, sampler | printed in the trace now (`swz`, `blend rt0`), all as expected |
| Monitor with the overlay draws skipped (`[nvn] skip_fs_file`) | dim grey-teal static with scanlines and nothing else (`play4_monitor_now_overlay_on_off.png`); this matches the description of the console |
| Which rooms draw the static shader at all | of 20 Frigate areas checked right after a warp, only the Emergency Evacuation Area and Biohazard Containment |

So the screens show static plus a glitch overlay because the game's draw list has both. If the console really shows only static there, the difference has to be a game-side choice (for example a state flag that turns the overlay draws off), not something the runtime does wrong. The way to settle it is a frame from the Eden emulator at the same place.

### New debug aids (all off by default)

* `[nvn] skip_fs_file = FILE` (env `NXRT_NVN_SKIP_FS_FILE`): FILE holds fragment shader hash prefixes, or draw ranges such as `#198-#210`, separated by blanks. Draws that match are not drawn. The file is read twice a second, so it can change while the game runs.
* `[nvn] dump_astc = DIR` and `dump_astc_w = N`: level 0 of every ASTC texture of width N as tight ASTC blocks, to decode with another decoder.
* The draw trace now prints each texture's swizzle, the blend factors of render target 0 and the bounds of the first three vertex attributes over the whole draw (half and float formats decoded).

### What was not checked

No Eden frame exists at the console. `edengdb2.py` and `eden_run2.py` call the game's warp and teleport functions through Eden's GDB stub (the same five calls as `@warp`, then `CPlayerMP1::Teleport`). In one run all five warp calls went through, but Eden then stopped answering the final step. In the other runs Eden stalled on the planet loading screen or stopped producing frames while other game instances were running. The scripts are a starting point for anyone who repeats this. The one missing piece is a reliable Eden start. Try it with nothing else running; `finish()` now resumes without a single step.

### Parasite Queen

Walking to the ring (`queen4.py walk`) starts the introduction cutscene. The player then stands on the ring about 39 units from the Queen. She is inside a glass chamber and fires green acid blasts through it, about 10 health every 12 s. Findings:

* The scan works. Aim 11 units above the Queen object's position and hold ZL on the scan visor for about 150 frames. The result is "Scan complete", a log entry, and a message that her weak spot is in her mouth and can be targeted with auto-targeting.
* Missiles are the R button (and the right mouse button), not X or A. A test pass with `press Y` turned Samus into the ball and spoiled one run. `press Y` is the morph ball.
* Charged beam shots and missiles at her, locked on, with the weak spot scanned, leave her object unchanged. The two health-like values at offsets 1356 and 1360 stay at 1000. Shots land on the glass or the railing in front. What opens the fight, and how the glass goes, is still unknown.
* The player object, the Queen object and `CNewIntroBossMP1` have three entries in the object scan at the same position. Two of them are stale copies left from earlier area loads.

Health was restored with the `@poke` development aid in these runs (`combat.heal`). This is not input, and it is named here on purpose.

When a script drives the slot list, the pointer has to rest on a slot for a moment before the click. A click straight after a long move once picked the neighbouring "New Game" slot.

A real save station was not used. The Tallon station that `@warp` offers sits far north, next to the Reactor Core of Tallon, about 370 units from the landing site. The first station on the way is in the Chozo Ruins.
