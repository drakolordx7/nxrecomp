# S49: high refresh in real-time play

Branch `hz` in `runtime` (this document only) and in the root repository (the test scripts). No runtime or game code changed.

## Short answer

The earlier physics checks (S22, S25, S30) ran on the test clock: every step was exactly 1/rate. This round runs the game the way a player does: in a window, on the real clock, with a frame cap of 60, 120, 144 or 240. The game step is the measured frame time.

* Running, the stick turn, the mouse aim and the camera match at every cap. The aim and the camera move on every frame.
* The morph ball is not 1 to 2 % faster at high caps. In game time it is 0.2 to 0.3 % faster than at 60. That is the same small integration effect S30 measured with fixed steps. The S26 question is closed.
* Jump height matches at 120, 144 and 240 when frames are even (+0.1 to +0.4 %). One jump at the 144 cap went 2.7 % higher. The cause is found and explained below. It is a variable-step effect in the game's own jump code. It is not fixed in this round.
* Frame pacing at 60 and 120 is steady. This PC did not reach the 144 or 240 cap: medians were 123 and 126 frames per second, while another game session ran next to it. When frames come late, the timing alternates between short and long frames.

## Method

`python -I hz_run.py batch b2 --caps 60,120,144,240 --reps 3 --shots` (root repository, branch `hz`) runs one game process per run, one after another. Each run does a New Game with `skip_intro`, uses the Frigate's Exterior Docking Hangar, then exits. The settings are the factory `controls.ini` with `fps_cap` set, `vsync = 0` (the monitor is 144 Hz, so vsync would have held the 240 cap at 144), a 1280x720 window and render size, the null audio sink, `NXRT_NVN_POOL_MIRROR=off`, below-normal priority and `[time] mode = real`. The script runner's `@rate 60` is turned off at once with `@rate 0`. There is no deterministic clock and no fixed step.

Inputs go through the test script runner's pad and mouse, never through global input. Holds use host wall-clock time (`@sleep`), the way a player holds a stick. The sequence:

1. Walk to (64.0, -92.8) and face 135 degrees. This is setup and is not measured. The approach uses holds in game seconds, so the stopping point does not depend on the cap.
2. Morph (Y), wait 1.5 s, hold the stick forward 3 s, release, then unmorph.
3. Hold the right stick fully for 1.25 s (stick turn).
4. Face back along the line (setup). Run forward 3 s, then do a standing jump with B held 0.4 s.
5. Mouse turn: 8 counts per frame for 120 frames.

All numbers come from the game's own player state in the per-frame trace: position, velocity, aim yaw, camera yaw and movement state (`out/trace.jsonl`). Each trace line also carries the frame's host time (`ms`). Caps ran in rotated order across the three repeats (60-120-144-240, then 240-144-120-60, then 120-240-60-144). The 12 runs took about 25 minutes, back to back in one session.

The line across the hangar was found with `@rays`. It is the longest stretch of flat, clear floor from the start area, about 56 units. The Frigate's first force field is a dynamic object and has a barrier near z = -132 that the static rays do not see.

## The jump outlier: the jump timer's last frame and the speed cap

In run `b2_c144_1` the standing jump peaked at 3.594, against 3.500 to 3.520 in every other run. That run had uneven frames, and the step in which the jump's rise ended was 16.1 ms long; at a 144 cap it is normally about 7 ms. The other runs fit the same rule: the longer that step, the larger the possible gain.

How the game does it, read in IDA (main module, symbols from the knowledge base):

* `CPlayerMP1::SetMoveState` sets a jump timer (`CPlayerMP1 + 0x1e8 + 576`) when the rise starts. `CPlayerMP1::Think` subtracts the step from it each frame and switches to the falling state at zero.
* `CPlayerMP1::JumpInput` returns the vertical force for the frame. While rising it is the jump force. In the frame where the timer runs out partway (`timer < dt`), it blends: `f * jump + (1 - f) * gravity` with `f = timer / dt`. On its own, that is exact for any step.
* The rising speed is capped at 11.667 units/s (`CPlayerMP1::GetMaximumPlayerPositiveVerticalVelocity`; 14.0 with power-up item 15 owned). The cap is applied once per frame, in `CPhysicsActorMP1::PrePhysicsUpdate`, to the velocity *entering* the frame. The force is then integrated over the whole step.

A standing jump reaches the cap before the timer runs out. In real physics, the jump force is used up against the cap until the timer ends, and gravity acts after that. In the game, the blended force of the last frame is integrated on top of the capped speed. If `f` is above 35/85 (about 0.41), the net force is upward, and gravity for the `(1 - f)` part of that step is lost. Measured in `b2_c144_1`, the vertical speed fell by 0.026 in that 16.1 ms step instead of about 0.56. The extra height is at most about `0.59 * 11.667 * dt`, roughly `6.9 * dt` units:

| Step where the timer ends | Largest extra height |
|---|---|
| 16.7 ms (60 per second) | 0.115 (+3.3 %) |
| 8.3 ms | 0.057 (+1.6 %) |
| 6.9 ms (144) | 0.048 (+1.4 %) |
| 4.2 ms (240) | 0.029 (+0.8 %) |

Every run fits this bound. Run `b2_c144_1`: 16.1 ms gives at most 0.111; 0.094 was seen. The 240 runs, at 6.2 to 6.6 ms: at most 0.045; 0.016 and 0.020 were seen. Run `b2_c144_2`, at 7.2 ms: 0.000 (here `f` was below 0.41).

With fixed steps that divide the jump time evenly, `f` is always 1 and nothing is lost. That is why every fixed-step test since S22 read exactly 3.500, and why the console game, which always steps 1/60, never shows it. On the real clock the timer's end falls anywhere inside a frame, so a jump can go up to about 6.9 x step higher: up to +1.4 % at a steady 144 and +3.3 % with 16 ms frames. The effect only ever adds height and changes from jump to jump. Running jumps that leave the ground below the cap are not affected the same way (not checked).

Not fixed in this round (the maintainer asked to wrap up). The proposed fix lets game logic follow real elapsed time without special cases for any frame rate. In the frame where the jump timer runs out, the vertical speed should end at what a continuous cap gives: `min(v + a_jump * f * dt, vmax) + a_gravity * (1 - f) * dt`. That means an exit hook on `CPlayerMP1::JumpInput` (main module offset 0xcf0060) that rewrites the returned force in that one case, with the cap from `GetMaximumPlayerPositiveVerticalVelocity`. It needs a new hook site in `recomp/games/mpr/main.sites`, a relift, a unit test of the force rule, and this table run again. JumpInput is called from `ComputeMovement`; the fix does not touch `play_aim.cpp` or the ProcessInput hook.

## Other findings

* The first batch (`b1`) is not used for the ball numbers. Its setup walk (`live.goto`) counts frames, so at each cap it stopped Samus at a different spot. At 60 she stopped on a raised edge at (60.7, -89.8) and the ball rolled off it after the morph, at 10 units/s before the stick was pressed. `hz_run.py` now walks with holds in game seconds and starts on flat floor. The run, jump, turn and pacing numbers of the five `b1` runs agree with `b2`.
* Morph ball speed before the stick in `b2` is 0.5 to 1.3 units/s: the ball settles after the morph. It is the same at every cap and is too small to move the window.
