# S28: the mouse in every menu

Branch `mouse`. Before this, the keyboard and the pad worked in every menu, and the mouse did nothing there. Now the mouse is a pointer in the menus. It shows a cursor, hovering highlights an item, left click acts, right click goes back, the wheel scrolls and steps values, and the map can be dragged. Gameplay is unchanged: the pointer is captured and hidden while you play, as before.

## What it does, screen by screen

Checked in the real game at 1280x720 and 2560x1080 (shots in `work/shots_wip/mouse_*.png`). Driving was scripted through synthetic pointer events in the game window; no global mouse or keyboard input was used.

| Screen | Hover | Left click | Right click (back) | Wheel |
|---|---|---|---|---|
| Title ("press A") | no widgets | any click starts, like A | n/a | n/a |
| Main menu (Play, Options, Extras) | yes | yes | yes (from a sub menu) | moves the selection |
| Save slot select, difficulty | yes | yes | yes | moves the selection |
| Options pages of the front end (Display, Controls, Sound) | yes: the row, also over its value | the two halves of the value area are the arrow buttons: left half less, right half more | yes | over a value: steps it; elsewhere moves the selection |
| Slider rows of those pages (HUD Opacity) | selects the row | no | yes | moves the selection (the game gives sliders there no pointer area) |
| Extras and its galleries | yes | yes | yes | moves the selection |
| Pause screen: category lists (Inventory, Log Book, Options) | yes | yes | yes (one level up, then closes the pause) | moves the selection |
| Pause screen tab and button labels (L and R tabs, Back, Exit, Select) | no | yes: the label is that button | n/a | n/a |
| Options tab of the pause screen: option rows, sliders, Quit Game and its Yes / No | yes | yes; a slider takes a click and a drag along its track | yes | over a slider: steps it |
| Map | n/a | n/a | yes (leaves the map) | zoom |
| Map drag | left button drag rotates, middle button drag moves | | | |
| Save station and message boxes | not exercised (no save station was reached) | a click on a screen with nothing to click counts as confirm | yes | n/a |

Not done, and why:

* The right-hand list of the Inventory and Log Book tabs (the item and entry lists). It is inactive until the pad or keyboard moves into it, and the pointer only works on the list that is active. Choosing a category on the left already fills the right list.
* Dragging the sliders of the front-end Display page. The game builds no pointer area for them (their boxes are empty), so only the row is clickable there. The wheel and the keyboard step them.
* The inventory model (Zoom, rotating Samus) and the text pages of the log book. They read the pad's commands directly. The wheel scrolls the log book pages, as the keys do.
* Save station prompts and message boxes were not reached in a run. They are built from the same frames (tables of rows) as the Quit Game question, which does work.

## How it works

The front end (title, main menu, save slots, options, extras) is built from script-driven UI components. Menus (`CUIMenuGOC`) hold widgets (`CUIWidgetGOC`), and each widget links a button (`CUIButtonGOC`) with a bounding box in the UI's own units. The UI camera is orthographic and authored for 16:9: x runs from -8 to 8, and y from -4.5 to 4.5.

The Switch version fed its touch screen into this. `CUIWidgetGOC::ProcessWidgetTouchScreenInput` selects and activates a widget at a touch position. On the PC build, the call that decides "a touch happened" is built from the invalid command and never fires, so the old `menu_touch` setting (a left click sent as a touch) never did anything. The new code feeds the same game routines from the pointer instead.

Three hooks handle the front end:

* `CUIMenuGOC::BeforeThink` hook (`menu_mouse.cpp`, `menu_hook`): before the menu runs its widgets, the pointer's position in UI units is tested against the widgets' boxes, and the nearest hit is chosen. The game's own boxes are wrong on PC for text buttons. The code that builds them adds the bounds of the inactive text panes, which are zeros, so a box runs to (0, 0) or into the next row. The hook rebuilds each box from the active parts only. It gives a text-only box the room of the bar it sits on (at least 3.3 x 0.75 units, left aligned at the text), splits the gap between the two arrow buttons of an option row, and writes the result back into the button. The game's routine then tests the same box.
* `CUIWidgetGOC::ProcessInput` hook (`widget_hook`): for the chosen widget, when the pad did nothing, a hover queues the widget as the next selection. This is the "deferred selection" that a touch on a select-only widget makes; the menu applies it after its widgets have run. A click runs the game's `ProcessWidgetTouchScreenInput`. A widget that normally only selects on the first touch acts at once for a click, because the routine runs with its touch mode set to "select and act" for that call. Hovering an arrow button selects the row's label.
* `CFinalInput::GetTouchScreenPosition` hook: answers the pointer position (in UI units) while that routine runs.

The older frames (pause screen, its Options tab, the quit question, the map's text) are `CGuiFrame` widget trees: tables of rows (`CGuiTableGroup`) and slider groups. The `CGuiFrame::ProcessControllerInput` hook (`gui_pointer`) handles them. For every visible, active table, it projects the rows' text panes through the frame's own camera (`CGuiCamera::ConvertToScreenSpace`) into screen space, and selects the row under the pointer with the table's own `MAF_SelectRowAtIndex`, which also tells the screen. A click is the accept key (the pad's A, pulsed once). Some screens read accept themselves rather than through the table's callback. A slider takes the pointer's place on its track as a new target value. The slider's own `Update` then snaps it to its increment and tells the screen, as it does for the pad. The tab and button labels of the pause screen belong to its manager (`CPauseScreenManagerMP1`, with a hook on its `ProcessControllerInput`). The label's text pane is projected the same way and widened to cover the word next to the icon.

The pointer is converted to a position on the presented picture, taking into account the letterbox from `keep_aspect` and the internal size (`menu_mouse_math.cpp`). The front end's UI keeps its 16:9 shape in the middle of a wider picture (S10). On an ultrawide window, the UI plane is the middle 16:9 part, so the pointer outside it hits nothing. The older frames are projected over the whole picture and use the camera as it is, so they follow whatever the display options did to them. Both were checked at 2560x1080 (main menu, pause screen, tabs).

Other parts:

* Cursor: the OS cursor is shown while a menu is up and the mouse was the last thing used. A key or pad button hides it until the mouse moves (`platform::set_cursor_visible`). In play (raw mouse mode) it stays hidden, as before. The game ships no pointer art (no cursor or pointer texture in its paks), so there is no game cursor to use.
* Prompts: moving the pointer in a menu counts as using the mouse. With the default `auto` prompt style, the footer icons switch to keyboard icons.
* A click on a screen where the pointer has nothing to hit (title screen, message boxes) pulses the confirm key.
* Right click is the existing `Mouse3 = back` binding of the menu and map contexts. The wheel is the existing `WheelUp/Down = dpad_up/down`. Over a slider track or an option's arrow buttons, the wheel steps the value (d-pad right / left) instead. On the map, the wheel zooms (the L and R buttons, a 160 ms press per notch).
* Map footer: the map's Key / Legend button (the pad's X) had no keyboard key. The default layout now binds `X = btn_x` in `[bindings.map]`, and the footer shows the key icon. An existing `controls.ini` keeps its own bindings, so add the line to get it. The footer's Rotate and Move still show the pad's L and R stick icons. They are not among the 17 button textures the prompt pack can replace, so no mouse or key icon can stand in for them (listed under the gaps).
* Map drag: while the left button is held, the pointer's speed becomes the left stick. While the middle button is held, it becomes the right stick. The movement is added to whatever else the sticks do (`Engine::set_aux_sticks`). A full stick is a drag of 0.8 window heights per second, whatever the frame rate.
* Test aids: `[play] pointer_draw = 1` draws an arrow at the pointer into the game's frame, because game screenshots do not contain the OS cursor. `NXRT_MENUMOUSE_LOG=1|2|3` and `NXRT_MENUMOUSE_DUMP=1` log what the pointer hits and dump the widgets of the older frames. The script step `keydown mpos X Y` puts the pointer at a window pixel, using the same events the window makes. See `docs/CONFIG.md`.

## Settings

`[mouse] menu_cursor = 1` (on by default) turns the whole pointer on or off: cursor, hover, click, wheel steps, and map drag. With it off, the left click is the `Mouse1 = confirm` binding of the menu context again. There is a checkbox, "Mouse pointer in menus (cursor, hover, click)", on the F1 page (Controls tab) and on the launcher's Controls tab. The old `menu_touch` key is still read and ignored.

## Decisions

* The pointer goes through the game's own widget code wherever there is a pointer path: front-end selection and the touch routine, and table row selection. The accept in the older frames and the labels of the pause screen are pad button pulses, because those screens read the buttons themselves.
* Every box's text is padded to a bar-sized area, not sized to the text bounds alone. Only the Switch's touch screen needed those bounds to be exact.
* The OS cursor is used. It does not appear in the game's own screenshots, which is why `pointer_draw` exists.
* A click acts at once on any item, as in PC menus. The Switch needed a second touch on select-only items.

## Tests and rerun

* Runtime: `pwsh mouse_tests.ps1 [-Filter re] [-NoBuild] [-Clean]` runs every unit, gfx and lift test of the worktree in `work\mouse_layout`. New groups: `menu_mouse` (arithmetic and pointer state), new cases in `play_engine` (pulse, aux sticks) and `play_config` (`menu_cursor`, the ignored `menu_touch`).
* Recompiler: `mouse_oracles.cmd` (difftest, mutation, e2e, hooks, known answers).
* The game: run `cfg_mouse.cmd` once, then `build_mouse.cmd`. `mm.sh boot` starts it in a window (run folder `work\run_mouse`). `mm_pause.sh` goes through New Game with the mouse and opens the pause screen. The commands are `mm.sh move X Y`, `click [Mouse1|Mouse3]`, `down/up`, `wheel DY`, and `shot NAME`.

## Gaps

* The map footer's Rotate and Move keep the stick icons while the mouse is used (see above). The prompt pack replaces only the game's 17 button icon textures.
* No save station or message box was reached in a run.
* The pointer does not move between the two lists of the Inventory and Log Book tabs.
* Front-end sliders are not draggable.
* Ultrawide was checked on the main menu and the pause screen only. 32:9 and a window narrower than 16:9 are covered by the arithmetic tests, not by a picture.
* Exclusive fullscreen: the pointer maps through the picture the present pass draws, and the cursor is the OS one. Not checked in a run.
