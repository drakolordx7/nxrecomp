## What the stalls were, and what changed

### 1. Texture first use on the render thread

Findings from the trace (marks `tx.init`, `tx.reg`, `tx.flush`, `tx.use`, `[nvn] tex_prep_log`):

* About 7,700 textures are uploaded in the first 100 s of the route. 7,500 of them are the video planes of the cutscenes (a 1600x900 R8 plane and an 800x450 RG8 plane, a new texture object for every movie frame, 0.55 ms together on the render thread). That is a steady cost during a movie, not a hitch. The ASTC textures that come from the BC7 cache take 0.1 to 0.5 ms each.
* The hitch is six sparse 3D textures that the hangar loads (512x256x368: two BC6H of 46 MB, four BC1 of 23 MB). They are registered in a texture pool about ten seconds before the first draw, their tiles are mapped and written piece by piece, and each takes 15 to 60 ms in `prepare_texture` plus 20 to 45 ms to copy into a staging buffer. One frame of 280 to 450 ms.
* The game never says when a texture's data is final: only 271 of 7,985 textures saw a flush of their memory before first use, and a texture is initialized, registered and drawn within about 2 ms. Nothing can be prepared "when the game is done"; the preparation has to be checked against the content.

What the stream added (`src/gfx/nvn/nvn_texprep.cpp`, header comment of `nvn_texprep.h` has the full rules):

* Worker threads (a third of the hardware threads, 2 to 8) run `prepare_texture` for block-compressed textures before the first use. A job starts when a handle of the texture is bound in a command list being recorded, when a texture of at least 1 MB is registered in a texture pool, and, for a sparse texture that was named by one of those, 40 ms after the last tile write.
* A result is used only if no CPU write was reported since the job started and the storage still hashes to what it hashed to before and after the job. A texture whose job is still running is waited for. Anything else is prepared on the render thread exactly as before, so a texture is never drawn with data that is not ready and never with older data than the old path would have used. `[nvn] tex_prep_verify = 1` compares every used result with a fresh preparation (365 results compared in a full route run of the final build, none differed).
* Jobs never transcode: an ASTC texture without a disk cache entry is left to the render thread (an unfinished texture would otherwise cost a long transcode of data that may still change).
* A big result (1 MB and more) is also copied into its upload buffer by the job, so the render thread only records the copy. Without that the staging allocation and the 47 MB copy still cost 20 to 45 ms per volume.
* The sparse texture gather copies tile pieces without holding the pool's lock, and a texture that sits in one piece of one physical pool is untiled straight from it (no 47 MB copy).
* Memory held by finished results is capped (`[nvn] tex_prep_mb`, 512 MB; oldest unused results go first). A worker that touches a page the game has unmapped is caught.
* Hooking the bind path would cost the recording thread a handle lookup per bind (thousands per frame). A small per-thread table of handles already looked at, reset whenever a texture is initialized, registered or written, brings that to one comparison for nearly every bind.

Result: see the table at the top. In a run, about 750 textures are scheduled, 365 are used from a job (one or two of them waited for), none were stale, and about 250 were declined because they had no cache entry or changed under the job. At the hangar load the render thread now spends 15 to 35 ms in total waiting for jobs, and the worst frame went from 280-445 ms to 110-125 ms.

What is still on the render thread at that load: the sparse volumes are finished by the game a few milliseconds before the draw, so their jobs run while the frame waits (a frame of 110 to 250 ms against 280 to 450 ms before).

### 2. Movie decoder start and stop on the main thread

Stall attribution named three calls, 14 to 15 times per run: `Extractor::GetSampleTime` (60 to 120 ms) at every movie start and at every loop restart, `Extractor::~Extractor` (60 to 80 ms) at every movie end. The extractor's worker had not decoded anything yet when the main thread asked, and the destructor joined the worker and released the Media Foundation reader (which stops its decoder) on the main thread.

* Preroll: once the game has selected every audio and video track, `SelectTrack` starts decoding and waits (at most 2 s) for the first samples. That runs on the guest loader thread that sets the movie up (36 to 78 ms in the logs), so the main thread's first `GetSampleTime` finds them queued. With some tracks unselected nothing changes (a track selected after reading began would start late).
* Loop look-ahead: when every selected track has reached its end, the worker positions the reader at 0 and decodes the first samples into a second queue. `SeekTo(0)` of a looping movie swaps it in (6 samples queued in the logs). Any other seek, or a track selection, drops it.
* Close: the destructor returns at once; a short-lived thread joins the worker and releases the reader.

The new loop test (`media_movie.movie_loop_restart`) found a real mistake in the first version: a sample read for the look-ahead at the moment it was swapped in was thrown away, so the second pass started one frame late. Fixed (such a sample now goes to the queue that replaced the look-ahead). The 25-movie oracle (`media_movie.movie_all_fmv`, every frame md5 against ffmpeg, timestamps, audio) passes with all three on. One stall per run is left at the first output buffer of a movie (`Decoder::GetOutputBuffer`, 35 to 90 ms once); not touched.

### 3. Reflex against the new pacing

Two problems, both found by running `[latency] mode = on` with the frame trace:

* The frame cap never reached Reflex at start. `set_cap_fps` ran before the renderer existed, so the swapchain's Reflex sleep mode was set with a minimum interval of 0 us ("interval 0 us" in the log) and stayed that way until the next settings change. A new instance now starts with the remembered cap (`lowlat_note_cap`), and the log says "interval 16666 us".
* With a cap, Reflex's sleep (minimum interval between simulation starts) is the frame pacer. The limiter's wait at the frame boundary stacks a second pacer on the same frame. While Reflex is active and a cap is set, the boundary wait is skipped (`[latency] reflex_limiter = true` keeps it). The limiter still paces presents that no boundary paced (loading screens, movies).

Numbers (cap 60, three to five runs per column, same exe, input to present p50 / p95 in ms): Reflex off 6.5 / 10.2, Reflex alone 6.0 / 9.7, Reflex plus limiter 8.7 / 15.5. Frame rate 59.6 to 59.8 in all three. Reflex helps where a queue exists: uncapped, input to present p95 falls from 21.8 to 12.1 ms and input to GPU p95 from 34.0 to 23.7 ms. Two game instances run at the same time on one GPU are not a usable comparison: whichever instance the driver starves shows 45 fps and 300 intervals over 50 ms with any setting, so all runs here are one at a time.

### 4. The vsync and uncapped matrix

With vsync on and no frame cap below the display's refresh rate the limiter used to stand aside: the display paces. The matrix showed what that does to latency. The game renders as fast as the swapchain takes frames, the queue behind the display fills (three images, FIFO), and every picture is shown one to two frames after it was simulated: input to present 14.2 ms median at 144 Hz, input to GPU finished 26 ms, against 7 ms at a 60 fps cap. Switching the wait for frames in flight to 0 changed nothing (input to present p50 14.3 ms, input to GPU finished 26.6 ms), so the queue sits in the display path.

Fix (`[latency] vsync_cap`, default on): with vsync on and no cap below the refresh rate, the limiter holds 0.05% under the refresh rate (143.93 fps at 144 Hz), so the queue stays empty. The cap is set when the window exists (it was read before that and was 0) and again after a window mode change. Reflex, when on, takes the same cap as its minimum interval. Measured: input to present p50 fell from 14.2 to 9.3 ms and input to GPU finished from 26.1 to 19.0 ms; the p95 does not move (31 ms) because the heavy parts of the route are GPU bound and the queue builds there whatever the cap. The limiter's wait zone confirms the cap is active in the new runs (median 3 to 5 ms per frame; no wait before). A frame is repeated about once every 14 s when the display's real rate is exactly the reported one. With a refresh rate that cannot be read the cap stays 0.

Uncapped: nothing to fix (260 fps either way); Reflex is the one that helps there (p95 from 22 to 12 ms). Cap 120: the route is GPU bound in its heavy part (about 110 fps), and before and after agree within the spread.

The three movie stalls left are `Decoder::GetOutputBuffer` at the first frame (35 to 90 ms, once per run) and one frame where the main thread slept in the limiter (see below).

## What is left

* The area-load frame at the hangar (110 to 250 ms): the render thread waits for the jobs of the sparse volumes, which the game finishes writing a few milliseconds before drawing them. A parallel untile of one big level would shorten it; `tegra_tiling` (tools repo) has no range version of `untile_level`.
* Memory pool imports: the 360 MB pool takes 100 to 140 ms on the importer thread and the render thread waits (no lead: the game makes the pool and uses it in the same frame); the 110 MB pool 30 to 65 ms when the render thread has to import it itself. The driver's cost grows with the size of the pool (0.3 ms/MB). Importing in chunks would change how GPU addresses resolve; not done.
* An empty pipeline cache (a player's first run; `SEED=0` in `st_run.sh`). The first runs of this work, with no pipeline cache and no key file yet, had three to five frames per run of 90 to 750 ms inside `pipe.create`. A run with an empty key file but the driver's own shader cache warm shows none, so a first run of a player cannot be reproduced on this machine. Prewarm only helps from the second run, because the key file is written by the first. Shipping a recorded key file with the release is your decision (the file is derived from the game). * GPU waits (`nvnSyncWait`, `gpu.exec`): the game waits for a fence of its own submission while the GPU time-slices with other processes. They scale with how many other game instances run on this machine (one run had 241 of them, 9.5 s in total, while another stream was running games). The runtime cannot remove them.
* Long waits inside the limiter's timer (60 to 300 ms, one to four per run, before and after alike): the main thread sleeps in the limiter's timer wait for far longer than planned. The new warning in `FrameLimiter` (`frame wait: planned 12.3 ms, woke 77.8 ms after the target`) shows the plan was right and the thread woke late, so it is not schedule drift. A busy machine and a window that is not in the foreground are the likely cause (the runs here are started from the background with two to four other game instances running); I did not find a mechanism inside the runtime and did not change the limiter. If it shows up for a player in the foreground, the warning is already in the log.
* `LockBusyMutex` on the main thread (35 to 100 ms, once per run): S20.
* Anti-Lag 2 (AMD) was not run: no AMD GPU here. It receives the same remembered cap.
* The video planes of cutscenes still cost 0.55 ms per movie frame on the render thread (a new texture object per frame; not a hitch).
