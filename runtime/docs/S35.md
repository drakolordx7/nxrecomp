# S35: controller play

Branch `pad`. The right stick looks up and down again. The free lock-on turns the way the game's own turn does. A pad now works through the whole game: menus, map, log book, morph ball, scan, lock-on, charge, missiles, rumble and gyro. No new hook in the recompiled code was needed, so there was no relift.

The test machine has no real controller. Every pad check here ran through an SDL virtual gamepad inside the game process (see "Testing without a pad"). It uses the same SDL, mapping and game input path as a real pad. The end of this page lists what a virtual pad cannot show.

## What was wrong with the stick

The mouse aim hooks `CPlayerMP1::ProcessInput`. It kept its own pitch angle and, after the game's code ran, wrote that angle over the game's pitch and pitch target. The right stick works by moving that target, so each frame the stick's change was overwritten. Sideways looking worked because it goes through the body's turn, which the aim never touched.

Now, while a pad is looking up or down (the right stick's vertical axis is off centre, or the gyro is moving), the aim leaves the pitch to the game and takes the game's value as its own. The mouse still adds to it in the same frame. The first frame after the stick is let go takes the game's pitch again. Whichever device was used last wins, so the two never fight.

Checked in the Frigate hangar with the Dual Stick scheme:

| Test | Result |
|---|---|
| Stick down, then up, at 60 steps per second | Pitch goes to the game's limits (-1.22 and +0.87 rad) and stays where the stick left it |
| Mouse up 0.46 rad, stick up 0.16, mouse up 0.11, stick down 0.23 | Every step adds on top of the last one |
| Free lock, stick up and down | The view stops at +0.35 and -0.35 rad, the free lock margin |

## The game's own controls

The pause menu's Options, Controls page has four schemes (Dual Stick, Pointer, Hybrid, Classic), inversion for both axes, sensitivity settings for the camera, aim and spring ball, and a few layout swaps. The pad behaves as it does on a Switch, since it goes through the game's own code. Dual Stick is the default, and it is the scheme the stick pitch above applies to.

| Scheme | Pitch from the right stick | Gyro |
|---|---|---|
| Dual Stick | accumulates while the stick is held, stays when let go | none |
| Hybrid | eases back to level; R or ZR held turns the stick into a free look | R or ZR held = gyro camera |
| Classic | R or ZR held = free look, eases back to level | none |
| Pointer | pointer on the screen | pointer from the pad's orientation |

## Frame rate

Superseded by `docs/S36.md`: the stick's pitch code now runs at 60 calls per second whatever the step rate, the gyro is scaled by the step, and the fitted exponent below is gone. The numbers in this section describe the S35 build.

In the Dual Stick scheme the game adds the stick's pitch to its target once per ProcessInput call, with no time step. At 60 steps per second that is 1.18 rad/s at full deflection. At 144 steps per second the same code gave 2.7 rad/s. The amount added also grows with the stick's deflection, to about the power 2.2 (measured: 20, 50 and 90 percent give 0.5, 20 and 80 percent of the full step). Scaling the result would not work. The game keeps a smoothing filter on that target, and rewriting the target makes it drift. The fix scales the stick's vertical axis before the game reads it, by (step x 60) to the power 1/2.2, while the scheme is on.

| Steps per second | Pitch speed at full stick (rad/s) |
|---|---|
| 60 | 1.18 |
| 90 | 1.17 |
| 120 | 1.11 |
| 144 | 1.19 |
| 240 | 1.39 |
| 30 | 0.54 |

Below 60, the stick is already at full range and cannot be scaled up, so 30 steps per second pitches at half speed. At 240 it is 17 percent fast, because the game's response is not an exact power law. To rerun: `python pad_pitch_sweep.py 30 60 90 120 144 240` (needs a pad run in gameplay, see below).

The gyro look has the same fault, and it is not corrected. In Hybrid, the same turn of the pad pitches 2.7 times as far at 144 steps per second and 4.5 times as far at 240 as at 60. The input is the sensor's angular rate, and the game adds it once per call. Yaw is not affected, because it goes through the game's physics.

## Free lock-on with the stick

The game turns Samus toward the stick by pushing her angular velocity toward the stick, times the full turn speed. Lock-on skips that step, so S32 applied the full turn speed at once. It now ramps up the way the game's own turn does. Measured with the body unlocked at 60 steps per second, full stick from rest: 47, 72, 85, 92 and 96 percent of full speed in the first five frames, then 45, 11 and 2.6 percent in the three frames after the stick is let go. That fits an exponential approach with a time constant of 0.0262 s going up and 0.0117 s going down (`turn_ramp_step`, constants in `play_lockcam.cpp`). In free lock, the same measurement gave 0.706 of the 1.5 rad/s full turn speed in the first frame (47 percent), the same curve. Because the ramp is exponential in time, it is the same at every frame rate.

The view still stops at the margin: yaw 0.58 rad (33 degrees) either side of the target, and pitch 0.35 rad, as in S32.

Everything here used an SDL virtual Xbox pad in the Frigate hangar, on a fresh New Game.

## Gyro

`[pad] gyro` (default on) passes SDL's gyro and accelerometer data to the game's six-axis sensor. Two additions:

* The pad's orientation (`direction` and `angle` of the six-axis state). The game's Pointer scheme reads this, and it was always the identity before. `pad_orient.cpp` integrates the gyro and slowly pulls the tilt back toward gravity using the accelerometer.
* The hid service now takes both from the input source instead of writing the identity.

Checked with a virtual gyro (SDL virtual sensor data):

| Scheme | What happens |
|---|---|
| Hybrid, R held | A gyro turn about the pad's x axis pitches the view, y and z turn it. Without R nothing happens |
| Dual Stick, Classic | The gyro does nothing, as in the game's own diagram |
| Pointer | The game asks for a calibration (passes), after that the view reacts to the gyro. The directions of the turn were not checked against a real pad |

`gyro_scale` multiplies the readings (0.1 to 4). With a DualSense or Switch Pro pad, try Hybrid's R-held gyro camera first.

## Settings

New keys in `[pad]`. All are documented in `docs/CONFIG.md`, on the F1 page and in the launcher's Controller tab:

| Key | Default | What |
|---|---|---|
| `deadzone` | 0.10 | left stick dead zone (it was both sticks') |
| `right_deadzone` | 0.10 | right stick dead zone; a file with only `deadzone` gives the right stick the same |
| `invert_y` | off | right stick up looks down, in play only; adds to the game's own invert |
| `look_sens` | 1.0 | multiplies the right stick in play (0.25 to 3) |

Rumble (`rumble`, `rumble_scale`), gyro (`gyro`, `gyro_scale`) and the trigger point were already there. Checked in the game (fresh New Game, `invert_y = 1`, `look_sens = 0.5`): pushing the stick down looks up. Pitch speed drops to about a quarter (0.0045 rad per frame against 0.0195), because the game's pitch response is roughly the square of the deflection. Sideways turning is linear and drops to half.

## Testing without a pad

* Script steps in the live test mode (`src/gfx/play/play_vpad.cpp`): `keydown vpad attach xbox|ps4|ps5|switch`, `vpad axis lx|ly|rx|ry|lt|rt <value>`, `vpad button south|east|west|north|back|guide|start|lstick|rstick|lshoulder|rshoulder|up|down|left|right <0|1>`, `vpad gyro x y z` (rad/s), `vpad accel x y z`, `vpad detach`. The virtual pad needs a window run (`python live.py start --gfx window`), because SDL announces pads through the window's event pump.
* Helper scripts in ``: `pad.sh` (live driver for `game-build-pad`), `pad_cmd.py "line|line" ...` (send script lines and print the status), `pad_tap.py TAG btn ...` (tap buttons with a shot after each), `pad_matrix.py` (what each button changes), `pad_pitch_sweep.py` (pitch speed per frame rate).
* A development run needs `NXRT_PROMPTS_DIR=<runtime>\assets\prompts` for the game's own prompts.

## Not verified, needs a real controller

* Real stick feel, and the dead zone and sensitivity values. The virtual pad sends exact values.
* Rumble on a real motor. The game's values do reach SDL's rumble call. A DualSense or Xbox pad may need different strengths; `rumble_scale` is there for that.
* Gyro: the scale of the sensor data (SDL gives rad/s, the console rev/s), axis directions, Pointer scheme direction, and drift. Frame-rate scaling for the gyro look is not done.
* How Hybrid and Pointer feel with a pad held the usual way.
* Grapple: the Frigate has no grapple point, so it was not tried (the lock-on code is the game's own).
* The morph ball camera did not move with the right stick in the hangar. The ball's camera follows the ball by itself in the Dual Stick scheme. The mouse orbit is a PC feature of S13. Since S36 the right stick orbits it too.

## Known

* (Fixed in S36.) 30 steps per second pitches at half speed with the stick (see Frame rate).
* (Fixed in S36.) The gyro look follows the frame rate above 60 steps per second.
* (Removed in S36.) The stick scale's exponent (1/2.2) is a fitted number, not read from the game.
