# 402 Input-to-picture latency of 50 ms at 60 fps: the limiter sleeps in the present call and the game queues three frames

Symptom (S18): the earlier proxy put input to present at 250 to 360 ms. Measured as below on a run with the full shader cache, it is 49 ms at a 60 fps cap and 24 ms at 120 in player-controlled frames: three frame times.

Measurement (`src/gfx/extras/lowlat.cpp`, `src/gfx/vk_renderer.cpp`, only while `[prof] trace` is on): every frame carries an id from `CGameArchitectureSupport::Update` to its present. Marks: `lat.sim` (frame start), `lat.input` (the sample that `ProcessInput` takes; the last one of an id wins), `lat.inflight` (frames simulated and not presented when a frame starts), `lat.gpuq` (GPU submissions not finished), `lat.present` and `lat.present_end` (present call), `lat.gpudone` (a watcher thread waits on a timeline semaphore that the present submission signals, so this is the GPU finishing the frame's last command buffer). A present with no simulation behind it (loading, menus) carries id 0 and does not shift the ids of later frames. `lat_report.py` turns the trace into median, p95 and the in-flight counts. A WDDM capture with Nsight Systems of the same run agrees on the cadence (DXGI present starts 16.67 ms apart at p50) and shows the present call returning in 0.27 ms, so nothing queues behind the present.

Where the delay sat: the frame limiter ran inside `nvnQueuePresentTexture` on the render thread. With the render path faster than the cap, the render thread slept there and the game's main thread, which runs two frames ahead of the render job, filled that queue: `lat.inflight` was 2 at every frame start, so a sample was shown three frame times later. The GPU queue was short (`lat.gpuq` 0 to 2), and the four submission slots, the swapchain (3 images, present returns at once) and the present pass were not the cause.

Fix: the limiter waits at the frame boundary (`update_hook`), before the input is sampled; the present call only runs the pre-frame hook (present mode changes) and waits itself only when no boundary paced the present (loading screens, movies). A frame now starts one render time before it is shown. The wait for frames still in flight (`[latency] frames_ahead`, default 1) is on by default and gives up after 100 ms, or at once when nothing has been presented for 250 ms. `[latency] pace = present` restores the old placement.

Measured (player-controlled frames of the gameplay run, same exe, toggled by `NXRT_LATENCY_PACE`), input to GPU done, median / p95: cap 60 50.3 / 56.5 ms before, 13.6 / 22.9 ms after; cap 120 26.1 / 58.6 ms before, 12.7 / 42.7 ms after (GPU-bound in the heavy part, GPU shared with other games). Input to present call returned at cap 60: 49.1 / 49.5 before, 9.1 / 13.9 after. Frames in flight at frame start: 2 before, 0 after.

Trade-off: the old queue also hid main-thread hitches of up to two frames; with the limiter at the boundary a main-thread stall (a movie decoder start, for one) shows as a long frame. The remaining stalls are listed in S18.md.
