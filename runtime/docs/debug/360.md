# 360 Freezes during loading: a spinning busy mutex starves the lock holder

Symptom (sweep, S15): in roughly one boot in ten the game stops producing frames during a loading screen, or later during an area load. The watchdog reports "no frame tick" and the thread dump always looks the same:

- the main thread waits in `CGraphicsFrameToken::WaitUntilFinished` (the graphics frame never completes) or spins in `nn::os::LockBusyMutex` called from `TAllocatorLock<CBusyMutex>::Alloc` (`CGameAllocator::Alloc`);
- one or two more guest threads (the job workers, the room loader) also sit in `LockBusyMutex` for the game allocator lock;
- exactly one guest thread is inside the game allocator with the lock held, at a different place in each dump (`CSmallBlockAllocator::Free`, `CGameAllocatorHeap::FindFreeBlock`);
- the NVN render thread is idle.

Where it is not: not the render thread (idle), not a lost wake-up (nothing waits on an event), not allocator corruption (the two dumps show the holder at different places in its code, and `NPowerBlock::TAllocator::Free` has no loop that could cycle).

Cause: `nn::os::LockBusyMutex` is a pure spin lock: `ldaxr`, `cbnz`, `wfe`. The lifter compiles `wfe` as a no-op, so a waiting thread spins at full speed and never gives the processor away. On the console the waiter spins on its own core and the holder cannot be preempted (the SDK raises a disable count in the thread's TLS while it holds the lock). Here the console core model (`kernel/sched.cpp`, debug notes 180 and 221) pins every guest thread to one of three host processors and maps the HOS priority bands to Windows priorities with the wake-up boost off. A spinner that outranks the holder on the same processor keeps it off the processor; Windows' starvation boost gives the holder a few milliseconds every few seconds, so the lock stays held for minutes while every other thread waits for the allocator. Measured on this machine with a stand-alone program (`.weaver/busy_spin_demo.cpp`: a lowest-priority holder doing 300 ms of work with the lock held, a highest-priority waiter pinned to the same E-core): the pure spin gets the lock after 4.2 s, the yielding waiter after 0.31 s. Every contended section of the allocator lock can cost such a stall, and machine load (more runnable threads on the same three processors) makes it worse: the freeze showed up twice in about a dozen boots while other games and builds were running, not in 8 quiet boots, and not at all in 28 boots of the first sweep pass (three games at once, but the sweep's own runs were the only load).

Fix (`src/kernel/busy_mutex.cpp`, `[sched] busy_mutex_hle`, default on): `LockBusyMutex` is replaced by host code through `module_override_symbol` (main reaches it through its import). It acquires with a compare-and-swap on the lock word at +0x10 (the same value the SDK's `ldaxr`/`stxr` pair uses, so it interoperates with the SDK's `TryLockBusyMutex` and `UnlockBusyMutex`, which stay guest code) and raises the TLS disable count on success, and while it waits it goes `YieldProcessor` x64, then `SwitchToThread` (which hands the processor to any ready thread on it, a lower-priority holder included), then `Sleep(1)` after 20000 rounds.

Regression test: `kernel_busy_mutex.waiter_that_outranks_the_holder_does_not_starve_it` (a lowest-priority holder doing 300 ms of work with the lock held and a highest-priority waiter pinned to the same processor; the waiter must get the lock) and `uncontended_lock_sets_word_and_disable_count`. The sweep (`tools\test\sweep.py`) is the end-to-end check.

Not covered: `TryLockBusyMutex` does not spin, and the lifter's `wfe`/`yield` no-ops affect any other guest spin loop (a lifter-side `yield` in `wfe` would cover them all; noted for the lead).
