# S19: integration and polish

Branch `polish`. It merges the button prompt work (`prompts`) into the main line, checks it in the real game, and closes five loose ends from the last session.

## Merge of `prompts`

Every conflict with the display extras was additive, so both sides were kept: both sets of settings sections (`[hdr]`, `[upscale]`, `[latency]` and `[prompts]`), enums, ini writers and readers, struct members, tests, and the declarations in `nvn_core.h`, `nvn_texdata.h` and `nvn_texture_registry.cpp`. The `console_block_height` fix in `nvn_texture_layout.cpp` also stays. It fixed 263 small textures that were being untiled with the wrong block height.

## Button prompts in the real game

The first real run found two bugs the unit tests could not see.

1. The front end has its own icons. The title screen and the menus draw red copies of the buttons from `PreloadFrontEndMPT.pak` (`btn_A`, `btn_A_P`, `btn_B` ... `btn_minus`), not the blue ones of `GuiSysMP1.pak` that the table listed. The hook never recognised them (the log showed "17 of 17" and not one replacement). `prompt_resolve.cpp` now carries the front end id next to each icon (16 of 17; the d-pad is the same texture in both), and the scan in `prompts.cpp` hashes both copies (33 textures).
2. The game stores its UI textures upside down. The first replaced icons came out with the A upside down and the Enter arrow flipped. The hook now writes the upright pack icon with its rows reversed (`tex_override.h` says what order the hook has to deliver).

Evidence (screens from `polish_shots.sh` (local test script), 1920x1080, headless, files in `work/polish_shots/`):

You can switch styles without a restart. The Button prompts combo on the F1 page sets `prompts.style`, the same way the self-test step `set:` does (queued, applied at the next frame). `set:prompt_style=<name>` is new. In a window run (`NXRT_PLAY_SELFTEST=wait:1500,set:prompt_style=xbox,wait:180,set:prompt_style=playstation,...`) the title prompt went Switch, Xbox, PlayStation, keyboard, Switch with no restart. The log shows each change, and the icon textures were resolved again (`TXTR_ButtonA -> xbox/a`, `ps/cross`, `kbm/return`). `work/polish_shots/live_switch.png` has the pictures. Not covered: clicking the combo on the F1 page itself. Nothing can drive the Dear ImGui page from outside, so the step calls the same apply path instead.

## Setup tool: texture cache entry formats

`tools/setup/src/texcache.cpp` now writes the three entry kinds described in `docs/S4f.md`. The key formula is unchanged. The encoder revision is now 3, so the marker file triggers a rebuild of any old `bc7_cache`.

* BC5 is used for a linear texture whose level 0 is fully opaque and whose blue channel is at most 2 (two-channel normal maps). It is encoded with `rgbcx::encode_bc5_hq` from bc7enc_rdo, which now sits in the setup core next to the reference BC7 decoder.
* RGBA8 (UNORM or sRGB, matching the source) is used for a texture whose BC7 result is under 28 dB. Measured over all 4,413 textures at quality 3, only one falls under 33.6 dB: the white-noise lookup, at 19.2 dB.
* Block height. The runtime's `console_block_height` (the S17 fix) also applies to ASTC textures, and the cache key includes the block height. Setup still used the smallest covering height. For the affected textures, that meant writing entries under the wrong key and untiling them incorrectly. Setup now follows the console rule.

Full run on the player's RomFS: 4,413 ASTC textures, 4,369 distinct cache keys (44 textures share one), 0 failed, 3 min 34 s on all threads: 1,395 BC5, 1 RGBA8 (349,804 bytes, `3933333769ba44db.bc7`), 2,973 BC7. `check_texcache.py` over 734 entries (every 6th texture, 238 of them BC5): PSNR RGB minimum 34.84 dB, mean 50.35. Two textures miss the script's default floors (SSIM 0.962 and alpha 32.6 dB). They are the two known worst cases of `check_texquality.py`, and they are BC7 as before. In the game, 78 BC5 entries were loaded from this cache in one gameplay run.

## Vulkan validation error "image is VK_NULL_HANDLE"

Cause: a texture still alive at back-end shutdown (the game never finalized it, or a test left it behind) stayed in the texture registry, and `gpu::tex_shutdown` freed every image. The texture kept its pointer to the freed image. The next texture created over the same memory with the same shape matched it as an alias (`texture_registry_find_alias`, added in S4f) and used freed memory: a barrier on a null or garbage image, or a crash. In `gfx_nvn_scene_state` this showed under load, because the heap reused the freed block. Before the fix, the group crashed or logged the error in 5 of 8 runs.

Fix: `texture_registry_detach_gpu()` clears `Texture::gpu` on every registered texture before the images are freed. Regression test `gfx_nvn_texgpu.shutdown_detaches_live_textures_from_freed_images` (verified to fail without the fix). After the fix, `gfx_nvn_scene_state` ran 8 of 8 clean with validation on.

A gameplay run with validation on (hangar and map screen, 204 seconds in) found a second error, `VUID-vkCmdDraw-imageLayout-00344`: ten draws sampled an image in SHADER_READ_ONLY while it was the colour target of the pass. The back end already binds the dummy texture when a draw samples its own colour or depth target, but it compared texture objects. Since S4f, several objects over one storage share one image, so the sampled object and the target object can differ while the image is the same. `nvn_replay.cpp` now compares the image (`shares_image`). Regression test `gfx_nvn_scene_texture.sampling_an_alias_of_the_pass_target_binds_the_dummy` (reproduced the exact error before the fix).

## Shader cache

Block `46742355274dd77e` was never missing from the cache. It is translated (7,632 bytes, `spirv-val` clean) and was already in the release pack. The "missing" lines came from probe runs with no shader cache configured at all; every one of the 454 blocks in those runs showed as missing. The block that really was missing from the pack is `f8e9efd694abe636`, which S4f translated after the pack was built. The pack is rebuilt from the 13,019 modules of `work/shader_cache/spirv` (13,020 entries with `results.tsv`, zstd level 12, 261 MB) at `work/setup_test/shader_cache.mprshc`. Both blocks are inside.

## Release

* `tools/release/make_release.py` now ships `prompts/prompt_icons.pak` and `prompts/LICENSE-Kenney-InputPrompts.txt` (`--prompts-dir`, default `runtime/assets/prompts`). The audit still rejects every other `.pak`. This one passes on its exact path, a size under 4 MiB and its `MPIP` header.

* The Visual C++ runtime was open here and is closed in S22: every shipped binary is now linked against the static runtime (`/MT`), so players need no redistributable. See `docs/S22.md`.
