# S14: HDR output, upscaling and low-latency modes

Work area S14 of the Metroid Prime Remastered recompilation. Branch `extras`. Everything here is off by default except HDR "auto", which turns on only when Windows reports HDR for the monitor.

## Result

| Feature | State |
|---|---|
| HDR10 and scRGB output | Done and checked on screen in an offscreen HDR10 image (see "HDR" for what could not be checked). The scene runs in float16, the game's tone curve keeps its look up to the start of its shoulder and then reaches the display's peak, the HUD stays at paper white. |
| NVIDIA Reflex (VK_NV_low_latency2) | Done and measured on the RTX 3080. |
| AMD Anti-Lag 2 (VK_AMD_anti_lag) | Written to the extension's specification, not run: no AMD GPU here. |
| Frames-ahead pacing | Done: a host-side wait that keeps the game's frame queue short, on any GPU. |
| FSR 1 spatial upscaling | Done, in two places (the finished picture, and the HDR scene before the game's tone-map). |
| FSR 3.1 temporal upscaling, DLSS, XeSS, frame generation | Not done. The renderer produces no motion vectors and no jitter; "Upscaling" says what each needs. |

## Settings

Everything is in `controls.ini` (the F1 page, tab Extras, edits it) and can be overridden from `mpr.ini` or the environment (`NXRT_HDR_MODE` and so on); a key set in `mpr.ini` or the environment wins over the file.

| Section | Key | Default | Meaning |
|---|---|---|---|
| `[hdr]` | `mode` | `auto` | `off`, `auto` (HDR when Windows reports HDR on for the monitor), `on` (HDR scene pipeline whatever the display says). Applies at the next start. |
| `[hdr]` | `format` | `auto` | `auto` (HDR10 when offered, else scRGB), `hdr10`, `scrgb`. Next start. |
| `[hdr]` | `peak_nits` | `0` | 0 takes the display's reported peak (1000 when it reports none); else 200 to 10000. |
| `[hdr]` | `paper_white_nits` | `0` | 0 takes Windows' SDR content brightness when HDR is on there, else 203; else 80 to 500. |
| `[hdr]` | `highlight_boost` | `1.0` | 0 keeps the game's SDR look, 1 lets highlights reach the peak, 2 pushes further. |
| `[upscale]` | `mode` | `off` | `off`, `fsr1`. (`fsr3`, `dlss`, `xess` are read and kept but do nothing yet.) |
| `[upscale]` | `sharpness` | `0.8` | RCAS sharpening, 0 to 1. |
| `[upscale]` | `scene_scale` | `100` | Percent (25 to 100) of the output size per side at which the 3D scene is rendered; the HUD and post effects stay full size. Live. |
| `[latency]` | `mode` | `off` | `off`, `auto`, `on`, `boost`. `auto` and `on` use Reflex or Anti-Lag 2, whichever the GPU has, and the frames-ahead wait. Next start. |
| `[latency]` | `frames_ahead` | `1` | With the mode on, a frame's simulation starts only when at most this many earlier frames are still on their way to the screen (-1 to 3, -1 turns the wait off). |
| `[latency]` | `log_timings` | `0` | One log line per second with the latency numbers. |

The log line `gfx: HDR:` at start-up states what the surface offered, what Windows reported, and the levels chosen. `[gfx] log_fps = 1` writes the frame rate and the GPU time of the present pass once a second.

## HDR

How it works, in the order a frame goes:

1. At start-up the renderer reads the surface formats and asks Windows (DXGI `IDXGIOutput6::GetDesc1` and the display-configuration API) whether the monitor has HDR on, its peak luminance and its SDR white level. The NVIDIA driver lists HDR10 and scRGB formats whether or not Windows HDR is on, so `auto` needs Windows' own answer and falls back to SDR when it cannot get one (a disconnected session, for instance). The result, the paper white and the peak are published as `HdrState`.
2. With the HDR scene active, the NVN back end keeps the render targets of the post chain (the window texture and the targets the post passes copy through; 8-bit sRGB, created compressible or for display) as float16 instead. They hold linear light where 1.0 is paper white; the game's own blends (bloom, FXAA, the HUD) work on them as they did on the sRGB targets, which also blend in linear.
3. `NTonemap::build_tonemap_eval_params` (main + 0x211c60, a new entry hook) writes the 80-byte curve block the tone-map shader reads. The runtime lets it run, then replaces the shoulder (rational, `y = B + A v / (v + 1)`) by one with the same value and slope where it starts and an asymptote at the peak: `A' = R - y0`, `B' = y0`, `p' = s / (R - y0)`, `q' = -p' t2`, with `R = 1 + boost * (peak / paper_white - 1)`. Everything below the shoulder, and every per-room parameter (exposure, toe, grade), is the game's.
4. The tone-map fragment shader samples two 3D grading volumes with the curve output as coordinate, so values above 1 would clamp. The runtime patches the shader's SPIR-V (matched by structure, not by hash; `hdr_tonemap_patch`): each graded channel is multiplied by `max(y, 1)`. With the unextended curve `y <= 1` everywhere and the shader writes exactly what it wrote before.
5. The present step (`OutputPass`) encodes the float window texture: HDR10 (BT.709 to BT.2020, nits = value x paper white clamped to the peak, ST 2084), scRGB (value x paper white / 80), or sRGB for an SDR swapchain. HDR metadata (`VK_EXT_hdr_metadata`) carries the peak. The F1 page is drawn into an RGBA8 target and composited over the picture with the same encode, so it is readable.

The SDR path is not touched when HDR is off: same targets, same shader, same present pass. The unit test `hdr_tonemap_patch` and the screenshots below check the rest.

Checked:

* `hdr_math` (10 cases), `hdr_capture` (9), `hdr_tonemap_patch` (7, including spirv-val of the patched shader of the real game).
* HDR screenshots of the opening cutscene and the Frigate intro with a false-colour map of brightness above paper white (`work/shots_s14/hdr_on_static.png`, `.hdrmap.png`, and a `.pfm` of the scene-linear values beside every HDR screenshot). In a lit-planet frame the brightest pixel was 475 nits against 203 paper white and 2.4 percent of the pixels were above paper white; in the text screens of the intro every pixel stays at or below 203 nits (maximum 199 to 202), which is the HUD and text sitting at paper white. The SDR-clipped preview looks like the SDR picture. An exact SDR-against-HDR pixel diff was not possible: the game's clock, not the frame count, decides what is on screen, so two runs never show the same frame.
* Validation layer: zero messages in the HDR-on run, the window run with Reflex on and off (after the threading fix below), and the FSR 1 runs. `extras_output` GPU test: 5 of 6 cases pass (HDR10 and SDR encode, exact copy, FSR 1 gradient and HDR highlights); the scRGB case failed because the shader had no peak cap and the CPU reference does; the shader now caps like HDR10 and the generated file is updated (the case was not rerun after that last change).

Not checked: an HDR display. This machine's monitor was in SDR mode and the test session is disconnected from the console, so Windows did not report HDR and the surface path (HDR10 swapchain on the real compositor) never ran. Everything up to the swapchain image ran, in an offscreen A2B10G10R10 image with the same encode. `[hdr] mode = on` forces the HDR scene pipeline; with a real HDR monitor, turn Windows HDR on (Win + Alt + B) and leave `mode = auto`.

## Low latency

One frame crosses the guest main thread (pacing, input sampling, simulation), the host render thread (replay and present) and the driver. The markers follow that: the main thread sleeps (Reflex `vkLatencySleepNV`, or Anti-Lag's input stage), then sets SIMULATION_START and INPUT_SAMPLE just before the mouse and pad are read (and again at the late sample in `ProcessInput`); the render thread sets SIMULATION_END and RENDERSUBMIT_START when it starts replaying the frame's commands, RENDERSUBMIT_END and PRESENT_START before `vkQueuePresentKHR` (with `VkPresentIdKHR`), PRESENT_END after. A frame keeps its id from simulation to present through a small queue. The validation layer wants calls on one swapchain from different threads kept apart (it flagged `vkLatencySleepNV`, `vkSetLatencyMarkerNV` and `vkGetLatencyTimingsNV` against `vkQueuePresentKHR`), so all of them take the queue lock. The swapchain is created with `VkSwapchainLatencyCreateInfoNV`, the cap of the frame limiter becomes Reflex's minimum interval.

The game queues several frames between its main thread and the GPU. Reflex's own sleep is small there (the game blocks the main thread already), so the mode also holds the simulation of a frame back until at most `frames_ahead` earlier frames are unpresented. That part needs no vendor extension.

Measured with `lat_ab.py` (local test script): one run, window mode, the mode flipped on and off every 8 seconds so both states see the same load. The proxy is "input sample to the end of `vkQueuePresentKHR`" and, with Reflex on, the driver's own "input sample to GPU render end".

| Run (window 1920x1080, mode flipped every 8 s) | State | Input to present, median / mean (ms) | Reflex: input to GPU render end (ms) |
|---|---|---|---|
| 3840x2160 internal, `frames_ahead` 1 | off | 361 / 386 | n/a |
| | on | 252 / 262 | 404 (off: 548) |
| 1920x1080 internal, `frames_ahead` 1 | off | 317 / 337 | n/a |
| | on | 291 / 325 | 395 (off: 471) |
| 1920x1080 internal, `frames_ahead` 0 | off | 284 / 466 | n/a |
| | on | 371 / 439 | 667 (off: 682) |

With the wait at 1 the input-to-present proxy fell by 30 percent at 4K and 8 percent at 1080p (medians), and Reflex's own input-to-GPU-end figure by 26 and 16 percent. With `frames_ahead` 0 the frame rate drops (the CPU and GPU no longer overlap) and the result was not better; 1 is the default. Reflex alone (the sleep) averaged 11 to 35 ms of waiting per frame in these GPU-bound runs.

The machine was shared with other test runs for the whole session (the GPU sat at 98 percent), so these are indications, not benchmarks. The direction held in every pair; the size varied.

## Upscaling

What the renderer offers: no velocity buffer, no jitter and no temporal anti-aliasing; the only anti-aliasing is FXAA (`CRenderPass_FXAA`), the post chain is volumetric fog, bloom, tone-map, FXAA, then the HUD. The temporal upscalers (FSR 3.1, DLSS, XeSS) need motion vectors, depth and a sub-pixel jitter in the projection. What it would take, and why it was not done:

* Motion vectors would have to be synthesised from the depth buffer and the camera of the previous and current frame: camera motion only, so moving enemies, particles and animated parts would ghost. The camera matrices are in the scene uniform block and in the camera objects; neither is hooked.
* The jitter has to go into the world projection (`CDisplayManager::UpdateCameraNodes` builds it; a frustum projection with shifted extents would do).
* The upscaled colour has to replace the tone-map input, which is what the scene upscaler already does for FSR 1, so that part exists.
* FSR 3.1 is MIT licensed and has a Vulkan backend only up to FidelityFX SDK v1.1.4 (May 2025); the v2.x line (v2.3.0, June 2026) lists "Vulkan is currently not supported in SDK" in its README, and FSR 4 is not offered through Vulkan there. `work/ffx114/build.cmd` builds `amd_fidelityfx_vk.dll` from that tag's source in about a minute (exports `ffxCreateContext`, `ffxConfigure`, `ffxQuery`, `ffxDispatch`, `ffxDestroyContext`). Nothing loads it yet.
* Frame generation (FSR 3.1 frame interpolation) also needs a HUD-free colour image, motion vectors and ownership of the swapchain; the HUD is drawn into the same target as the scene. Not attempted.
* DLSS and XeSS would be loaded from DLLs the player supplies (`dlss_dll`, `xess_dll`); they are not shipped. Both need the same inputs.

What is there: FSR 1 (EASU, then RCAS), in two places.

* Present stage: when the window is larger than the picture the game rendered (`[display] render_scale` below 100, which shrinks everything, HUD included), the output pass runs EASU and RCAS on the finished picture instead of the bilinear filter. On the SDR path it works on the sRGB-encoded bytes; on the HDR path on `c = x / (1 + x)` so highlights survive.
* Scene stage: with `[upscale] scene_scale` below 100 the game's own dynamic-resolution path renders the 3D scene smaller (the hook on `CDynamicResolutionControl::GetResolutionScale` returns the area factor, which the game turns into `sqrt(factor)` per side), while the post chain and the HUD stay at full size. The tone-map pass reads the small HDR target and writes the full-size window texture. With FSR 1 on, the replay runs EASU and RCAS on that target (on `c = 0.1 x / (1 + 0.1 x)`, since the scene colour is before exposure) and the tone-map draw samples the result. This gives a sharp HUD at any scale.

Frame cost and quality, 3840x2160 output, opening logo scene (`fsr_matrix.py`, screenshots in `work/shots_s14/`):

| Variant | Present-pass GPU time | PSNR of the 4K text region against native 4K |
|---|---|---|
| bilinear from 50 percent (1920x1080 internal) | 0.06 ms | 30.1 dB |
| FSR 1 from 50 percent | 0.46 ms (EASU + RCAS + encode) | 34.1 dB |
| bilinear from 67 percent | 0.06 ms | not comparable (the scene fades between runs) |
| FSR 1 from 67 percent | 0.47 ms | not comparable |
| scene scale 50, FSR 1 on the scene | 0.37 ms | not comparable (see below) |

FSR 1 costs about 0.4 ms more than the bilinear filter at 4K and gains about 4 dB on text. The frame rates of these runs (46 fps native, 14 to 39 fps for the others) mean nothing: the GPU was shared with other test runs at 98 percent. The scene-scale screenshots (`scene50.png`, `scene67.png`) came out darker than the others at the same second because the logo fades in and out on the game's clock, so no PSNR is quoted for them; their text is sharp in the HUD-native way described above. The picture of the lit planet in the HDR run (`hdr_on_static.png`) was taken with scene scale off.

## Decisions

* HDR scene targets are float16 (not R11G11B10F or 10-bit): the post chain blends into them and needs signed headroom. Cost: twice the bytes on those targets.
* The curve extension is done in the parameter block and the shader, not by replacing the shader or the grade: the per-room exposure, toe, shoulder start and colour grading stay the game's.
* Paper white follows Windows' SDR content brightness when Windows HDR is on, else 203 nits (ITU-R BT.2408).
* `auto` never chooses HDR without Windows saying so (see HDR, step 1).
* Reflex's frame cap is the limiter's cap; the limiter keeps running, so the cadence has two sources and the later one wins.

## Gaps and stubs

* Stub: FSR 3.1 temporal upscaling, DLSS, XeSS and frame generation (settings are read and kept, nothing runs). Where they plug in: the scene upscaler in `nvn_replay.cpp` (`scene_upscale_for_draw`) takes colour and returns a full-size image; a temporal upscaler would add depth, motion vectors and jitter there.
* HDR on a real display, and AMD Anti-Lag 2, were not run.
* The overlay composite and the HDR swapchain path were compiled and the encode shaders validated, but never presented to an HDR compositor.
* Reflex numbers come from a heavily shared GPU.
* The scene upscaler assumes the tone-map input is the first 2D sampler of the tone-map shader (true for the one variant of the game seen); other variants would pass through unchanged.
* Pause, map and morph-ball transitions were not looked at in HDR; they use the same window texture and post chain.
