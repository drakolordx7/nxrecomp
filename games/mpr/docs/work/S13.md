# S13: verifying the PC features in real gameplay

Branch `verify`. Gameplay became reachable, so the probes, the mouse aim, the controls and the high refresh step were run against the real game for the first time. Debug notes 320 to 322. Source: `src/testtools/` (probes, script steps), `src/gfx/play/` (aim, camera look, bindings), `src/kernel/sched.cpp` (core pick). Host tools: `tools/test/gameplay.py`, `hifps_probe.py`, `mouse_linearity.py`, `bindings_run.py`, `stutter_probe.py`.

## Game facts read off the running game

* The world is Y up. Forward is +Z at yaw 0 and left is +X: forward is (sin yaw, 0, cos yaw), so a positive yaw is a turn to the left. The walking speed is 12.8 units per second.
* The player's yaw lives in its transform and in the physics object; the first-person camera is a separate object. Pitch is a float at `CPlayerMP1+0x5cc`; the game eases it toward a target at `+0x5d0` on every Think.
* Movement states in the trace: 0 on ground, 1 jump, 2 apply jump, 3 falling. Camera state 0 is first person, 4 a cinematic, 1 the ball camera; the morph word is 0 unmorphed, 2 and 3 in transition, 1 in the ball.
* The game clock stands still while an area loads. The warp (`@warp`) puts the player in control about 4 game seconds after the area is current.

## What was wrong and is fixed

* The aim turned the player about Z and so rolled it; the game flattens the roll every Think. Everything about yaw is about Y now (debug note 320).
* Pitch was written to the field the camera reads but the game eased it back to a target; the target is written too.
* "In game" was decided by 300 ms of host time, so slow frames read as a menu and every menu-only binding was dead. It is counted in frames now.
* Select pulses (beams, visors) lasted 80 ms of host time and were lost when a frame took longer. A pulse now lasts until a poll has seen it and two frame boundaries have passed (debug note 321). Unit tests cover both.
* The scripted front-end press (`@mash`) lasted 40 frames, too short in deterministic mode; it is 250 ms of host time.
* The console core model picked every second processor from the top of the mask, which on this CPU is E-cores and second hardware threads. It now picks the three fastest free physical cores and one hardware thread of each (`[sched] pick = auto`, `top` is the old rule). The frame-time effect was not measured (see open items).

## Script steps and tools added

`@sleep ms`, `@run seconds` (game time), `@mash keys period area|world id`, `@give item n`, `@rate hz` (docs in `include/nxrt/tt_script.h`); trace fields in `tt.h`; `tools/test/gameplay.py` is the shared helper (prologue, warp, run, rows); `vscript.py` (local test script) runs one script, `vtrace.py` summarises a trace. Hook sites added to `recomp/games/mpr/main.sites`: `CFirstPersonCameraMP1::Think` 0x7100d72314 and `CBallCameraMP1::Think` 0x7100cff7ec (entry hooks; the main module needs a new lift). Without them free look and the ball camera do nothing and everything else works.

## Open items

* Physics deviation table at 60, 120, 144, 240: not produced. `hifps_probe.py` is rewritten for the Y-up world and one-process runs with `@rate`, but the full run did not finish: the machine had five to seven game processes on it and front-end loads took 5 to 15 minutes. What exists: a hand-scripted 4 s walk at 60 and 144 steps per second agrees within 0.2 % (32.58 and 32.53 units). The one probe run that got partial samples (`work/hifps_probe/run_all_snap4.txt`) is less comfortable: walk at 120 against 60 gives steady speed 11.34 against 11.84, distance 32.95 against 34.39 and slide after release 1.17 against 1.37, all outside the 1 %, 2 % and 6 % tolerances. The two runs differ in how they start, so treat it as a signal to rerun, not a result; 144 and 240 have no samples. The jump, turn and morph-ball scenarios, projectile range and the HUD timer are not measured. At 30 steps per second (the clamp) the position advances only 0.844 of velocity times game time; the cause is not found (suspect: the physics world's own step limit).
* Keyboard beam and visor keys (1 to 8, wheel) and the missile key: the pad sequences work, the keyboard pulses did not change anything in the last real run, before the frame-counted pulse fix. The fix is unit-tested but not run in the game. The missile did not fire from F or the middle button either; the pad R button alone was not tried. Free look, lock-on re-sync (needs a lockable target) and the Switch layout for charge, lock-on, morph and missile are unverified in the game.
* Core-model stutter: no frame-time numbers. Every run of the matrix (`stutter_probe.py`) failed at the front end or timed out on the loaded machine. Rerun `tools\.venv\Scripts\python tools\test\stutter_probe.py --variants "old:NXRT_SCHED_PICK=top,NXRT_SCHED_PRIORITY_CLASS=normal;new_high:NXRT_SCHED_PRIORITY_CLASS=high;free_high:NXRT_SCHED_CONSOLE_CORES=0,NXRT_SCHED_PRIORITY_CLASS=high" --load 24 --repeat 3 --out work\verify\stutter_matrix` on a quiet machine. The priority class (`auto`: high in a window) comes from the display merge and is kept.
* Freezes: three scripted runs out of about fifteen stalled while the main thread waited inside a guest wait during a warp load (10 s at start up, 10 s and 60 s at a warp); the watchdog fired. Cause not found; the machine was heavily loaded. The runner raises the watchdog to 60 s.
* Eden comparison: Eden read world, area, health and play time identical to ours, but the player transform pointer is not readable over its GDB stub (the same failure as in S5), so the position was not compared there.
* The ball camera offset persists until the ball is left; there is no recentre.
