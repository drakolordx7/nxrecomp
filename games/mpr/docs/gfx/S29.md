# S29: what the pipeline libraries cost, and what replaced it

Branch `gplopt`, cut from main at 6eb2888 (after S24 and the mouse merge). It follows the method of S18, S21 and S24: one `mpr.exe` per condition, the Frigate route from the first screen to the hangar, window 1920x1080 (1280x720 at a cap of 60), shader cache on, frame trace on, one run at a time, a new SPIR-V salt for every run so the driver compiles everything from scratch ("cold", see S24).

## Result

The frame rate gap that showed up after S24 (20 to 25 % fewer frames with libraries on in a 120 s headless boot) does not come from the libraries themselves. Measured in several ways, the pipelines linked from parts run within 1 to 2 % of whole pipelines, and on a machine that is busy with other work the libraries are much better than whole pipelines. The headless boot numbers moved by more than that between runs of the same setting (8,986 against 5,284 frames in two boots with the same defaults), so single runs are not conclusive.

What this branch adds:

* Linked pipelines are replaced by an optimised version in the background (`gpl_upgrade`). It costs 2 to 4 s of one background thread per session.
* A draw that has to wait for a part another thread is still building now lends that thread normal priority and full speed until it is done.
* The settings and a measurement mode that compares the two kinds of pipeline inside one run (`gpl_ab`).

## Where the gap was looked for

1. Are the linked pipelines slower on the GPU? Measured inside one run, so the scene and the load cancel out: `gpl_ab = N` keeps both pipelines of every draw and runs the linked ones in even windows of N presents and the replacements in odd windows. Each window is compared with the average of its two neighbours (`gplopt_ab_report.py` (local test script)). Linked pipelines were slower by 1.2 % over 195 windows of 150 frames (1.4 % where frames take under 5 ms, 3.6 % at 5 to 8 ms, -0.5 % where the GPU is the limit), 2.3 % over 22 windows of 800 frames, and 0.5 % and -0.1 % against the link-time optimised replacements (126 and 128 windows). On this GPU (RTX 3080) the fast link is nearly as good as a whole compile. This is what the replacement recovers.
2. Duplicate pipelines? No. The 292 against 50 in the boot comparison is a counter: `pipelines` in the end-of-run line counts every part, link and replacement built, not distinct pipelines. In the route runs the libraries link 109 pipelines (96 to 163 depending on the run length) where whole pipelines creates about 102. Both modes ask for the same keys. The 109 links need about 2,830 parts built ahead (that is the 55 to 60 s of background compile in S24); only about 540 are ever found again by a draw.
3. CPU work only the libraries do on the render thread? The extra work per draw is zero (the pipeline lookup is the same); a link costs 0.3 ms and happens once per pipeline. The render thread's replay zone per frame was 1.26 ms (whole) and 1.09 ms (libraries) in a pair of runs. Not found.
4. What the libraries do cost is the speculative compile: about 2,830 parts for 109 pipelines, each part about as expensive as a whole pipeline on this driver (20 to 25 ms on an efficiency core). That competes with the game only while it runs (the first minute of a cold run) and shows as a loss only when the game is limited by one CPU thread. `gpl_cold = false` skips the speculative part and compiles only what a command buffer was recorded with. That cut the background work to 3.6 s (245 parts), the frame rate stayed the same, and the render thread then made about 1 s of pipelines (worst 40 ms) at the draw. The default stays on speculation, because S24's result needs it.

## What was built

* `gpl_upgrade` (default `whole`). When a pipeline is linked, the key goes to a background thread (`gpl_upgrade_threads`, default 1). With `whole` it builds the whole pipeline as the key file prewarm does; with `lto` it links the same four parts again with `VK_PIPELINE_CREATE_LINK_TIME_OPTIMIZATION_BIT_EXT` (the parts are then made with the retain flag). The pipeline lookup swaps the finished one in at the next draw that asks for the key; the linked one is destroyed after the GPU is done with the frame being recorded (`defer_destroy`). Per session on the route: 109 to 163 replacements, 2.9 to 4.2 s of thread time for `whole` (26 ms each), 2.1 s for `lto` (13 ms each), one not used again, none failed.
* Why `whole` is the default: it is the path the key file prewarm already uses on every driver, it keeps nothing extra in memory, and it was no slower than `lto` on the frame rate. `lto` costs half the work and is there for GPUs where it matters; both gave the same frame time as linked pipelines within 1 %.
* The Vulkan spec describes the same approach: linking without the LTO flag is as fast as possible, and the result may run slower on the device; with it, the link takes longer and should match a monolithic pipeline; an application can link fast first and replace the pipeline in the background ([VkPipelineCreateFlagBits2](https://docs.vulkan.org/spec/latest/chapters/pipelines.html)).
* Priority lending: a part has an owner thread while it is being built. A draw that has to wait for it raises that thread to above normal and takes it out of efficiency mode; the thread puts its settings back when the part is done. Not shown to matter with the spinners (the scheduler is fair to them); it is there for starvation under other loads.
* `gpl_cold`, `gpl_ab`, `gpl_ab_pause` (see `CONFIG.md`). `gpl_ab_pause` rests the compile threads in alternating windows; draws then wait for parts and loading slows, so it only served to look at this and is not for play.
* The end-of-run line of `nvn.gpl` now also reports replacements queued, built, taken and failed, the programs the game set and the raster variants learned.

## What is left

* The fast link costing 1 to 2 % is for this GPU and driver. Not tried on AMD, Intel or an older NVIDIA driver; there the replacement may matter more, or `lto` may be the better choice.
* The route does not run the same way every time at a high frame rate. The button presses are by frame count, so about one uncapped run in five lands in the intro movies and never gets going (2 of the first 10; both are left out of every table here, and all 12 runs of `u1` and 8 of `u2` got through). A closed-loop route would fix it.
* The key file still records linked keys (as in S24), so a second run builds those pipelines whole through the prewarm and never links them. The replacement matters in the first run and for new content later.
* The priority lending is not applied to the prewarm threads (`nvn_prewarm.cpp`): a draw waiting for a pipeline a prewarm thread is building has the same exposure.
* The replacements are in the pipeline cache file as well (more entries than before, 109 to 163 per route).
