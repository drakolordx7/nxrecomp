# S40: shader programs with no translated stage

KNOWN_ISSUES said that a few hundred of the game's shader programs, some gun shaders among them, have no translated stage
and are skipped. This work found which ones, why, and translated them. CPU work only: no game run and no GPU test.

## Counts

| | before | after |
|---|---|---|
| Programs in the player's program list (`programs.bin`, written by setup) | 28,805 | 28,805 |
| Programs with a stage the cache has no SPIR-V for | 328 | 0 |
| Distinct code blocks the game's files hold | 13,104 | 13,104 |
| Blocks in the shader cache | 13,019 | 13,104 |
| Blocks missing from the cache | 85 (all fragment) | 0 |

The 328 matches the `missing: 328` that `mpr.exe --prepare-shaders` wrote to `work\shader_cache\prepare.state`; that is
where the "few hundred programs" came from. The "after" column is counted offline against `programs.bin` and against a
fresh scan of the game files. The game has not been run with the new cache yet.

## Cause

All 85 blocks come from four MTRL assets in `Preload/MPR1/SamusGunMP1.pak` (the arm cannon's materials). Each block is used
by 2 to 8 programs.

The shader cache was built from the S4c survey corpus. The survey read the `.MTRL` files that retrotool had extracted into
`work\survey\paks`. retrotool stopped part way through `SamusGunMP1.pak` at an asset named `gun_cskr_DGRP?` (a `?` is not
allowed in a Windows file name: "Failed to create file ... os error 123"). The assets after that one were never written,
and 11 of the pak's 12 MTRL assets were among them. No other pak failed. `extract_all.ps1` did not show the failure: it
printed an empty `FAIL  exit=` line for each of the 340 paks, so the one real failure was lost among them.

So no translator, harness or validation problem was involved. Once the 85 blocks were found, the harness translated all of them
with no change: 85 of 85 `ok-retry` (the same DebugMode retry that 8,722 of the cached blocks need), and 85 of 85 pass
`spirv-val --target-env vulkan1.3` on a separate run.

The setup tool reads the paks directly (`setup/src/programs.cpp`), not through retrotool, so `programs.bin` has always listed
these programs. That is why preparation counted them as missing.

## Fix

`shaders/scripts/gap_corpus.py` reads the game files the way the setup tool does: MaterialArchive.arc's SNVN records, and every MTRL
asset of every pak, read from the pak itself through the META record in its table of contents. It never goes through extracted
files. It writes the blocks a cache lacks (or every block, with `--all`) in the corpus layout `spirv_harness --batch` reads,
and writes `gap_report.json` (counts, and for each missing block its stage, size, source pak and asset, and the number of
programs that use it). With `--programs programs.bin` it also checks that its own program list equals the setup tool's.

```
tools\.venv\Scripts\python -I tools\shaders\scripts\gap_corpus.py game\romfs --cache work\shader_cache\spirv --out work\shadergap\gap_corpus --programs work\shader_cache\programs.bin
dotnet tools\shaders\build\bin\Release\net10.0\spirv_harness.dll --batch work\shadergap\gap_corpus --out work\shadergap\gap_out --jobs 8 --target-env vulkan1.3
```

The scan takes 37 s. Its program list equals `programs.bin` exactly (28,805 programs, none only on one side), and its block set
equals the new cache exactly (13,104). Use it as the completeness check before shipping a shader pack.

## Checks

- The harness build in `tools\shaders\build` reproduces the existing cache: 44 blocks sampled from `work\shader_cache\corpus_code`
  were translated again and all 44 are byte-identical to the cached `.spv`.
- 85 of 85 new `.spv` pass `spirv-val --target-env vulkan1.3`.
- Offline, `programs.bin` against the new cache: 0 of 28,805 programs have a missing stage.

## New cache

`work\shadergap\spirv` is a complete cache: the 13,019 old `.spv` (hard links to the files in `work\shader_cache\spirv`),
the 85 new ones, and `results.tsv` with the old rows followed by the 85 new ones. `work\shadergap\spirv_delta` holds only the 85
`.spv` and their `results.tsv` rows. Neither is committed: both are game-derived.

To merge into the main cache: copy `spirv_delta\*.spv` into `work\shader_cache\spirv` and append `spirv_delta\results.tsv`
without its header line to `work\shader_cache\spirv\results.tsv`. Or point `NXRT_NVN_SHADER_CACHE` at
`work\shadergap\spirv`. Then rebuild the release shader pack (`setup/scripts/make_shader_pack.py`), which held 13,020 entries.
Run preparation again too: `prepare.state` keys on the program count, which stays the same, so `--prepare-shaders` with
"only if needed" will skip the run until it is forced.

## What remains

- In-game check (needs the GPU): run with the new cache and confirm no `no translated shader` line on the gun, and look at the
  four beams. What these programs drew wrong before is still not known.
- Eight blocks were reported missing once each, in 8 of the 586 logged runs that had a cache open (`fc1d2ee19c936ed2`,
  `cf3d0abed89b0bf0`, `96645b697ed701e0`, `8abd2bfcfde9bfc2`, `7e2e6289b5f3bab9`, `6c759a5a8d0d0bb8`, `54574cfb0ee43f78`,
  `348542b5284b8da6`, code 0x400 to 0x1500 bytes). None of them is in the game's files, a different one turned up in each run,
  and none repeated. The runs did not have `dump_missing` set, so their bytes were not kept. One guess, not checked: the
  hash was taken while the game was still writing the code memory, or the game builds a block at run time. The next GPU
  window should run with `[nvn] dump_missing` set so the bytes are kept if it happens again.
- `tools/survey/extract_all.ps1` still prints its useless FAIL lines and retrotool still stops on `?` names. The shader corpus no
  longer depends on them. The other survey outputs (textures, inventory) of `SamusGunMP1.pak` may be incomplete too.
