# S27: launcher, frame rate counter, pad remapping, button prompts

Branch `launcher`. Four requests from play-testing: a launcher that opens before the game, a frame rate counter, button icons that follow the player's real keys, and icons that follow the device in use.

## The launcher

`mpr_launcher.exe` (`apps/launcher/`, CMake target `mpr_launcher`, `cmake/launcher.cmake`) is a plain Win32 program with Common Controls 6. That is the same toolkit and look as the setup tool: system message font, white window, grey hints, 16 px margins, per-monitor DPI. It links the static MSVC runtime, needs no installer and downloads nothing. It is 3.4 MB; SDL3 is linked only for its key name table.

What it does:

* Reads and writes `controls.ini` in the game folder with the game's own settings code (`play_types.cpp`, `play_config.cpp`, `play_defaults.cpp` are compiled into it), so the file it writes is exactly what the F1 page and the game read. The tabs are Display, Extras, Controls, Keyboard and Controller (see the release `README.txt`).
* Shows whether the game folder is complete (`exefs\main`, `romfs`, and `setup_state.tsv` saying the setup finished) and starts the setup tool for the first-time setup: it runs `mpr_setup.exe --out <game folder>` and waits. The setup logic is not copied; the launcher only starts the tool and checks the folder again when it closes.
* Starts `mpr.exe --game <game folder>`. The game folder is the folder of the launcher by default; "Change..." picks another one and the choice is kept in `mpr_launcher.ini` next to the launcher.
* A `controls.ini` that cannot be read shows the defaults, and saving keeps the old file as `controls.ini.bak`.

Options for scripted runs: `--game <folder>` (this run only), `--page <n>`, `--auto-play` (no window, start the game now), `--game-args "<text>"`, `--setup-args "<text>"`.

Not written by the launcher: `mpr.ini`. The setup tool owns it (paths and the texture quality), and it rewrites it on every setup run, so the launcher's settings all live in `controls.ini`.

## Frame rate counter

`[fps]` in `controls.ini`: `show` (off by default), `key` (F2), `corner`, `detail` (0 frame rate, 1 plus frame time, 2 plus the 1% low and the worst frame), `in_screenshots`. The key is consumed before the game sees it (press, repeat and release), flips `show` and saves the file. The F1 Display tab and the launcher's Extras tab set the same values.

The overlay hook (`Overlay::draw`) has two early exits. With the menu hidden and the counter off it does one relaxed atomic read and returns (the clock read was already there). With the counter on it measures the time between two presented frames, keeps five seconds of them (`fps_stats.cpp`, a pure class with unit tests) and draws four short lines through ImGui's foreground draw list, so it never takes mouse or keyboard input. The text refreshes four times a second.

A frame that is being captured is drawn without the counter (`Renderer::capture_pending()`), so the test tooling's screenshots, `[nvn] shot_frames` and the boot screenshots stay clean. `[fps] in_screenshots = 1` (or the F1 checkbox, or self-test `set:fps_in_shots=1`) puts it in the picture.

## Controller button remapping

`[padmap]`: one line per physical button (`south east west north left_shoulder right_shoulder left_trigger right_trigger start back left_stick right_stick dpad_up dpad_down dpad_left dpad_right`), value `default`, `none` or Switch buttons joined by `+`. A remapped button presses only what the line says. The launcher (Controller tab) and the F1 page (Controller tab) edit it. The Xbox and PlayStation prompt icons follow it: the icon of a Switch button shows the physical button that really presses it.

## Questions from the request

Do the keyboard icons show the bound keys? Yes, and they already did (S19). `input_for_button` looks up the action that presses each Switch button and takes the input bound to it in the current context. Checked in the game: with `G = confirm` in `[bindings.menu]` the log says `TXTR_ButtonA -> kbm/g` and the title screen shows "PRESS [G] TO START" (`work/run_launcher/crop_prompt_counter.png`). A unit test rebinds the jump key and expects the new icon. The limit is the icon set: the pack has an icon for every key name SDL has (540 icons); keys without a drawn icon get the plain key icon. A Switch button that nothing is bound to keeps the game's own icon.

Auto-switching between keyboard and pad icons also already existed (`auto`, S19): the last key, mouse button or wheel notch means keyboard icons, a pressed pad button or a stick moved well off centre means that pad's icons (Xbox, PlayStation, Switch), and before any input the first connected pad decides, else the keyboard. It uses the same live path as the F1 combo. This work made `auto` the default, which gives keyboard icons when no controller is connected, and put it first in the launcher and the F1 list. The decision logic is covered by unit tests; no controller was available here, so the switch caused by a real pad press has not been seen on screen.

## Tests

Runtime, one batch (`pwsh launcher_tests.ps1`, 159 CTest entries including the lift tests): 158 passed; `svc_info` failed once under the parallel run and passed when run alone (one of the known timing-sensitive tests). New groups: `launcher_keymap`, `launcher_game_info`, `launcher_bindings_edit`, `gfx_fps_stats`; extended: `play_config`, `play_pad`, `play_ui`, `prompt_icons`. Release builder: `python -I -m unittest discover -s release -p test_make_release.py` in the tools repository, 31 tests (5 new for the launcher). A packaging run against the real exe and launcher passes the launcher's checks (no dynamic CRT import, size, no local paths in the launcher); it stops on the setup tools in `tools/setup/build/release/bin`, which are older /MD builds.

End to end: `launcher_e2e.py settings` drives the real launcher window with window messages (it never uses global mouse or keyboard input), changes a setting on every tab, rebinds jump through the capture window, saves and checks every value in `controls.ini`; with `--play` it presses Play (25 checks pass). `launcher_e2e.py setup` opens the launcher on an empty folder, runs the real setup on the real dump through the setup button and waits for "Ready to play". On the first try the wait ran out at 25 minutes because the machine was busy; the setup itself finished in 1,544 s and produced a folder the launcher reports as ready and the game boots from (default settings: keyboard icons, counter off). The same path with `--again` (setup on a finished folder, which only checks sizes) passes in 8 s. `launcher_game.sh` starts the game through the launcher and `NXRT_PLAY_SELFTEST` scripts the F2 key, the F1 page and the screenshots.
