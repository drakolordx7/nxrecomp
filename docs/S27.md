# S27: launcher, frame rate counter, pad remapping, button prompts

Four requests came out of play-testing: a launcher that opens before the game, a frame rate counter, button icons that follow the player's real keys, and icons that follow the device in use.

## The launcher

`mpr_launcher.exe` (`apps/launcher/`, CMake target `mpr_launcher`, `cmake/launcher.cmake`) is a plain Win32 program that uses Common Controls 6. It shares its toolkit and look with the setup tool: system message font, white window, grey hints, 16 px margins and per-monitor DPI. It links the static MSVC runtime, needs no installer and downloads nothing. The exe is 3.4 MB. SDL3 is linked only for its key name table.

The launcher:

* Reads and writes `controls.ini` in the game folder using the game's own settings code (`play_types.cpp`, `play_config.cpp` and `play_defaults.cpp` are compiled in). The file it writes is exactly what the F1 page and the game read. Its tabs are Display, Extras, Controls, Keyboard and Controller (see the release `README.txt`).
* Checks whether the game folder is complete (`exefs\main`, `romfs`, and `setup_state.tsv` saying setup finished). For first-time setup, it runs `mpr_setup.exe --out <game folder>` and waits. The setup logic is not copied. The launcher only starts the tool, then checks the folder again when the tool closes.
* Starts `mpr.exe --game <game folder>`. The game folder defaults to the launcher's own folder. "Change..." picks another one, and the choice is saved in `mpr_launcher.ini` next to the launcher.
* If `controls.ini` cannot be read, the launcher shows the defaults. Saving keeps the old file as `controls.ini.bak`.

Options for scripted runs: `--game <folder>` (this run only), `--page <n>`, `--auto-play` (no window, start the game now), `--game-args "<text>"`, `--setup-args "<text>"`.

The launcher never writes `mpr.ini`. The setup tool owns that file (paths and texture quality) and rewrites it on every setup run, so all of the launcher's settings live in `controls.ini`.

## Frame rate counter

`[fps]` in `controls.ini` has five keys: `show` (off by default), `key` (F2), `corner`, `detail` (0 is frame rate only, 1 adds frame time, 2 adds the 1% low and the worst frame) and `in_screenshots`. The key is consumed before the game sees it, for press, repeat and release. It flips `show` and saves the file. The F1 Display tab and the launcher's Extras tab set the same values.

The overlay hook (`Overlay::draw`) has two early exits. With the menu hidden and the counter off, it does one relaxed atomic read and returns; the clock read was already there. With the counter on, it measures the time between two presented frames and keeps five seconds of them (`fps_stats.cpp`, a pure class with unit tests). It draws four short lines through ImGui's foreground draw list, so it never takes mouse or keyboard input. The text refreshes four times a second.

A frame being captured is drawn without the counter (`Renderer::capture_pending()`), so the test tooling's screenshots, `[nvn] shot_frames` and the boot screenshots stay clean. Set `[fps] in_screenshots = 1`, tick the F1 checkbox, or use self-test `set:fps_in_shots=1` to put the counter in the picture.

## Controller button remapping

`[padmap]` has one line for each physical button. The button names are `south east west north left_shoulder right_shoulder left_trigger right_trigger start back left_stick right_stick dpad_up dpad_down dpad_left dpad_right`. Each value is `default`, `none`, or Switch buttons joined by `+`. A remapped button presses only what its line says. The launcher (Controller tab) and the F1 page (Controller tab) both edit it. The Xbox and PlayStation prompt icons follow it: the icon for a Switch button shows the physical button that actually presses it.

## Keyboard icons and automatic switching

The keyboard icons show the bound keys, and they did before this change. `input_for_button` looks up the action that presses each Switch button and uses the input bound to it in the current context. Checked in the game: with `G = confirm` in `[bindings.menu]`, the log says `TXTR_ButtonA -> kbm/g`, and the title screen shows "PRESS [G] TO START" (`work/run_launcher/crop_prompt_counter.png`). A unit test rebinds the jump key and expects the new icon. The limit is the icon set. The pack has an icon for every key name SDL has (540 icons), so keys without a drawn icon get the plain key icon. A Switch button with no binding keeps the game's own icon.

Automatic switching between keyboard and pad icons already existed in `auto` mode. The last key, mouse button or wheel notch selects keyboard icons. A pressed pad button, or a stick moved well off centre, selects that pad's icons (Xbox, PlayStation or Switch). Before any input, the first connected pad decides; with no pad, the keyboard is used. It uses the same live path as the F1 combo. This change also made `auto` the default, so keyboard icons show when no controller is connected, and moved it to the top of the launcher and F1 lists. The decision logic is covered by unit tests. No controller was available for testing, so a real pad press causing the switch has not been seen on screen.

## Tests

The runtime test run (`pwsh launcher_tests.ps1` (local test script), 159 CTest entries including the lift tests) passed 158. `svc_info` failed once during the parallel run and passed when run alone; it is one of the known timing-sensitive tests. New groups: `launcher_keymap`, `launcher_game_info`, `launcher_bindings_edit`, `gfx_fps_stats`. Extended groups: `play_config`, `play_pad`, `play_ui`, `prompt_icons`. Release builder: `python -I -m unittest discover -s release -p test_make_release.py` in the tools repository, 31 tests (5 new for the launcher). A packaging run against the real exe and launcher passes the launcher's checks (no dynamic CRT import, size, no local paths in the launcher). It stops at the setup tools in `tools/setup/build/release/bin`, which are older /MD builds.

End-to-end checks: `launcher_e2e.py settings` drives the real launcher window with window messages. It never uses global mouse or keyboard input. It changes a setting on every tab, rebinds jump through the capture window, then saves and checks every value in `controls.ini`. With `--play`, it also presses Play (25 checks pass). `launcher_e2e.py setup` opens the launcher on an empty folder, runs the real setup on the real dump through the setup button, and waits for "Ready to play". The first try ran out the 25-minute wait because the machine was busy. The setup itself finished in 1,544 s and produced a folder that the launcher reports as ready and the game boots from (default settings: keyboard icons, counter off). The same path with `--again` (setup on a finished folder, which only checks sizes) passes in 8 s. `launcher_game.sh` starts the game through the launcher, and `NXRT_PLAY_SELFTEST` scripts the F2 key, the F1 page and the screenshots.
