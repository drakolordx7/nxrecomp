# S25: a real playthrough, a frame-rate bug, the 240 steps jump stall

Branch `play` in `runtime` and `recomp`. The test scripts (`live.py`, `route.py`, `lv.sh`) are local test scripts and not part of the repositories. Screenshots and the route log are in `work/run_play2/route/` (not committed, they come from the game).

## Short answer

The game is playable from New Game through the opening cutscene, the first two force fields of the Frigate, scanning, locking on, shooting and jumping, and, with warps, through the Tallon IV landing, saving and loading, the pause screens, the map, the morph ball, charge shots and missiles on keyboard and mouse, an elevator ride and the first two rooms of the Chozo Ruins up to the Main Plaza. Nothing crashed, nothing softlocked and nothing drew wrong in about five hours of play. The scripted route did not get past the first ledge of the Frigate: finding the next door by blind steering from screenshots did not work in the time spent, and the Parasite Queen, the escape and the Hive Totem were not reached. See "Where the route ended".

The main result is a fix for a bug that has been in every gameplay run so far: the mouse aim code called `WriteProcessMemory` once per player tick, and for an address in the guest heap that call took 56 ms. Gameplay ran at 8 to 20 frames per second whatever the GPU did. With the fix the same run does 100 to 200 frames per second, and a New Game to the first control takes 100 s instead of 4 to 10 minutes.

## How the route was driven

A new script mode keeps the game running while someone feeds it steps: `[test] live = FILE` (env `NXRT_TEST_LIVE`). When the script has no steps left, the runner waits for lines appended to FILE, runs them (same DSL as before) and writes `FILE.status` (one JSON line: frame, play time, area, position, yaw, pitch, health, move state, beam, visor, missiles) each time it goes idle. The game stands still while it waits, so nothing happens between two commands. Two side files act at once: `FILE.shot` (a name, takes a screenshot even while a long step runs) and `FILE.abort` (drops every pending step, for a wait that can never end). Unit tests: `tt_live` (2), `tt_script` (4 new for `@watch`), `timestep` (4 new).

`live.py` is the client: `start`, `newgame`, `send "line" ...`, `shot NAME` (also writes a 960 px preview), `look NAME [n]` (n views around you as one contact sheet), `goto X Z`, `go X Z` (goto that jumps and side-steps when blocked), `face`, `turn`, `aim X Y Z`, `shoot X Y Z` (aim, lock on, fire), `objs CLASS...`, `note TEXT SHOT`, `abort`. `lv.sh` and `lvb.sh` run it for the two run folders, `lvbg.sh` runs a command in the background and waits up to 95 s. `route.py` holds the scripted steps of the Frigate (`hangar_field1`, `hangar_scan_panel`, `hangar_field2`).

Two new script steps help finding things: `@objs door dock pickup special actor platform trigger relay player` (or any class name from the game's vtable list) scans memory for the vtable pointer and writes every live object's position to `out/objs.txt`; `@watch on|off` sets debug-register write watches on the player's vertical speed and height and logs the writing instruction and the guest call chain of every hit. `@objs` found the Frigate force field lights and the Tallon and Chozo doors; `@watch` found the jump stall.

## Where warps and item grants were used

The Frigate part is real play from New Game with pad input only. After that:

* `@warp tallon tallon_landing_site` skips the rest of the Frigate. It plays the landing cutscene and the end of the prologue ("New Extras unlocked", the save prompt), which is how the save test came about.
* `@warp tallon tallon_transport_to_chozo_ruins_west` put Samus in the elevator room. The elevator ride, the door and everything after it were played with inputs.
* `@give MorphBall 1`, `@give ChargeBeam 1` and, for the missile test, `@give Missiles 10` (a later fixed form, see below). The prologue takes all upgrades away, so the keyboard checks needed them.

## Where the route ended

On the upper walkway after the first ledge of the Frigate. The walkthrough says "go left along the path to a door"; two dead ends (a ship-facing platform to the south and a hull wall to the north) and a cargo container were found, the door was not. Without a map to read, steering from screenshots took about two hours for the two force fields and the scan, and a flood fill over the walkable floor (`explore.py`) was too slow to finish. An attempt to read door positions off the in-game map screen failed because the map view moves between openings. The Frigate's rooms use scripted force fields, not the door objects that Tallon and Chozo use, so `@objs door` shows nothing there. What would finish it: the room geometry and door positions read from the area files (a parser for the area script layers), then a path search; `@objs` and `go` already cover the rest.

In Tallon and Chozo the doors are real door objects and `@objs door` gives their positions, which is how the elevator room, the Ruins Entrance and the Main Plaza were reached. Two pickups in the Main Plaza (`61.1 8.9 294.7` and `107.0 20.9 272.1`) are on ledges that `go` did not climb; the first Missile pickup and the Hive Totem were not reached.

## Bugs found

| Problem | Cause | Fix |
|---|---|---|
| Gameplay at 8 to 20 frames per second, 100 to 200 ms frames (the S13 and S22 notes about "loaded machine" and "30 Hz clamp" were this) | `guest_write` in `src/gfx/play/play_aim.cpp` used `WriteProcessMemory`. It looks up the region first (`NtQueryVirtualMemory`) and for an address in the guest heap that takes about 56 ms (3 to 10 us for other addresses, measured from outside against the live process). The aim code writes the player's yaw and pitch every tick. Eight of eight stack samples of the main thread were inside that call | direct store: a read proves the page is mapped, then a store under `__try`. Same change for `write_mem` in the test probe. A read-only page would still fault (not the case for guest memory) |
| Jump at 230 to 288 steps per second is 2 to 4.7 % longer | see the next section | `fix_stuck_tracker` in `[time]` |
| `@give` and `@grant` wrote the wrong table, `msl` in the trace was the capacity | the item table is `{amount, capacity}` per item from `CPlayerStateMP1 + 0x2c` (`GetItemAmount`, `SetPowerUp`); the code used `+0x30` and `+0x44`. The beam and visor checks of S22 passed by luck | offsets fixed in `give_item`, `grant`, and the `msl` probe |
| Keyboard and mouse inputs did nothing in a script run | a script only merged the keyboard's pad into the scripted pad when it contained key steps at load time | live mode merges always. With that, the missile, morph and charge inputs all work; the "missile key not working" item of S13 was this |
| Suspect that the three-core pinning made the frames slow while another game held the cores | not the cause: runs with the pinning on and off were both slow in gameplay until the write fix; after it the unpinned runs take 10 ms per frame (the pinned case was not measured again). `live.py start` sets `NXRT_SCHED_CONSOLE_CORES=false` | none |
| One run (first session) never reached the first area after New Game: 17,000 frames with the world set and the area not | not found; five later New Games all worked, one of them while the machine was as loaded. The run was started before the status file race below was fixed, which cannot cause it. The pinned-core starvation above is the suspect | none |
| Live status file stayed stale and a client waited forever | the status file is replaced with `MoveFileEx`, which fails while a client has the old file open; the idle status was written once | retried until it works |

## The standing jump at 240 steps per second

S22 ruled out the move-state, impulse, momentum, collision, teleport and area-load functions. The zero is not written by the physics world either: `@watch` showed the frame's only velocity write from the normal path (`PostSimulation` then `SetVelocityWR`) replaced by a different one: `CPlayerMP1::ProcessInput` called `CPhysicsActorMP1::Stop` (which zeroes the velocity and the forces) and then built a collision box around the player and tested it against the world. The call is in the "player is stuck" branch: `CPlayerStuckTrackerMP1::IsPlayerStuck` returned true.

The tracker keeps the last 20 samples of position, velocity, state and input, one per player tick, and calls the player stuck when the path length of the 20 samples is under 1/30 unit (plus bounding box tests). That is 1/3 s at 60 ticks per second and 1/12 s at 240. Just after the top of a jump the speed is about 1.4 units per second, so the path is short enough and the tracker says "stuck". At 144 to 220 steps per second the window is long enough or the path just long enough; 230 and up trips it.

Fix: an entry hook on `CPlayerStuckTrackerMP1::AddState` (`recomp/games/mpr/main.sites`, main module relift needed) skips the sample until 1/60 s of game time has gone by. At 60 ticks per second or less every call samples, as before.

Rerun: `phys_table.py --exe <build> --rates 60,230,236,250,288 --scenarios jump --tag stall` and `--rates 60,120,144,240` for the full table. The watch run: `stall_run.py` (`--nowatch` for the plain jump); in the log the stall shows as `watch: frame N vel.y=0 rip=+0x32b7858`, the symbolized call chain is `SetVelocity <- Stop <- ProcessInput`.

Result with the fix (`phys_table.py`, one game process per rate, `@rate`; game build `game-build-play2`):

| Standing jump, 0.4 s button | 60 | 230 | 236 | 240 | 250 | 288 |
|---|---|---|---|---|---|---|
| Air time (s) | 0.9876 | 0.9864 | 0.9826 | 0.9827 | 0.9861 | 0.9826 |
| Against 60 | | -0.12 % | -0.51 % | -0.50 % | -0.15 % | -0.51 % |

Before the fix the 240 value was 1.0263 (+3.9 %), and +3.7 % to +4.7 % at 230 to 250, +2.3 % at 288. The other rates of the full table (60, 120, 144, 240) match the S22 table: walk speed within 0.01 %, jump air time -0.5 %, running jump distance -1.1 % to -1.4 %, walk start-up time +5 % to +8 %. Morph ball roll speed at 120, 144 and 240 steps per second is +1.0 % to +2.2 % against 60 in four runs (S22 had +0.4 % in one run); the 60 Hz reading moves between 16.22 and 16.32 from run to run, and the result is the same with `fix_stuck_tracker = false`, so the ball difference is not from this change.

## Decisions

* Normal difficulty after the first runs (Casual was picked in the first session).
* Pad input for the Frigate; the keyboard and mouse path was checked in Tallon where it is easier to see.
* Instead of an interactive debugger the game is driven by files, so the same commands can be replayed as a script (`route.py`).
* The `@objs` memory scan lists the vtable pointers of the classes it is given; class names come from `work/run_play2/vtables.json`, written from the IDA database (3,795 classes).

## Not done

* Frigate after the first ledge, the Parasite Queen, the escape, the Hive Totem, the first Missile pickup.
* Audio under the live runs (null sink).
* Free look and lock-on re-sync (S13 open items) were not touched.
* The first-session load hang is not explained.
