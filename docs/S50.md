# S50: the jump timer's last frame

Branch `jump` in `runtime` (the fix, its test, this document), in `recomp` (two hook sites) and in the root repository (test scripts).

## Short answer

S49 found that a jump could go up to 3 % higher when frames are uneven. This round fixes it. A standing jump now peaks at 3.499 to 3.501 at every frame cap and in every forced uneven pattern. Before the fix, the same patterns reached 3.532 to 3.613. With even 1/60 steps (the console) nothing changes.

## Cause

`CPlayerMP1::JumpInput` (main 0xcf0060) returns the vertical force for each frame. While Samus rises, that is the jump force. A jump timer of 0.25 s limits the rise. `CPlayerMP1::Think` counts the timer down by the step. In the step where the timer runs out partway, JumpInput blends the two forces: `f * jump + (1 - f) * gravity`, with `f = timer / dt`.

The rising speed is capped at 11.667 units/s, or 14.0 with the Space Jump boots (`GetMaximumPlayerPositiveVerticalVelocity`). The S49 traces fit one rule exactly, to 1e-4 in every run: each frame, the speed entering the step is capped, Samus moves at that speed, and then the step's force is added on top. A standing jump reaches the cap before the timer runs out. In the blend frame, the jump part is added on top of the capped speed. The next frame's cap removes that extra speed, and with it the gravity of the `(1 - f)` part of the step. So the jump goes too high, by an amount that depends on where the timer falls inside the step.

With 1/60 steps, the timer runs out on a step boundary. Counting down in floats leaves 1.1e-8 s, so `f` is 7e-7 and the blend frame is plain gravity. That is why the console, and every fixed-step test since S22, reads 3.500.

## Fix

In the blend frame only, the jump part may raise the speed up to the cap and no further, which is what a cap acting through the whole step would allow:

```
v_end = min(v + a_jump * f * dt, vmax) + a_gravity * (1 - f) * dt
```

* An entry hook on JumpInput records `dt`. A mid hook at 0xcf0750 runs only in the blend path. There `s8` holds `f * jump force`, `s9` holds `(1 - f) * gravity` and `s0` holds the mass. The hook lowers `s8` to `mass * (vmax - min(v, vmax)) / dt` when `s8` is larger. The game's own next two instructions then add the gravity part. The cap comes from the game's own function, so the 14.0 cap with the boots is included.
* The cap scales the whole velocity vector, not only the vertical part (`CPhysicsSteppedMoverCollider::MoveObject`: `v *= vmax / v.y`). At 1/60, a running jump's horizontal speed drops from 11.733 to 10.960, which is 11.667 / 12.5. The jump part that the fix removes would have caused that loss in the next frame. So the hook applies the same loss directly: it scales the horizontal velocity by `vmax / (min(v, vmax) + jump part / mass * dt)`.
* Every other frame is unchanged, and so is the blend frame of a jump that is still below the cap. No frame rate is treated as a special case.
* `[physics] jump_fix = 1` (default). Setting it to `0` (or `NXRT_PHYSICS_JUMP_FIX=0`) runs the game's code unchanged. Code: `games/mpr/play_jump.{h,cpp}`. Sites: `recomp/games/mpr/main.sites` (entryhook 0x7100cf0060, midhook 0x7100cf0750).

## Numbers

Window runs on the real clock, the S49 method (`jump_run.py`, same hangar spot, 720p, null audio). One game process per run. "Off" is the same exe with `NXRT_PHYSICS_JUMP_FIX=0`. The forced cases use `@rate` on every frame, so they are the same in every run. In `a0` the step alternates between 1/144 and 1/60, and the timer ends 0.42 of the way through a 16.7 ms step. `a1` is the other phase of the same alternation, with f = 0.83. In `s59` every step is 1/59 s, and the timer ends 3/4 of the way through a 16.9 ms step.

## Checks

* Lift: `work/lift_jump` against main's `work/lift`, compared function by function (`lift_fdiff.py`). sdk, subsdk0 and rtld are identical. In main, only `f_7100cf0060` (JumpInput) changes: it is now noinline, it calls the entry hook, and the mid hook call sits before 0xcf0750. Five functions are new because the mid hook splits JumpInput (0xcf0750 and its tails 0xcf0194, 0xcf02b0, 0xcf048c, 0xcf0598).
* Runtime tests: group `play_jump` (the force rule, the horizontal scale, unusable inputs, and a jump stepped through the game's integration rule at 10 step patterns: within 0.4 % of 1/60 after the fix, more than 2 % off before it; hook install and the config switch). All 155 runtime test groups pass (`jump_tests.ps1`, lift tests off).
* At even 1/60 steps, the fix on and off differ by at most 6e-7 units in height and 1e-6 units/s in speed, from the blend frame onward. That frame is the 1.1e-8 s leftover of the timer. The running jump's horizontal speed agrees within 3e-5 units/s (the two runs start at slightly different headings).

## Not done

* The cap 120 real-clock runs were not repeated. The forced cases cover the uneven steps.
* At even steps, the running jump's horizontal speed at the apex is 1.2 % lower with `@rate 144` than with `@rate 60` (11.29 against 11.43). The difference is the same with the fix off, and the speed at take-off already differs. That is outside this fix and was not looked into.
