# S5 notes: test tooling and reference captures

Part S5 of the Metroid Prime Remastered recompilation. To test without a player, this work gives automated runs a way to prove that gameplay works: scripted input, per-frame state traces, deterministic replays, and ground truth recorded from the real game in the Eden emulator. The runtime half lives here (`src/testtools/`, header `include/nxrt/tt.h`); the host-side half (Eden harness, comparators, suite runner) is in the tools repository, `tools/test/` (see its README). Numbered notes: `docs/debug/100.md` and up.

## What the runtime has now

Everything is off unless a `[test]` key (or its `NXRT_TEST_<KEY>` variable) asks for it; the full key list is the top comment of `include/nxrt/tt.h`.

| Piece | What it does |
|---|---|
| Frame boundary | One call, `tt::frame_boundary()`, per game frame. Sources: `hook` (entry hook on `CGameArchitectureSupport::Update`, needs the site list below), `tick` (the runtime's `diag_frame_tick`, so the present path), `svc:N` (a pseudo frame every N SVCs of the first guest thread, for bring-up), `manual` (unit tests). |
| Deterministic mode | `deterministic=1`: virtual clock (`kernel::system_tick` and `SleepThread` read it; one frame = 320000 ticks = 1/60 s, every read adds one tick, a sleep adds its length and only yields), a seeded RNG (`tt::rng_fill`), a fixed wall-clock epoch (`tt::wall_filetime`). |
| State hash and trace | At each boundary the probes read the game state, a 64-bit hash is built from it plus any memory regions named in `hash_regions`, and one JSON line goes to `<out>/trace.jsonl`. `final_hash` in `result.json` chains every frame hash: two runs that agree on it agree on every frame. |
| Probes | World id, area id, health from `gpGameState`; position, yaw, movement state and play time through the `CStateManager` the `ProcessInput` hook captured. Offsets and where each was read are in the header comment of `src/testtools/tt_probe.cpp`. Velocity in the trace is the position difference between two frames. |
| Input record and replay | `record=<file>` writes the pad of every frame (text, delta encoded, `include/nxrt/tt_inputfile.h`); `replay=<file>` feeds it back. Both go through S3c's `hid::InputSource` (`src/testtools/tt_hid.cpp`): the wrapper installs itself at the first frame boundary and re-wraps whenever another source is installed later. |
| Scripted runs | `script=<file.nxs>`: the DSL grammar is the top comment of `include/nxrt/tt_script.h` (waits, `press`/`hold`/`stick`/`mouse`, `@area`, `@pos`, `@warp`, `@shot`, `@hash`, `@assert`, timeouts). Result: `<out>/result.json`, exit code 0 pass, 1 script failure (assert, wait timeout, `@fail`), 2 usage or script parse error, 4 host crash, 5 watchdog freeze, 6 the process ended before the script did, 124 wall-clock timeout. |
| Crash, freeze, screenshots | A crash report turns into `result.json` (verdict `crash`, exit 4). A watchdog fire ends a scripted run with exit 5 (the thread dump goes to the usual freeze report). `@shot` calls the screenshot provider the graphics layer registers with `tt::set_screenshot_provider`; without one the shot is listed in `missing_shots` (a failure when `require_shots=1`). |

`tools/test/run_suite.py` runs a list of scripted runs and prints one PASS/FAIL table; `tools/test/regress.py`, `imgdiff.py` and `tracediff.py` compare runs, frames and traces.

## Hooks the lifted game needs

`tests/sites/mpr_testtools.sites` lists two entry hooks (`CGameArchitectureSupport::Update`, `CPlayerMP1::ProcessInput`). The lifter compiles a hook call only for the sites it is given, so `main` has to be lifted again with this list (`--sites`) before the `hook` frame source and the position/play-time probes work. Without it: `frame_source=tick` (or `svc:N` today) and only `gpGameState` fields (world, area, health).

## Decisions

* One frame boundary shared by every feature instead of one hook per feature, so a trace line, a hash, a script step and a recorded pad always mean the same frame. The state in trace line N is the state at the start of frame N; the pad of frame N acts on it.
* Text formats everywhere (input traces, scripts, traces as JSON lines, `result.json`): diffable by scripts and by `tracediff.py`.
* The mouse impulse of a replayed or scripted frame goes through a function pointer (`tt::set_mouse_sink`), not a direct call, because the SDL input queue is in the graphics library and the core library must not depend on it. The PC-input stream registers `input::mouse_delta_add` there.
* The GUID byte layout of area and world ids is a single assumption in `tt_guid_to_bytes` (the 16 bytes in text order). It is checked against Eden, see "Eden reference" below.
* Velocity is not read from the game's physics object (that needs a guest call); it is the frame-to-frame position difference on both sides of every comparison.

## Tests

CTest groups `tt_script` (40), `tt_inputfile` (14), `tt_core` (16: a fake game with the real memory shape, scripts, record/replay bit-identity, clock, RNG, hashing, warp sequence through host functions registered at the real function addresses, shots, freeze) and `tt_hid` (the adapter against S3c's `ManualInputSource`). The existing groups are unchanged. Rerun: `pwsh scripts\build.ps1 -Test -Filter "tt_"`; the pure units without a full build: `scripts\tt_unit.cmd <group> <sources...>`.

Oracle on what boots today (`mpr.exe`, bring-up probe, `frame_source=svc:4`, `hash_regions=module:main,module:sdk,module:rtld`, script `tools/test/scripts/bringup.nxs`): two runs give the same `final_hash` and the same hash on every frame. The boot is deterministic by itself at this point (a third run with `deterministic=0` gives the same hashes too: nothing time-dependent is stored in those regions yet), so this proves the plumbing, not the clock; the clock is proven in the unit tests. Rerun: `tools\.venv\Scripts\python tools\test\run_suite.py tools\test\suites\boot.toml`.

## Eden reference (what exists, what it showed)

Portable Eden v0.2.1 in `work/eden` (git-ignored; keys only in `work/eden/user/keys`), driven by `tools/test/eden_run.py` (see the tools README). Frames come from the Vulkan SDK's screenshot layer because the test session has no desktop (debug note 100); input is posted to the SDL window; game state is read through Eden's GDB stub (debug note 101). Captures are under `work/eden_ref/ref`: boot logo, title screen, main menu, file select, difficulty select, loading screen, three frames of the Frigate intro cinematic, an attract-mode gameplay frame.

Facts learned from the real game:

* The area and world ids are Windows-style GUID structs in memory (first three groups little-endian). `tt_guid_to_bytes` was changed to that after reading the Frigate world id over GDB; the area read at the same time, `f64f44a8...`, is `frigate_exterior_docking_hangar` in `tools/test/regions.tsv`, so the world-state layout (array at +0x18, area at +0x10) and the GUID mapping both check out end to end. Health (99.0) and the play time (83.4 s) read as expected too.
* Per-frame traces over GDB work (`edengdb.py trace`, a breakpoint on `CGameArchitectureSupport::Update`): during loading the function runs at several hundred calls per second, in gameplay once per frame.
* A new game needs 12 to 35 minutes of wall time to reach the Frigate in Eden on this machine; the main module base moves between runs.

## Gaps

| Gap | Why |
|---|---|
| No reference frame of first Frigate gameplay, and the player position probe is unverified | Six Eden sessions never got past the loading screen and the opening cinematic within their time limit. In the last two the state manager was captured but the transform read failed: the chain `CStateManager+0x4e0150 -> +0x18 -> +8 -> +0x20 -> +0x40` gives a pointer from which 48 bytes did not read. `edengdb.py raw_dump` and the `raw` timeline event exist to dump those objects in the next session; `tt_probe.cpp` has the one place to correct. World, area, health and play time are verified. |
| `@shot` has no graphics provider | The graphics layer (S4d) registers one with `tt::set_screenshot_provider`: a function that makes the renderer write the last presented frame as PNG (`Renderer::request_screenshot`). Until then shots are listed in `missing_shots`. |
| The `hook` frame source and the position/play-time probes need a relift | `tests/sites/mpr_testtools.sites` has to go to the lifter with `main`. |
| The deterministic oracle on `mpr.exe` only proves the plumbing | The boot stops after about 60 SVCs (debug note 103). |
| Deterministic mode does not cover guest threads racing each other | The virtual clock and the hash are deterministic for one thread; audio and loader threads will need hashing restricted to regions they do not touch. |
| `csrng` and `time:u` unix time are not deterministic until `docs/S5-services.patch` is applied | Services code. |
| Mouse impulses reach the game only through `tt::set_mouse_sink` and the hid mouse fields | The PC-input stream owns the mouse path. |
