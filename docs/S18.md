# S18: input latency and gameplay stutter

Branch `perf2` (worktree `runtime-wt/perf2`), cut from main at 8548d28. Debug notes 400 to 402. Everything here is measured with one `mpr.exe` and environment toggles, so before and after are the same binary.

## Result

Cap 60 and 120, player-controlled frames only (frames where the game ran `ProcessInput`), 140 s window of a Frigate run, window 1280x720, RTX 3080 shared with two or three other game instances that another stream was running. Medians and 95th percentiles in milliseconds.

| | cap 60 before | cap 60 after | cap 120 before | cap 120 after |
|---|---|---|---|---|
| input sample to present call returned, p50 / p95 | 49.1 / 49.5 | 9.1 / 13.9 | 24.3 / 43.5 | 7.2 / 28.1 |
| input sample to GPU finished, p50 / p95 | 50.3 / 56.5 | 13.6 / 22.9 | 26.1 / 58.6 | 12.7 / 42.7 |
| frames simulated and not yet presented at frame start | 2 | 0 | 2 | 0 |
| frame interval p50 / p99 | 16.67 / 25.6 | 16.66 / 21.1 | 8.35 / 25.3 | 8.67 / 23.3 |
| intervals over 2x the median (all frames of the window) | 44 | 31 | 500 | 408 |
| intervals over 50 ms (all frames of the window) | 12 | 21 | 29 | 10 |

Reading the table: the delay between the mouse and the frame that shows it fell from three frame times to about one render time. The 120 fps rows are GPU-bound in the heavy part of the run (the frame takes 9 to 12 ms on a GPU that other games share), which is why the cap-120 after numbers are not as low as at 60. The count of intervals over 50 ms rose at cap 60 because the old queue hid hitches of the main thread (movie decoder start and stop) behind two buffered frames; they are now visible, see "What is left".

Without a shader cache folder (`NXRT_NVN_SHADER_CACHE`), or with blocks missing from it, the old build also went from 60 fps to 2 to 5 fps over a run (debug note 400): 38.5 fps average and 448 frames over 50 ms at cap 60 before, 59.4 fps and 23 after, same exe. That run drew nothing (every program unlinked), so it says nothing about rendering cost; it is the retry loop only.

## What was measured, and how

`[prof] trace = file` now also writes latency marks (`src/gfx/extras/lowlat.cpp`, `src/gfx/vk_renderer.cpp`): per frame id the last input sample (the one `ProcessInput` takes), the present call, and the GPU finishing the frame's last command buffer (a watcher thread waits on a timeline semaphore that the present submission signals), plus the frames in flight and the unfinished GPU submissions at each frame start. `lat_report.py` reports median, p95 and the in-flight counts, for all frames and for player-controlled frames. `stall_attr.py` names the zone behind each frame interval longer than a multiple of the median. `perf2_run.sh`, `perf2_matrix.sh` and `perf2_matrix2.sh` run the gameplay matrix.

Nsight Systems: a WDDM capture of the gameplay window shows DXGI present starts 16.67 ms apart at p50 (the same cadence as the trace) and the present call returning in 0.27 ms at p50 (1 ms at the maximum), so nothing queues behind the present. The Vulkan layer trace of `nsys` needs registry write rights, which this shell lacks, so GPU completion comes from the timeline semaphore, not from `nsys`.

## Causes and fixes

1. **The limiter sleeps inside the present call** (debug note 402). The game's main thread runs two frames ahead of its render job; with the limiter in `nvnQueuePresentTexture` the render thread sleeps and that queue stays full, so a mouse sample is shown three frame times later (50 ms at 60 fps, 25 ms at 120). The GPU queue (`lat.gpuq` 0 to 2), the four submission slots and the swapchain (3 images, no blocking present) were not the cause. Fix: the limiter waits at the frame boundary, before input is sampled (`[latency] pace = main`, default). The present call still runs the pre-frame hook and waits itself only for a present no boundary paced (loading screens, movies). The wait for frames still in flight (`[latency] frames_ahead`, default 1) is now on by default and gives up when nothing was presented for 250 ms.
2. **Pool imports cost 30 to 100 ms each** (debug note 401). A level load creates about 150 tiny memory pools; each import went through the multi-gigabyte primary view of the heap section and the driver walks the whole mapping (stand-alone: 8.6 + 8.2 ms for 64 KB in the primary view, 0.00 + 0.05 ms in a small view of the same pages). Imports now go through a private small view (`[nvn] pool_view`). Pools under 1 MB: median 61 ms before, 0.20 ms after. Several importer threads were tried and made every import slower.
3. **A failed shader link is retried on every bind** (debug note 400). `nvnProgramSetShaders` returned 0 for a block missing from the shader cache; the game then rebuilds the shader (three programs and a pool-allocator buffer under the allocator lock) each time it is bound, and the allocator's first-fit scan grows with every attempt. Fix: success is reported for a program whose block is only missing from the cache (the program stays unlinked, its draws are skipped as before; `[nvn] accept_unlinked`). With a complete cache this does nothing; it protects partial caches and setups where the cache path is wrong.

Not causes (checked): the console core model (`NXRT_SCHED_CONSOLE_CORES=0` behaved the same), more import threads, the swapchain image count and present mode (present returns in 0.27 ms), the frame limiter's accuracy.

## What is left

* Texture first use on the render thread: `prepare_texture` hashes the ASTC source, reads the BC7 cache file and untiles inside `tex_ensure_current`, during replay. At area loads one frame can hold 70 textures (frames of 130 to 700 ms, two to six per 150 s run). In steady play it costs 0.4 ms per frame for the textures the game rewrites every frame. The fix would be preparing textures on a worker as soon as the game flushes their memory; not done.
* Movie decoder stalls on the main thread when a cutscene starts and ends (`Extractor::GetSampleTime` 60 ms, `Extractor` destructor 60 to 80 ms). S9 owns the movie code.
* The two large pools (360 MB and 580 MB) still import in 110 and 200 ms, once, at load.
* GPU time spikes of 100 to 240 ms (`gpu.exec`) at cap 120 coincide with other games using the GPU.
* One validation error is present before and after (`VUID-vkCmdDraw-imageLayout-00344`, an NVN texture drawn in the wrong layout, 10 times). No message mentions memory import, present, semaphores or the limiter.
* `[latency] mode = on` (Reflex) was not run against the new pacing.

## Settings added

`[latency] pace`, `[nvn] accept_unlinked`, `[nvn] pool_view` (see CONFIG.md). Every one defaults to the fixed behaviour and can be switched back with an environment variable for a before and after run.

## Notes

* The first batch of runs had no shader cache configured, so no draw was executed and the numbers from it (including the no-draw 6 ms input-to-GPU) are not used. Gameplay runs of this build need `NXRT_NVN_SHADER_CACHE=<work>\shader_cache\spirv`; `perf2_run.sh` sets it.
