## What the code does (read, not yet measured)

* The game's guest threads record NVN command lists. `nvnQueueSubmitCommands` and `nvnQueuePresentTexture` call `run_on_render_thread`, which queues the work to the one host render thread and blocks the calling guest thread until the replay (or present) finishes. So a guest render thread pays the full CPU cost of replay and present, in order.
* `present_on_render_thread` runs the frame limiter first (`begin_frame`, sleep to the cap), then acquires the swapchain image, records the present pass and presents. The cap therefore stalls the guest thread that presents, inside the present call. The main thread is held back only by whatever backpressure the game itself has (fences, its own queue depth).
* Up to 4 submission slots (`kSlots`) are in flight; `acquire_slot` waits on the slot used 4 submissions earlier. With a shared or slow GPU that backlog stays full, which adds up to 4 submissions of delay between replay and display.
* `lowlat.cpp` (S14) already timestamps the input sample (`update_hook` and `ProcessInput` call `input_sample`) and the end of present, matching frames by a queue of ids. The proxy ends when `vkQueuePresentKHR` returns, so it leaves out the GPU backlog. It runs only when the latency mode or `log_timings` is on.

## Why the earlier latency figures were so high (hypotheses to check)

1. The game queues several frames between its main thread and the presenting thread, and the limiter sleeps in the present call, so the queue fills to its limit whenever the render path is faster than the cap. Depth times frame time gives the delay.
2. The GPU backlog (up to 4 slots plus swapchain images) is not in the proxy but is in what the player sees.
3. With the GPU shared with other runs, every figure is inflated.

## Plan

1. Measurement
   * Add trace marks keyed by frame id: input sample (main thread), submit start and end, present start and end, and GPU completion of the frame's last serial (a watcher thread waiting on the timeline semaphore). Input to GPU done is the proxy for what the player sees. Report median and p95 at caps 60 and 120.
   * Count frames in flight at each input sample (main thread frame number minus presented frame number) to find where the queue sits.
   * Gameplay trace per cap (60, 120, 144, uncapped): p50, p99, stalls over 2 times the median, and zone totals per thread (replay, texture prepare, pipeline create, pool import, slot wait, sync wait, SVC).
2. Stutter causes to check in the gameplay trace: pipeline creation (prewarm misses on a first run), BC7 cache misses and texture prepare, pool import on the render thread, area-load streaming, guest thread scheduling under the 3-core model, replay cost per draw.
3. Fixes to try, in order of expected gain: a shorter in-flight limit (frames_ahead on by default when the cap is set, or a wait on the main thread tied to the presented frame), moving the limiter sleep so it does not hold the replay of the next frame, fewer slots in flight when the GPU is idle enough, and anything the gameplay trace shows on the render thread.
