# S36: stick and gyro look that do not depend on the step rate

Branch `padrate`. The right stick and the gyro now move the view at the same speed at 30, 60, 90, 120, 144 and 240 steps per second, and the morph ball camera orbits with the right stick. S35 used a fitted exponent for the stick (`(step x 60) ^ (1 / 2.2)`) and did nothing for the gyro. Both are gone. The stick's pitch code now runs 60 times a second whatever the step rate, and the gyro gets its rate times the step. The recompiler needed no change, so there was no relift: the one function that matters (`ComputeFreeLook`) already had a hook site from S32.

## What the game does

The pitch is worked out in `CPlayerMP1::ComputeFreeLook`, which `ProcessInput` calls once per step. The function has no time step. What it does with the right stick depends on the control scheme:

* Dual Stick: the stick adds a fixed amount to the pitch target on every call, then a smoothing filter (`CIIRFilter`, built in the player's constructor) runs over the target. The filter is `y = 0.1 x + 0.4 y[-2] + 0.5 y[-1]`, per call. Fed the accumulating target, it moves the view at a steady `inc / 14` per call after a short ripple (one pole at -0.4 decays in about three calls).
* The other schemes: the stick sets the target outright and the same filter follows it. If the free look button is held, the filter is skipped.
* Gyro (Hybrid, R held, `GetGyroFreelookControl`): the gyro's pitch rate is added to the target on every call, scaled by the maximum pitch. There is no filter.

The console calls the function 60 times a second, so all of this is per 1/60 s. At 144 steps per second the same code pitched 2.3 times as fast with the stick (S35 measured 2.7 rad/s against 1.18), the filter settled in 0.4 times the time, and the gyro moved 2.7 times as far. Below 60 it was the other way round.

S35 scaled the stick's vertical axis before the game read it. That kept the speed roughly right and the filter wrong. Its exponent was a fit to a response that the aim code had already distorted by overwriting the target every frame (see below).

## What it does now

### The stick: the game's own code at its own rate

The hook on `ComputeFreeLook` (`play_lockcam.cpp`) keeps a clock in game time. Every step adds the step's length. The game's call runs once per 1/60 s on that clock, and for that call the step length it reads is set to 1/60 (the timers inside it use it). At 60 steps per second that is every step, so nothing changes. At 120 it is every second step, at 240 every fourth, and at 30 twice per step. The accumulation, the filter and the timers run as on the console.

The clock and its rounding are in `play_lookrate.cpp`. A call is due when the clock holds a step within 10 percent (the time taken early is taken off the clock again). So a step of 1/60 s that float arithmetic makes slightly short, or frame times that jitter around 60 Hz, still give exactly one call per frame.

This is only done in plain first-person play. Cutscenes, the morph ball and the normal lock-on take other paths in the game's function that set or reset the pitch outright, and they run every step as before. So does the gyro camera. `NXRT_LOOKRATE=0` in the environment turns the clock off (the game's call once per step as it comes), for comparisons.

### Smoothness above 60

The pitch target only changes on the calls, so at 120 or 240 steps per second the view would move in 60 Hz steps. Measured: the speed from one frame to the next had a standard deviation of 70 to 170 percent of its mean at 90 to 240 steps per second.

Between two calls the hook carries the target on at the speed of the last call, so it holds what the target will be at the next call if the stick stays where it is. The game's own value is put back before each call, so the filter never sees the carried number. At exactly 60 steps per second the carry is zero. Anything else that moved the target in between (the mouse, a reset) is kept as a difference to what the hook wrote. After this the speed from frame to frame is constant (standard deviation 0.000 of the mean at every rate).

### The gyro: the rate times the step

The gyro value is an angular rate that the game adds per call with no filter, so the exact fix is to give it `rate x step x 60`. `PlaySource` multiplies the pitch axis of the six-axis sample by that factor (`look_rate_scale`, 0.05 to 4). Yaw from the gyro goes through the game's turn physics, which has a time step, so it is untouched. In the Pointer scheme the game reads the pad's orientation, which is integrated separately and not scaled.

### The aim no longer overwrites the target

While a pad was looking up or down, S35's aim code wrote the pitch and the target to the same value before every call. That cut the stick's lead over the camera every frame, which is where S35's odd power law came from (20, 50 and 90 percent of the stick gave 0.5, 20 and 80 percent of the speed). Now the aim leaves both alone.

When the mouse moves at the same time, the pitch and the target both move by the mouse's amount, and the memory of the smoothing filter moves with them (`shift_look_filter`). Without that, the filter would pull a target moved from outside back, and most of the mouse's move would be lost. Checked with stick and mouse together: the mouse adds its full amount (0.0691 rad at 60 steps per second, 0.1659 at 144, as for the mouse alone).

## Measured

Dual Stick scheme, fresh New Game, Frigate hangar, full stick or the stated gyro turn, with the step rate fixed by the test script (`@rate`). Speeds are slopes over a steady stretch of the trace. The lag is where the steady line crosses the starting value.

| Stick pitch speed, S35 (rad/s) | 0.622 | 1.244 | 1.208 | 1.137 | 1.211 | 1.405 |

| Gyro yaw per rad turned | 1.974 | 1.887 | 1.864 | 1.856 | 1.853 | 1.917 |

The stick's pitch speed and the gyro's pitch speed are the same to the fourth digit at every rate. S35's old gyro numbers were 2.7 times as far at 144 and 4.5 times at 240.

The pitch delay is the game's 60 Hz sampling. On the console the view holds each value for a whole step, which is half a step of delay on average. The carried target is continuous, so it comes out 10 to 20 ms earlier at the high rates, and one step later at 30 (both calls of a step run at its end). The pitch stops at once when the stick is let go (no coast), because the aim adopts the view's pitch on the first frame without the pad.

The yaw does not have this fault. The steady turn speed is the same at every rate. The delay and the coast come from the game's turn physics, which pushes the angular velocity toward the stick with a torque integrated over the step. The response is about 40 ms in continuous time and each step adds a fraction of a step of delay (the coast is 1.1 steps of turning at 240 and 1.6 at 60). Nothing in it counts calls, so it is left as it is.

The gyro's yaw per rad turned is within 2 percent of the 60 Hz value from 90 steps per second up. The 30 Hz and 240 Hz figures (+4.6 and +1.6 percent) are inside the one-step uncertainty of starting and stopping the turn.

To rerun the tests: `python rate_sweep.py --what pitch,yaw,gyro,gyrospeed,gyroyaw [--rates 30,60,...]` (local test script). The script reads the per-frame trace of a live run (`sh padrate.sh start --gfx window`, then `newgame`, `keydown vpad attach xbox`). For the gyro, use Hybrid with R held: set the control scheme in the pause menu's Options. For stick and mouse together, run `python mix_test.py 60 144`.

## The morph ball camera and the right stick

The game gives the right stick no job in the ball, and the camera there follows the ball on its own. The orbit around the ball is a PC feature of S13 that only the mouse drove, so the stick did nothing. Now the right stick orbits too, at `[pad] ball_orbit` radians per second at full deflection (default 2, 0 turns it off, see `docs/CONFIG.md`). It is a rate times the step, so it is the same at every step rate. Checked in the hangar with a virtual pad and the Morph Ball given by script: the stick right turns the camera round the ball, the stick up tilts it (screenshot `work/shots_wip/padrate_ball_orbit_stick.png`).

## Not verified

* The other control schemes. In Classic with ZR held the stick set the pitch within two steps at 60, 144 and 240 steps per second (the game skips the filter when that button is held), so nothing there depends on the rate. In Hybrid the stick gave no pitch with the virtual pad whatever button was held, so the game's filtered target was only reached through Dual Stick. The clock treats all schemes the same way.
* A real controller (the stick shape, dead zones, the gyro's scale), as in S35.
* The free lock-on with a target in view (the pitch margin) was not run again. The stick pitch in it uses the same clock.
