# S38: GPU time in the open scenes

Branch `gpuperf` (worktree `runtime-wt/gpuperf`). The open scenes (Tallon canyon cavern and gully, Chozo ruined fountain, Phendrana shorelines) ran at 7 to 15 ms of GPU time per frame on the RTX 3080 and hardly changed between 720p and 4K internal. S34 suspected two things: draws read their vertex, index and uniform data straight from host memory over PCIe, and about a tenth of the GPU time is spent between passes (full barriers).

## Result in short

* Confirmed: reading the pools from host memory was the larger cost. With device-local copies of the pool pages the draws read, GPU time per frame at 1080p fell by 21 to 45 % (canyon 7.7 to 6.0 ms, gully 7.8 to 4.2, fountain 9.3 to 7.3, shore 13.6 to 9.2). Almost all of it is in the two main 1080p passes, the ones that draw the world.
* The barriers are a small cost. Tracked barriers shorten the time between passes by 0.2 to 0.3 ms per frame (canyon 1.16 to 0.94 ms, shore 1.40 to 1.08) and gain 1.5 to 5 % fps.
* Both together, measured in a quiet window: +21 to +72 % fps (median of the paired windows) in the four open scenes at 1080p, 1440p and 4K internal, and 22 to 44 % less GPU time per frame (see "Frame rate"). The pictures are the same (see "Pictures").
* Both are on by default now (`[nvn] pool_mirror = on`, `[nvn] pass_barriers = tracked`) after a 29 minute run through 95 area loads with no device loss and no new validation messages (see "Defaults"). `pool_mirror = off` and `pass_barriers = full` give the old behaviour.

## How it was measured

`[prof] gpu_passes` (S34) writes a GPU timestamp between the render passes of every submission. `[nvn] gpuperf_ab = N` (new) turns both new paths off for N presents, then on for N, and so on, and marks every switch in the frame trace. One run then holds both states in the same scene with the same load on the machine, which is the paired-window method of S29: every window is compared with the mean of its two neighbours of the other state, so slow drift (other games starting and stopping) cancels. `gpuperf_ab_report.py` prints fps in off and on windows, the paired gain (median, 10th to 90th percentile of the per-window estimates) and with `--gpu` the GPU time per pass kind in each state.

This PC was shared with other streams running games the whole time; every run's `load.txt` in `work/run_gpuperf/<tag>/` has the system CPU busy share, the GPU busy median and the number of other game processes. Absolute fps move with that load; the paired gains move much less.

A first experiment copied the pools once and never followed the CPU's writes (`pool_mirror = static`). ## Mechanism 1: device-local copies of pool pages (`[nvn] pool_mirror = on`)

NVN memory pools are game memory imported into Vulkan as host memory (`VK_EXT_external_memory_host`), so every vertex fetch, index fetch and uniform read of a draw goes over PCIe. `src/gfx/nvn/nvn_gpu_pool.cpp` now gives a pool that draws read from a device-local buffer of the same size (the "copy"), page by page:

* A draw's vertex buffers, index buffer and uniform blocks go through `resolve_read`. If every 4 KiB page of the range is current in the copy, the draw binds the copy; otherwise it binds the pool as before and marks the pages as wanted.
* At the start of the next submission the wanted pages are copied from the pool buffer (at most 64 MiB a submission), with a full barrier before and a copy-to-everything barrier after.
* The CPU's writes: `src/mem/write_watch.cpp` makes copied pages read-only. The first write to such a page faults, a vectored exception handler (first in the chain) makes the page writable again and marks it written, and the write goes ahead. A written page is read from the pool until it is copied again. File reads into game memory (`fs_romfs.cpp`, `fs_volume.cpp`) and every mapping or protection change in `memory.cpp` hold a scope that keeps the tracker off those pages while they run (the kernel cannot write into read-only pages, and the guest's own protection wins). Pages that also have an alias view (`heap_alias`) are never tracked, because writes through the alias would not fault.
* The GPU's writes into pools (uniform buffer updates, fills, copies, image-to-buffer copies, storage buffers, stream-out) make the pages stale too, and the replay binds again.
* Pages the game rewrites every frame (the small CPU-uncached ring pools, flags 0x22) would be copied and overwritten before any draw read the copy. Two such wasted copies in a row make a page "hot": it stays in the pool for 600 presents, twice that the next time, up to 16 times.

`[nvn] pool_mirror_mb` (default 2048) caps the video memory the copies take. In the scenes measured the copies were 580 MiB and 110 MiB for the two large pools plus a few MiB of small ones.

Census at 1080p (mirror on, `census`): vertex bindings 3.76 million to the copy against 1.19 million to the pool, index 3.04 million against 0.13 million, uniform blocks 55 thousand against 9.37 million (uniform data is almost all per-frame, so it stays in the pool). About 1,500 write faults a second.

## Mechanism 2: tracked barriers (`[nvn] pass_barriers = tracked`)

The replay ended every render pass with a full memory barrier. With `tracked`, a pass whose draws can only have written its own attachments (no storage buffers or images, no stream-out) ends without one and remembers its attachments; the next pass or copy that touches one of them, or anything that is not a plain draw, gets the full barrier first. Layout changes take their stages and access from the old and new layout instead of everything (`src/gfx/nvn/nvn_gpu.cpp`, `layout_scope`); an image whose old contents are undefined still waits for all earlier commands, because its memory may belong to something in flight.

## Frame rate

Measured in a quiet window on 2026-10-25 (01:40 to 02:04): no other game on the PC, one game process at a time, a CPU build of another project at -j4 running beside it. Both new paths together (`pool_mirror = on`, `pass_barriers = tracked`), `gpuperf_ab = 120`, 20 s per scene, window 1280x720, audio muted, warm pipeline cache. Two rounds per resolution, run folders `work/run_gpuperf/q1080a`, `q1440a`, `q2160a` (round a) and `q2160b`, `q1440b`, `q1080b` (round b).

The two rounds were not equally quiet. In round a the other project's build kept the CPU 47 to 64 % busy and the GPU was busy only 66 to 72 % of the time (median): the game was often waiting on the CPU, and at 1440p and 4K some "on" windows were slower than their "off" neighbours (canyon at 4K -19 %, fountain at 1440p -14 %). In round b the CPU was 17 to 28 % busy and the GPU 87 to 94 %, and every scene gained at every resolution. Round b is the clean measurement:

## Defaults

Both on (`pool_mirror = on`, `pass_barriers = tracked`) since the three checks were in: the quiet-window fps rounds and the screenshot comparison above, and a run through many area loads.

The area-load run (`work/run_soak/soak_gp38on3`, 2026-10-25 02:52 to 03:21, 29 minutes) had both paths on and the Vulkan validation layer on, with other games sharing the GPU. It was New Game, every item, then 95 areas of the soak tour by `@warp` in all seven worlds. In each area it took a screenshot 30 frames after the load, poked the health back every 50 frames and pressed A in case a game-over dialog was up (`work/run_gpuperf/soak/on3/ld_*.png`). Results:

* No device loss and no crash; the run ended with its own pass at the end of the script.
* Validation: two messages, both `VUID-VkGraphicsPipelineCreateInfo-shaderTessellationAndGeometryPointSize-08776` at pipeline creation in the first 3 s. The same two came in a run with both paths off, so they are not from S38.
* All 95 screenshots show the area as it should look, with no missing, stretched or garbage geometry after a load.
* Memory levels off: the copies levelled off at 1,434 MiB in 90 pools, and GPU dedicated memory and the process's private bytes plateaued (drift table in `report/soak_table.md`). 404 thousand write faults in the run, 1,885 MiB copied. In the paired first try below, GPU dedicated memory and private bytes ended about 1.4 GiB higher with the paths on than off: the copies.

A first try of the same run with both paths on and a second process with both off (`soak_gp38on`, `soak_gp38off`, 61 cycles of the soak route with walking) gave the same result for 13 areas in both: no device loss and the same two validation messages. Then Samus walked into the lava in Chozo Magma Pool in both, and the game-over dialog stopped the rest of the route. The second try above therefore only warps and heals.

The copies take video memory: about 1.4 GiB in the run above, at most `pool_mirror_mb` (2048 MiB). On a card with little video memory `pool_mirror = off` gives it back.

## Settings

| setting | default | what it does |
|---|---|---|
| `[nvn] pool_mirror` | `on` | `on`: device-local copies of the pool pages draws read; `off`: draws read the pools in host memory. |
| `[nvn] pool_mirror_mb` | 2048 | most video memory the copies may take |
| `[nvn] pass_barriers` | `tracked` | `tracked`: no full barrier after passes that only wrote their attachments; `full`: a full barrier after every pass |
| `[nvn] gpuperf_ab` | 0 | measurement: both paths off in even windows of N presents |
