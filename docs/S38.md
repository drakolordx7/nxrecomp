# S38: GPU time in the open scenes

The open scenes (Tallon canyon cavern and gully, Chozo ruined fountain, Phendrana shorelines) ran at 7 to 15 ms of GPU time per frame on the RTX 3080 and hardly changed between 720p and 4K internal. S34 suspected two causes: draws read their vertex, index and uniform data straight from host memory over PCIe, and about a tenth of the GPU time is spent between passes (full barriers).

## Result in short

* Reading the pools from host memory was the larger cost. With device-local copies of the pool pages the draws read, GPU time per frame at 1080p fell by 21 to 45 % (canyon 7.7 to 6.0 ms, gully 7.8 to 4.2, fountain 9.3 to 7.3, shore 13.6 to 9.2). Almost all of the gain is in the two main 1080p passes, the ones that draw the world.
* The barriers are a small cost. Tracked barriers shorten the time between passes by 0.2 to 0.3 ms per frame (canyon 1.16 to 0.94 ms, shore 1.40 to 1.08) and gain 1.5 to 5 % fps.
* Together, measured in a quiet window: +21 to +72 % fps (median of the paired windows) in the four open scenes at 1080p, 1440p and 4K internal, and 22 to 44 % less GPU time per frame (see "Frame rate"). The pictures are the same (see "Pictures").
* Both are on by default (`[nvn] pool_mirror = on`, `[nvn] pass_barriers = tracked`) after a 29 minute run through 95 area loads with no device loss and no new validation messages (see "Defaults"). `pool_mirror = off` and `pass_barriers = full` give the old behaviour.

## How it was measured

`[prof] gpu_passes` (S34) writes a GPU timestamp between the render passes of every submission. `[nvn] gpuperf_ab = N` (new) turns both new paths off for N presents, then on for N, and so on, and marks every switch in the frame trace. One run then holds both states in the same scene with the same load on the machine. This is the paired-window method of S29: each window is compared with the mean of its two neighbours of the other state, so slow drift (other games starting and stopping) cancels. `gpuperf_ab_report.py` prints fps in the off and on windows and the paired gain (median, 10th to 90th percentile of the per-window estimates). With `--gpu` it also prints the GPU time per pass kind in each state.

Other games were running on this PC the whole time. Every run records the system CPU busy share, the GPU busy median and the number of other game processes. Absolute fps move with that load; the paired gains move much less.

## Mechanism 1: device-local copies of pool pages (`[nvn] pool_mirror = on`)

NVN memory pools are game memory imported into Vulkan as host memory (`VK_EXT_external_memory_host`), so every vertex fetch, index fetch and uniform read of a draw goes over PCIe. `src/gfx/nvn/nvn_gpu_pool.cpp` now gives a pool that draws read from a device-local buffer of the same size (the "copy"), page by page:

* A draw's vertex buffers, index buffer and uniform blocks go through `resolve_read`. If every 4 KiB page of the range is current in the copy, the draw binds the copy. Otherwise it binds the pool as before and marks the pages as wanted.
* At the start of the next submission the wanted pages are copied from the pool buffer (at most 64 MiB a submission), with a full barrier before and a copy-to-everything barrier after.
* The CPU's writes: `src/mem/write_watch.cpp` makes copied pages read-only. The first write to such a page faults. A vectored exception handler (first in the chain) makes the page writable again and marks it written, and the write goes ahead. A written page is read from the pool until it is copied again. File reads into game memory (`fs_romfs.cpp`, `fs_volume.cpp`) and every mapping or protection change in `memory.cpp` hold a scope that keeps the tracker off those pages while they run (the kernel cannot write into read-only pages, and the guest's own protection wins). Pages that also have an alias view (`heap_alias`) are never tracked, because writes through the alias would not fault.
* The GPU's writes into pools (uniform buffer updates, fills, copies, image-to-buffer copies, storage buffers, stream-out) also make the pages stale, and the replay binds the pool again.
* Pages the game rewrites every frame (the small CPU-uncached ring pools, flags 0x22) would be copied and overwritten before any draw read the copy. After two such wasted copies in a row a page counts as "hot": it stays in the pool for 600 presents, twice that the next time, up to 16 times.

`[nvn] pool_mirror_mb` (default 2048) caps the video memory the copies take. In the scenes measured the copies were 580 MiB and 110 MiB for the two large pools, plus a few MiB of small ones.

Census at 1080p (mirror on, `census`): vertex bindings 3.76 million to the copy against 1.19 million to the pool, index 3.04 million against 0.13 million, uniform blocks 55 thousand against 9.37 million (uniform data is almost all per-frame, so it stays in the pool). About 1,500 write faults a second.

## Mechanism 2: tracked barriers (`[nvn] pass_barriers = tracked`)

The replay used to end every render pass with a full memory barrier. With `tracked`, a pass whose draws can only have written their own attachments (no storage buffers or images, no stream-out) ends without one and remembers its attachments. The next pass or copy that touches one of them, or anything that is not a plain draw, gets the full barrier first. Layout changes take their stages and access from the old and new layout instead of everything (`src/gfx/nvn/nvn_gpu.cpp`, `layout_scope`). An image whose old contents are undefined still waits for all earlier commands, because its memory may belong to something in flight.

## Frame rate

Measured in a quiet window on 2026-10-25: no other game on the PC, one game process at a time, and a CPU build of another project at -j4 running beside it. Both new paths together (`pool_mirror = on`, `pass_barriers = tracked`), `gpuperf_ab = 120`, 20 s per scene, window 1280x720, audio muted, warm pipeline cache. Two rounds per resolution: round a ran 1080p, 1440p, 4K and round b ran 4K, 1440p, 1080p.

The two rounds were not equally quiet. In round a the other project's build kept the CPU 47 to 64 % busy and the GPU was busy only 66 to 72 % of the time (median), so the game often waited on the CPU. At 1440p and 4K some "on" windows were slower than their "off" neighbours (canyon at 4K -19 %, fountain at 1440p -14 %). In round b the CPU was 17 to 28 % busy and the GPU 87 to 94 %, and every scene gained at every resolution. Round b is the clean measurement:

## Defaults

Both paths are on (`pool_mirror = on`, `pass_barriers = tracked`) after three checks: the quiet-window fps rounds, the screenshot comparison above, and a run through many area loads.

The area-load run (2026-10-25, 29 minutes) had both paths on and the Vulkan validation layer on, with other games sharing the GPU. It was New Game, every item, then 95 areas of the soak tour by `@warp` in all seven worlds. In each area it took a screenshot 30 frames after the load, poked the health back every 50 frames and pressed A in case a game-over dialog was up. Results:

* No device loss and no crash. The run ended with its own pass at the end of the script.
* Validation: two messages, both `VUID-VkGraphicsPipelineCreateInfo-shaderTessellationAndGeometryPointSize-08776` at pipeline creation in the first 3 s. The same two came in a run with both paths off, so they are not from S38.
* All 95 screenshots show the area as it should look, with no missing, stretched or garbage geometry after a load.
* Memory levelled off: the copies stopped growing at 1,434 MiB in 90 pools, and GPU dedicated memory and the process's private bytes plateaued. There were 404 thousand write faults in the run and 1,885 MiB copied. In the first try below, GPU dedicated memory and private bytes ended about 1.4 GiB higher with the paths on than off, which is the copies.

A first try of the same run had both paths on in one process and both off in a second (61 cycles of the soak route with walking). Both gave the same result for 13 areas: no device loss and the same two validation messages. Then Samus walked into the lava in Chozo Magma Pool in both, and the game-over dialog stopped the rest of the route. The second try above therefore only warps and heals.

The copies take about 1.4 GiB of video memory in the run above. Unless `pool_mirror_mb` is set, the cap follows the card: a quarter of the largest device-local heap, at most 2048 MiB, and no copies under 4 GiB (`src/gfx/nvn/nvn_mirror_cap.h`, logged at the first pool as `pool copies: cap ...`).

Both paths have a switch in the launcher (Display tab, under Frame rate) and on the F1 page (Display, after Chromatic aberration): "Faster GPU memory (uses more video memory)" and "Fewer GPU pipeline waits". Both are on by default, saved as `[display] fast_gpu_memory` and `fewer_gpu_waits` in controls.ini, and applied at the next start. A value of `[nvn] pool_mirror` or `pass_barriers` in mpr.ini or the environment wins over them.

## Settings

| setting | default | what it does |
|---|---|---|
| `[nvn] pool_mirror` | `on` | `on`: device-local copies of the pool pages draws read; `off`: draws read the pools in host memory. |
| `[nvn] pool_mirror_mb` | from the card | most video memory the copies may take; not set: min(2048 MiB, a quarter of the video memory), none under 4 GiB |
| `[nvn] pass_barriers` | `tracked` | `tracked`: no full barrier after passes that only wrote their attachments; `full`: a full barrier after every pass |
| `[nvn] gpuperf_ab` | 0 | measurement: both paths off in even windows of N presents |
