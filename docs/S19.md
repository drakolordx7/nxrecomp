# S19: integration and polish

Branch `polish`. It merges the button prompt work (`prompts`) into the line of the other streams, checks it in the real game, and closes five loose ends from the last session.

## Merge of `prompts`

The conflicts with the display extras were all additive: both sets of settings sections (`[hdr]`, `[upscale]`, `[latency]` and `[prompts]`), enums, ini writers and readers, struct members, tests and the declarations in `nvn_core.h`, `nvn_texdata.h` and `nvn_texture_registry.cpp` are kept. The `console_block_height` fix in `nvn_texture_layout.cpp` stays (263 small textures were untiled with the wrong block height).

## Button prompts in the real game

The first real run found two bugs the unit tests could not see.

1. **The front end has its own icons.** The title screen and the menus draw red copies of the buttons from `PreloadFrontEndMPT.pak` (`btn_A`, `btn_A_P`, `btn_B` ... `btn_minus`), not the blue ones of `GuiSysMP1.pak` that the table listed. The hook never recognised them (the log showed "17 of 17" and not one replacement). `prompt_resolve.cpp` now carries the front end id next to each icon (16 of 17; the d-pad is the same texture in both), and the scan in `prompts.cpp` hashes both copies (33 textures).
2. **The game stores its UI textures upside down.** The first replaced icons came out with the A as an upside-down A and the Enter arrow flipped. The hook now writes the upright pack icon with its rows reversed (`tex_override.h` says what order the hook has to deliver).

Not done: clicking the combo on the F1 page itself (nothing drives the Dear ImGui page from outside; the step uses its apply path).

## Setup tool: texture cache entry formats

`tools/setup/src/texcache.cpp` now writes the three entry kinds of `docs/S4f.md`. The key formula is the same; the encoder revision is 3, so an old `bc7_cache` is rebuilt by the marker file.

* **BC5** for a linear texture whose level 0 is fully opaque with a blue channel of at most 2 (two-channel normal maps). Encoded with `rgbcx::encode_bc5_hq` from bc7enc_rdo, which is now part of the setup core with the reference BC7 decoder.
* **RGBA8** (UNORM or sRGB as the source) for a texture whose BC7 result is under 28 dB. Measured over all 4,413 textures at quality 3, one texture is under 33.6 dB: the white-noise lookup at 19.2 dB.
* **Block height.** The runtime's `console_block_height` (the S17 fix) also applies to ASTC textures, and the cache key carries the block height. Setup still used the smallest covering height, so for the affected textures it would have written entries under another key and untiled them wrongly. Setup uses the console rule now.

Full run on the player's RomFS: 4,413 ASTC textures, 4,369 distinct cache keys (44 textures share one), 0 failed, 3 min 34 s on all threads: 1,395 BC5, 1 RGBA8 (349,804 bytes, `3933333769ba44db.bc7`), 2,973 BC7. `check_texcache.py` over 734 entries (every 6th texture, 238 of them BC5): PSNR RGB minimum 34.84 dB, mean 50.35. Two textures miss the script's default floors (SSIM 0.962 and alpha 32.6 dB); they are the two known worst cases of `check_texquality.py` and are BC7 as before. In the game, 78 BC5 entries were loaded from this cache in one gameplay run.

## Vulkan validation error "image is VK_NULL_HANDLE"

Cause: a texture that is still alive when the back end shuts down (the game never finalized it, or a test left it behind) stays in the texture registry, and `gpu::tex_shutdown` frees every image. The texture kept its pointer to the freed image. The next texture created over the same memory with the same shape found it as an alias (`texture_registry_find_alias`, added in S4f) and used freed memory: a barrier on a null or garbage image, or a crash. In `gfx_nvn_scene_state` this showed under load because the heap reused the freed block; before the fix the group crashed or logged the error in 5 of 8 runs.

Fix: `texture_registry_detach_gpu()` clears `Texture::gpu` on every registered texture before the images are freed. Regression test `gfx_nvn_texgpu.shutdown_detaches_live_textures_from_freed_images` (fails without the fix, checked). After the fix `gfx_nvn_scene_state` ran 8 of 8 clean with validation on.

A gameplay run with validation on (hangar, map screen, 204 s into the run) found a second error, `VUID-vkCmdDraw-imageLayout-00344`: ten draws sampled an image in SHADER_READ_ONLY while it was the colour target of the pass. The back end already binds the dummy texture when a draw samples its own colour or depth target, but it compared texture objects. Since S4f several objects over one storage share one image, so the sampled object and the target object can differ while the image is the same. `nvn_replay.cpp` now compares the image (`shares_image`). Regression test `gfx_nvn_scene_texture.sampling_an_alias_of_the_pass_target_binds_the_dummy` (reproduced the exact error before the fix).

## Shader cache

Block `46742355274dd77e` was never missing from the cache: it is translated (7,632 bytes, `spirv-val` clean) and was already in the release pack. The "missing" lines came from probe runs that had no shader cache configured at all (all 454 blocks of those runs were missing). The block that really was missing from the pack is `f8e9efd694abe636` (S4f translated it after the pack was built). The pack is rebuilt from the 13,019 modules of `work/shader_cache/spirv` (13,020 entries with `results.tsv`, zstd level 12, 261 MB) at `work/setup_test/shader_cache.mprshc`; both blocks are inside.

## Release

* `tools/release/make_release.py` ships `prompts/prompt_icons.pak` and `prompts/LICENSE-Kenney-InputPrompts.txt` (`--prompts-dir`, default `runtime/assets/prompts`). The audit still refuses every other `.pak`; this one is allowed by exact path, size under 4 MiB and its `MPIP` header.
* Licence texts added to `tools/release/licenses`: `LICENSE.yuzu-Eden.GPL-2.0.txt`, `LICENSE.libcxxabi.Apache-2.0-LLVM-exception.txt`, `NOTICE.MSVC-runtime.txt`; `THIRD_PARTY_NOTICES` (release template and this repo's `THIRD_PARTY_NOTICES.md`) list them.
* **Open: the Visual C++ runtime.** `mpr.exe`, the setup tools and the astcdec DLLs link the runtime dynamically (`MSVCP140.dll`, `VCRUNTIME140.dll`, `VCRUNTIME140_1.dll`) and the release does not ship them. A player without the Visual C++ Redistributable gets a "DLL not found" error at start. The notice says so. Either link the runtime statically (`/MT`, rebuild of the lifted libraries needed) or tell players to install the redistributable; shipping the DLLs needs the REDIST terms checked first.
