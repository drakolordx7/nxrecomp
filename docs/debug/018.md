# 018 Real boot stops in a lazy PLT binding (not a service problem)

Symptom: after nvdrv, vi and hid initialise, the graphics thread dies with GUEST TRAP: indirect call to an address that is not a known function (0x2bd1f0002bd0f9) at sdk+0x56cad0.

Finding: sdk+0x56cad0 is a PLT stub whose GOT slot (sdk+0xc7ade8) still holds 0x7700001318, the entry of the rtld lazy resolver, after the earlier calls; the resolver (host stand-in rtld_fn_138c in mpr_main.cpp) returns garbage for that slot. No service request is involved (every request before it succeeded, the IPC trace shows the last ones as nvdrv Close). Noted (boot work).

Detail: the stub at sdk+0x56cad0 is `stp x16, x30, [sp, #-0x10]!` then a branch through GOT slot sdk+0xc7ade8, which holds rtld+0x1318 (0x7700001318) until it is resolved: rtld+0x1318 is rtld's lazy resolver (spills x0..x8/q0..q7, `x1 = (x17 - x16 - 8) / 8` reloc index, `x0 = [x16 - 8]` link map, `bl rtld+0x8b0`, `br x16`). The resolve function at rtld+0x8b0 returned 0x002bd1f0002bd0f9, so the `br x16` at rtld+0x1388 trapped. This is the first lazy binding of that symbol (earlier PLT calls from the same module resolved), so the suspect is the symbol lookup behind rtld+0x8b0 (hash / symbol table walk, lifted code) for that relocation, not an IPC reply.
