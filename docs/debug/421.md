# 421 The sweep's "hangs" and "boot deadlocks" were not deadlocks

Symptom (S15 sweep, 31 chunks): 8 runs ended as hangs or boot deadlocks. Four froze after a warp with the main thread in `CGraphicsFrameToken::WaitUntilFinished`, and four never reached the Frigate during the boot (two with the main thread in `CScopedSceneTransferLock`, one in an audio IPC call). A lost wake-up in the kernel's condition variable or address arbiter was suspected.

What the dumps show, run by run:

- The watchdog (no presented frame for 60 s) fired in only one of the 8 runs (`phendrana_canyon_entryway`). There the render thread was inside `a2b_encode_bc7`, working through a cold BC7 cache: one 1024x1024 texture after another, 1.2 to 2.5 s each, all on the render thread. It was slow, not stuck. See "Watchdog" below.
- In the other 7, the sweep's own stall detector (300 s without a script marker, 420 s for the boot) wrote the dump and killed the run. The presented-frame count in those dumps was 2,395 to 81,667, and the game's main loop kept running (the audio update counter kept climbing at 20 to 40 a second). The game was alive, and its load did not finish.
- Each dump captured one moment of a live system: main in `WaitUntilFinished` (the frame token it waits for is signalled by the graphics thread, which was itself between two frames), the graphics thread in `nvnSyncWait` or in its command wait, and the job and file threads idle. The sweep dumps did not list the words the threads sleep on (the kernel waiter dump came after the sweep), so they cannot show a lost wake-up either way. In the stalls reproduced since (debug note 422), the waiters sleep on words that say "waiting" (a light event in state 1, condition variable keys at 1). Nothing is signalled and left unconsumed.
- The kernel's logic was checked against the SDK's own protocol. `tests/test_kernel_lightevent.cpp` ports `nn::os::detail::WaitLightEventImpl` and `SignalLightEventImpl` (read from the decompiled `sdk.nso`) and runs 20,000 auto-clear round trips with 1 and with 4 waiters, and 5,000 manual-clear rounds with 4 waiters. The mutex and condition variable have the existing stress tests (`kernel_sync`, debug note 180, which already showed by a ring log that a stuck hand-over is a thread that was woken and not scheduled). All of them pass, and none of them loses a wake-up.

Where the time went: a controlled reproduction, debug note 422. In short, the game was starved of CPU. The console core model pins each guest thread to one host processor in strict priority bands, and the resource loader and the file workers sit in the lowest band. When other programs keep that processor busy (other builds and games on the PC at the time of the sweep), those threads stay ready and get almost no CPU time. Meanwhile the main and graphics threads, in higher bands, keep the frames coming. The warp or the boot then takes minutes or never ends, and the scripted run reports it as a hang.

Watchdog: texture transcodes now count as progress (`diag_progress`, called after every transcoded level), so a cold cache no longer produces a "freeze" report. The freeze and stall dumps also gained what this analysis needed: the NVN back end state (last submitted serial, timeline value, sync waits begun and done, submits, presents), the CPU time of every thread, and, for a requested dump, a second sample `freeze_resample_s` later. A thread that sits in guest code and used under 5 % of the time between the two samples is starved. `tools/test/sweep.py` reports that in the failure reason.

The cause of the `frigate_air_lock` crash is not found in this note (see S20.md).
