# 422 A loaded PC starves the game's lowest priority band: boots and warps that never finish

Symptom: scripted runs on a busy machine (S15 sweep, debug note 421) stop reaching their goal. The boot does not get to the Frigate in 420 s (72 s on a quiet machine), or a warp does not arrive in 300 s (10 to 40 s). The game keeps drawing frames and the main thread keeps running its loop, but the load never ends.

Reproduction (`stab_hog_run.py`, `hogs.py`): the stab build runs the same chain (boot, then six warps: fiery shores, geothermal core, lake tunnel, canyon entryway, chapel of the elders, chapel tunnel) while six busy-loop programs at normal priority sit on the three host processors of the game's console cores (`[sched] host_cpus` fixes the processors so every run meets the same load). That is what another program's build or test run does to those processors.

| Setup | Result |
|---|---|
| no spinners (control, sweep of 110 areas) | 110 of 110 OK, 60 min with two games at a time |
| normal class, no guard | the boot never reached the Frigate in 1,231 s (6 of 6 areas not reached); in four more runs it hung three times and took 420 s once; with the spinners starting at "boot ready", every chunk stalled after the first warp (5 chunks in a row) |
| above normal class | 6 of 6 not reached |
| high class | 6 of 6 OK, 356 s (loads 9 to 14 s) |
| normal class with the starvation guard | 6 of 6 OK, 596 s (loads 18 to 31 s); with the spinners starting at "boot ready" 6 of 6 OK, 455 s |
| the S15 sweep build, normal class, spinners | stalls the same way |

The dumps of the stalled runs show the picture of the sweep (debug note 421): main in `WaitUntilFinished`, graphics thread in `present`, file and job threads waiting. The thread that matters is the resource loader (`guest-84`): it sits in guest code (`CBufferedCompression::DecompressBuffer`, a loop that decompresses 40 KB and yields), ready and not running, with 39 s of CPU time in 420 s of run time and about 30 ms between two dumps 4 s apart.

Cause: the console core model (debug notes 180 and 221) pins a guest thread to one host processor and maps the HOS priorities to six Windows bands. The loader and the file workers use the lowest band (Windows priority 6 in a normal class process). Spinners at 8 keep the processor, so the loader gets a time slice only when Windows' starvation boost lifts it to 15 for two slices after four seconds. A high class process lifts every band above the spinners; above normal does not (the lowest band is then 8, level with them).

A yield costs far more than it gives. Measured with `yield_demo.cpp` (one thread pinned next to six normal-priority spinners, 1 ms of work and then a yield, iterations in 4 s):

| thread | yield | normal class | high class |
|---|---|---|---|
| lowest band | `SwitchToThread` | 1 | 1,018 |
| lowest band | `Sleep(0)` | 1 | 932 |
| lowest band | none | 18 | 3,463 |
| highest band | `SwitchToThread` | 1,167 | 1,321 |
| time critical | `SwitchToThread` | 1,333 | 1,452 |
| time critical | none | 3,898 | 3,927 |

A yield hands the time slice to a spinner even when the spinner has the lower priority, and the thread waits for the next slice. The loader yields after every 40 KB it decompresses (`CThread::YieldCurrentThread` -> `SleepThread(0)` -> `SwitchToThread`), so even a boosted loader would get a third of its time.

Fix (`src/kernel/starvation_guard.cpp`, `[sched] starvation_guard`, `starvation_ms`): a poller asks the system every 150 ms (NtQuerySystemInformation) which of the process's threads are in the Ready state and have not been switched in since the last poll. A guest thread that stayed ready for 300 ms goes to Windows' top normal priority for 450 ms, and while it is boosted its yields (`yield_host`) keep the processor. Then it returns to its band. A healthy run never has a thread ready for 300 ms with no context switch, so nothing changes for it; the log line "was ready for N ms without running" names the thread the first five times (and then at powers of two). Play mode in a window runs in the high class and does not need it. `[sched] priority_class = high` (`NXRT_SCHED_PRIORITY_CLASS=high`) is still the better choice for a scripted run on a machine where nothing else matters; the guard is what keeps a run at normal class moving.

Regression test: `kernel_starvation.boosts_a_lowest_band_thread_that_other_programs_starve` (six normal-priority spinners on the processor of a lowest-band guest thread: under 500 ms of CPU in 3 s without the guard, over 800 ms in 4 s with it; 2,968 ms of 5 s in a run).

What this does not explain: the S15 dumps where the loader itself was waiting on its event (`wait_for_address`) and nothing in the process was running. A thread that has been woken and is waiting for its processor still shows the kernel wait in its stack, so those dumps fit a load the same way, but the sweep dumps carry no CPU times or ready states, and a rerun of the same chains with the S15 build and the stab build, without spinners, did not stall in 2 + 110 area loads. Treat that part as consistent with the cause above, not proven.
