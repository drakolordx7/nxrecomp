# 321 Beam and visor selects from the keyboard were lost on slow frames

Symptom: keys 1 to 8 and the wheel did nothing in a scripted run while the d-pad keys worked. Other keys read as "menu" bindings (`1 = none`) every few frames.

Cause 1: the context was "in game" only when `ProcessInput` had run within the last 300 ms of host time. A game frame under load takes 100 ms and more, so the flag flipped to menu and the menu layer switched the keys off. Cause 2: a select is a pulse of 80 ms of host time. The game samples input once per tick; with a 100 ms frame the pulse was over before the sample, and other readers of the pad could use it up.

Fix: "in game" means `ProcessInput` ran during one of the last four frame boundaries. A pulse lasts until a poll has reported it and two frame boundaries have passed (`Engine::frame_tick`, called from the frame hook), and only the head of the queue is ever reported. Unit tests `select_pulse_survives_a_slow_game_frame` and `select_pulse_holds_for_frame_boundaries_once_they_are_counted`.

Not verified in the game: the last real run was before the frame-counted hold. The pad sequences themselves are right: X plus d-pad up, right, down, left gave beams 0, 2, 1, 3.
