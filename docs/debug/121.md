# 121 NVNtextureView is 16 bytes wide in this game, not 0x28

Symptom: after NVN reached the Vulkan back end the graphics thread faulted in `CGraphicsHandleIndexer_NVN::FreeId(0)` (reading 0x78cfd0f5e0) at the start of the first frame: `CFrameDelayedKiller_NVN::InitializeFrame` frees 33 texture descriptor ids, all zero.

Cause: `CGraphicsTextureToken_NVN` (352 bytes) keeps an NVNtextureView at +0x40 and its own fields at +0x50 (-1), +0x58 (-1) and +0x60 (the descriptor id, -1 in the constructor). The constructor calls `nvnTextureViewSetDefaults(token+0x40)` last. The back end (S4d) used the 0x28 bytes of the practice mod's header and its SetDefaults cleared all 0x28 bytes, writing 0 over the id at +0x60. The next `ShutdownResources` saw id 0 (not -1), queued it, and the killer freed id 0 (below the reserved range 0x100): the indexer indexed far outside its table. On the console SetDefaults must only touch the first 0x10 bytes.

Fix (boot2): the view data is packed into 16 bytes (`ViewPacked` in api_texture_builder.cpp: four int16 level/layer fields, u16 format, 3 bits per swizzle component, target, depth/stencil mode, set mask), SetDefaults clears 16 bytes, Compare compares 16 bytes. The test values 0x7FFFFFFF levels became 0x7FFF.

For S4d / the lead: audit the other embedded NVN structs the same way. A struct the game embeds next to its own fields cannot be larger than the game's layout allows; the game is the oracle (here: token +0x40..+0x50). docs/nvn_struct_sizes.md lists 0x28 for the view from three sources that all trace to the practice mod header.
