# 420 The guest's WFE and YIELD only paused the host core

Symptom (S15, debug note 360): the SDK's busy mutex froze loads because `nn::os::LockBusyMutex` is a spin loop (`ldaxr`, `cbnz`, `wfe`), and the lifter compiled `wfe` to nothing. A host stand-in for that one function fixed the freezes; every other spin loop in the SDK was left as it was.

The module contains 4 `wfe` and 65 `yield` in the SDK (`sdk.nso`), and none in main, subsdk0 or rtld. The `wfe` instructions sit in `LockBusyMutex` and in the disable-count code around it. Most `yield` instructions belong to a 64-round spin lock that polls with a plain load and then falls back to `ldaxr`. Because the lifted `yield` did nothing, the compiler was also free to read that plain load once and reuse the value.

Change: the lifter now emits `nx_spin_hint(1)` for `wfe` and `nx_spin_hint(0)` for `yield` (recomp `ctx.h`, `a64.py`, tier 2 `misc.py`). `sev`, `sevl` and `wfi` stay no-ops. `nx_spin_hint` calls the function stored in `nx_spin_hook`. With no hook set, it is an x86 `pause`, so the difftest, mutation and end-to-end oracles, which never set a hook, run the same code as before. The call goes through a pointer the compiler cannot see through, so a spin loop of plain loads is no longer folded into one load.

The runtime sets the hook (`src/kernel/busy_mutex.cpp`, `[sched] spin_yield`, default on). `wfe` hands the host processor to another ready thread at once (`yield_host`). `yield` pauses, and hands the processor over on every 64th call. Both go through `yield_host`, which does nothing for a thread the starvation guard has boosted (debug note 422).

Checks: `kernel_busy_mutex.wfe_spin_loop_does_not_starve_the_thread_it_waits_for` (a highest-priority spinner and a lowest-priority releaser on one host processor; the spinner is released within 10 s; it was not before), `installed_hook_receives_both_kinds`, `spin_hint_without_a_hook_is_only_a_pause`. The recomp oracles are unchanged and green (S20.md).

The host stand-in for `LockBusyMutex` stays on. It is cheaper than the SDK loop, takes the lock the same way and has its own test. With `NXRT_SCHED_BUSY_MUTEX_HLE=0`, the SDK loop now works too (S20.md has the run).
