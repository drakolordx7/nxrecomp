# 320 Mouse aim did nothing in the real game: the world is Y up

Symptom: with the mouse turned on, `CPlayerMP1::ProcessInput` ran the aim hook (counts arrived, the gate was open, the transform call returned) but neither the view nor the probe yaw moved, and the transform read back as yaw 0 at the next frame boundary.

Cause: the aim rotated the player's transform about Z, as in a Z-up world. The game's world is Y up (forward is +Z at yaw 0). A turn about Z is a roll, and `CPlayerMP1::Think` flattens any transform whose second row has an X or Z component (the `LookAt` block near 0xc6eac8), so the roll was removed every tick. The physics object had taken the rolled orientation (a quaternion with only a Z part), which is how it showed up. Pitch had a second problem: `CPlayerMP1+0x5cc` is eased toward `+0x5d0` by `UpdateFreeLook` on every Think, so the value the aim wrote was pulled back before the camera used it.

Fix: yaw is applied about Y, left-multiplied onto the rotation (`rotate_transform_yaw`); the pitch target at `+0x5d0` is written with the pitch. The heading in the trace is `atan2(m[2], m[0])` (positive = turn left); forward is (sin yaw, 0, cos yaw).

Evidence: 1000 counts right gave yaw -0.767945 and a screenshot turned to the right; 500 counts up gave pitch +0.383972 and the view looked up the cliff wall. At 60, 144 and 240 steps per second all bursts are within 0.0001 % of counts times sensitivity.
