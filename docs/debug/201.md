# 201 The audio renderer paced by the host clock: queue creep, and what keeps it from clicking

`AudioProcessor::Wait` (the port of Ryujinx.Audio's pacing) sends a 5 ms frame every 5 ms by the host's steady clock and sleeps 1 ms at a time until the next frame is due. On the console and in Ryujinx the device's `AppendBuffer` blocks, so the device clock ends up setting the pace. Here `HostAudioDevice::AppendBuffer` hands the frames to a sink and returns, so nothing ties the renderer to the sound card:

- A card that runs a little slower than the host clock (a few hundred parts per million is normal) fills the queue; after a while the sink's queue is full and a 5 ms frame is dropped: a click, once every few minutes.
- A card that runs faster drains it; the queue empties and the card plays silence until the next frame: a gap.
- `sleep_for(1 ms)` is rounded up to the timer period (15.6 ms by default). Frames then come in bursts of three, and a thread that is descheduled for 25 ms by a busy machine empties the queue.

Changes (`src/services/audren/Dsp/AudioProcessor.h`, `Integration/*`, `audio_xaudio2.cpp`, `audio_paced.cpp`):

1. `AudioSink::has_device_clock()` and an exact `queued_frames()`. XAudio2: `submitted - SamplesPlayed` of the source voice. `HostAudioDevice::GetQueuedNanoseconds()` turns it into time.
2. `Wait()` with a device clock keeps about 40 ms queued: it sleeps while the queue holds more and returns at once (render the next frame) when it holds less. Longest wait is eight frames, so a stuck device cannot stall the guest. Without a device clock (null sink) the original host-clock pacing runs unchanged.
3. The two renderer threads register with MMCSS ("Pro Audio") and the process timer is set to 1 ms while a renderer is open. The game calls `RequestUpdateAudioRenderer` from its main thread (once per game update, `CAudioManager::PostScriptingUpdate`), and `AudioRenderSystem::Update` holds the renderer's lock; `SendCommands` (the renderer's own frame) needs the same lock. A main thread that the system deschedules inside the update holds up the frame: priority inversion. Under a heavy compile load that showed as an underrun every minute or so. The update handler (`audio.cpp`) raises the calling thread to THREAD_PRIORITY_HIGHEST for the length of the call (`ScopedAudioLockBoost`), the stand-in for priority inheritance.
4. `[audio] sink = paced` is a simulated device (drains at the sample rate, optional `paced_ppm` clock error, counts underruns and queue lows) so the loop can be measured on a machine without a sound card, and a log line carries the time of each underrun.

Measured (game headless on the title and front end, WAV capture, the numbers are in S9.md): the first version, host clock only on the paced device with 25 ms target and no thread priority, had 2 underruns in 73 s (queue low 0 frames). With MMCSS, the 1 ms timer and a 25 ms target: 0 underruns in 73.6 s, lowest queue 172 frames (3.6 ms), which is why the target is 40 ms now.
