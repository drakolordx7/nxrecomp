# 001: spirv-val rejects a geometry shader that writes the viewport index

**Symptom.** First run of the Ryujinx harness on the stand-in corpus: 221 of 222 blocks valid, one `invalid`:
`Operand 3 of Decorate requires one of these capabilities: MultiViewport ShaderViewportIndex ShaderViewportIndexLayerEXT ...`.
The row was labelled `vertex`.

**Cause.** Two things. (1) The harness only distinguished vertex, fragment and compute, so the block was a geometry
shader (SPH type 4) reported as a vertex shader and given vertex binding slots. (2) Ryujinx's SPIR-V back end declares
`ShaderViewportIndexLayerEXT` for vertex and tessellation stages that write Layer or ViewportIndex, and `Geometry`
for geometry stages, but never `MultiViewport`, which a geometry-stage `ViewportIndex` output needs. Wonder's corpus
had no geometry shaders, so it never showed. It is back-end bug 3, next to the two Wonder documented.

**Fix.** `harness/Program.cs`: stage now comes from the SPH type (1 vertex, 2 tess control, 3 tess evaluation,
4 geometry, 5 pixel) and `StaticGpuAccessor` uses Ryujinx's stage slots 0..4. `AddMissingBuiltInCapabilities` inserts
`OpCapability MultiViewport` when the module decorates `BuiltIn ViewportIndex` without any of the three capabilities.
Corpus result after the fix: 222 of 222 valid. Upstream candidate: add the capability in `SpirvGenerator.Generate`.
