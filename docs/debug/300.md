# 300 The game runs once per Update call at 1/60, so a faster frame is a faster game

Symptom: at 120 and 240 frames per second the front end (movies, menu timers) ran 2 and 4 times too fast; the movie player consumed video at `frames / 60` per second. Audio, which plays in real time, fell behind.

Cause: `CGameArchitectureSupport::Update` (0x3c81c8) adds the elapsed time to an accumulator, subtracts 1/60 in a do-while and floors the accumulator at -1/60. When a frame is shorter than 1/60 the floor wins, the loop body runs once, and the tick it queues carries the literal 1/60 (`BeginSimulationTick`, `CInputGenerator::Update`, `TimerTick`, the render-state sum). The accumulator never holds more than a frame, so there is no catch-up and no slow-down either way: time is "one tick per call".

Fix: the mid hooks load the measured step into the three registers that held 1/60 (w8 at 0x3c8238 and 0x3c8354, w27 at 0x3c830c) so the accumulator arithmetic stays as it was and still ticks once per call. The 14 ms background budget (four sites) is scaled by the same ratio, otherwise a 4 ms frame would hand 14 ms to area loading.

Check: deterministic runs at 60, 120, 144 and 240 steps per second consume 1.000 game seconds per second of virtual time; the retail game on the same clocks gives 1.0, 2.0, 2.4 and 4.0 (`tools/test/hifps_timing.py`).
