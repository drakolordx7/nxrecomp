# S22: release fixes, physics at high frame rates, keyboard beam and visor keys

Branch `rel` in all four repositories. Code and tools: `CMakeLists.txt` and `cmake/gfx.cmake` here, `tools/test/phys_table.py` and `tools/test/keys_check.py`, `tools/release/make_release.py`.

## Release fixes

**Static C++ runtime.** `mpr.exe`, `mpr_setup.exe`, `mpr_setup_cli.exe` and the three `astcdec` DLLs are now linked with `/MT`, so a player does not need the Visual C++ Redistributable. CMake gets `CMAKE_MSVC_RUNTIME_LIBRARY` set to `MultiThreaded` before `project()` in the runtime, `game-build`, `tools/setup`, `tools/textures` and `tools/tiling`, and in the recompiler's toolchain file (the lifted libraries must use the same runtime, so they need a rebuild: `recomp\scripts\build_mpr.cmd`). The release builder now reads the import table of every `.exe` and `.dll` it packs and refuses a release that imports `VCRUNTIME*`, `MSVCP*`, `MSVCR*`, `VCOMP*`, `CONCRT*`, `UCRTBASE` or `api-ms-win-crt-*`. Checked on the new binaries: `mpr.exe` (the release flavour too) imports only Windows system DLLs, `mpr_setup*.exe` and the `astcdec` DLLs only `KERNEL32` and a few other system DLLs, and a test release (`make_release.py`, slim variant) passes the audit. The old DLLs imported `MSVCP140`, `VCRUNTIME140` and `api-ms-win-crt-*`. `tools/release/licenses/NOTICE.MSVC-runtime.txt` and entry 19 of `THIRD_PARTY_NOTICES.txt` now say the runtime is compiled in and no Microsoft file ships.

**Texture test.** `gfx_nvn_scene_texture.real_astc_8x5_texture_transcoded` compared the frame with a stored picture (`work/nvn_refs`) made by an older encoder. It now works out its expected picture itself: it runs level 0 through `a2b_transcode` with the same options as the back end, decodes the BC7 blocks with the reference decoder of bc7enc_rdo, and compares the frame with that (tolerance 2; the result is exact, worst difference 0). It also uses a fresh empty BC7 cache folder for the run, so no old cache entry can reach it. The test passes from a clean build folder. `cmake/gfx.cmake` adds `bc7decomp_ref.cpp` to the gfx test program.

**Config reference.** `docs/CONFIG.md` lists every key the code reads (173 pairs checked by script, none missing), including `[prompts] style` (read from `controls.ini`, not `nxrt.ini`), `[latency] pace`, `[nvn] pool_view`, `[nvn] accept_unlinked`, `[sched] starvation_guard` and `starvation_ms`. A new section describes the keyboard beam and visor keys.

**Pool count.** S18 said about 150 tiny pools per level load and debug note 401 said about 200. The recorded S18 traces (25 gameplay runs) show 198 to 202 pools under 1 MB per gameplay boot: 76 to 78 in the first seconds and 121 to 125 in the later load. S18.md and note 401 now say that. The "61 ms" median in S18 matched no run; the measured pairs are 63 ms before and 0.19 ms after at a 60 cap, 42.5 and 0.22 ms at 120.

**`INDEX.md`.** Two lines left over from a mangled path were removed.

**README, build from source.** Followed on a fresh clone of both public repositories (`drakolordx7/MetroidPrimeRemasteredRecomp` and its `base` submodule). Every step works with the three junctions; no script change was needed for them. Two real problems: `fetch_zstd.ps1` fails when run from Git Bash (Git's `tar` reads `C:` as a host name; the script now calls `%SystemRoot%\System32\tar.exe`) and the README did not say so. The README now says to use `cmd` or PowerShell, that the first configure downloads SDL3 and others, and that the sccache server and cache are shared by every checkout on the PC. Not checked: the dump extraction step (no `.nsp` on this PC, only the unpacked folder), and running the freshly built `mpr.exe`.

## Physics at 60, 120, 144 and 240 steps per second

Method: `tools\.venv\Scripts\python tools\test\phys_table.py --exe game-build-rel\build\rel`. One game process per rate runs the scripted prologue and, for each scenario, warps to `tallon_canyon_cavern`, sets `@rate R` (the game step is exactly 1/R for every frame; the clock stays real) and reads the player's position from the trace. Results are compared with the 60 value. Metroid Prime has one walking speed, so "run" is the walk at full stick; the half-stick walk is added as a second speed.

| Measure | 60 | 120 | 144 | 240 | Verdict |
|---|---|---|---|---|---|
| Walk speed, full stick (units/s) | 10.842 | 10.844 | 10.844 | 10.844 | same (+0.01 %) |
| Walk speed, half stick | 6.703 | 6.702 | 6.704 | 6.701 | same |
| Walk, time to fall from 75 % to 25 % speed after release (s) | 0.0904 | 0.0904 | 0.0904 | 0.0903 | same |
| Walk, total distance in the 4.5 s run (units) | 32.58 | 32.53 | 32.53 | 32.51 | -0.2 % at most |
| Jump height, standing, 0.4 s button (units) | 3.500 | 3.500 | 3.500 | 3.500 | same |
| Jump air time, standing (s) | 0.9876 | 0.9825 | 0.9829 | 1.0263 | -0.5 %, -0.5 %, +3.9 % (see below) |
| Running jump height | 3.337 | 3.325 | 3.323 | 3.319 | -0.4 % to -0.6 % |
| Running jump air time (s) | 0.9039 | 0.8989 | 0.8985 | 0.8978 | -0.6 % to -0.7 % |
| Running jump distance in the air | 9.846 | 9.738 | 9.725 | 9.709 | -1.1 % to -1.4 % |
| Morph ball roll speed (units/s) | 16.42 | 16.48 | 16.45 | 16.43 | +0.4 % at most |
| Morph ball, time from 25 % to 75 % speed (s) | 0.434 | 0.433 | 0.431 | 0.427 | -1.7 % at most |

Earlier readings, explained. "Walk at 120 looked 4 % slow" came from the probe, not from the game: the trace field `spd` is the velocity read at the frame boundary, before the tick's walking friction, and the friction term is `friction * dt * 60` (1.0 units/s at 60 steps, 0.5 at 120). Read that way the speed was 11.84 against 11.34. The distance the player actually moves per second is 10.842 against 10.844. `phys_table.py` uses position differences. The odd "jump reading" was the same kind of problem plus a window that included a wall (half-stick and ball walks ran into the cavern wall about 20 and 40 units ahead; their hold times are shorter or the ball metric is the speed only).

What still differs, and why:

* **Start-up time of walking (rise 25 % to 75 %: 0.0939 s at 60, 0.0989 s at 120, 0.0997 s at 144, 0.1012 s at 240, up to +7.8 %).** The game steers the player's speed with a proportional controller and the physics integrates it with explicit Euler steps (`CPlayerMP1::ComputeMovementForce`, `Compute2DMovementForce`). The speed gap closes by a factor of 0.82 per step at 60 steps and 0.911 per step at 120 (1 - 10.8/rate). The continuous limit is 0.835 per 1/60 s, so 60 steps per second is the outlier: the shorter the step, the closer the response gets to the continuous curve, which is about 8 % slower to rise than the 60 step response. Top speed, stopping time, jump height and the roll speed do not depend on it. Not changed: matching it exactly would mean rewriting the force the game computes each tick, and the difference is under 8 ms. The distance after 1.0 s differs by up to +1.4 % for a different reason: input reaches the player two frames after the press, which is a shorter time at a higher rate.
* **Running jump distance -1.1 % to -1.4 %, air time and height -0.4 % to -0.7 %.** Same cause plus the Euler step of gravity (about a quarter of a frame at 60). Left as is.
* **Standing jump at 240 steps per second: air time +3.9 %.** A single frame about 0.6375 s after the jump starts (12 frames after the top, at a fall speed of about 1.4 units/s) has the vertical speed set to zero and the position unchanged; the next frame starts again from one step of gravity. The rest of the fall is normal (gravity 35 units/s^2 at every rate). It happens at 230, 236, 240, 244 and 250 steps per second (air time +3.7 % to +4.7 %), also at 288 (+2.3 %), and not at 144, 180, 200, 210 or 220. It repeats exactly and does not depend on the area (checked in `tallon_tallon_canyon`). **Mechanism found in S25: the player stuck tracker (`docs/S25.md`).** (S22 text follows.) Mechanism not found then. Ruled out with entry hooks on the guest functions (traced at 240): `SetMoveState` (no call at the stall frame; the state stays 2), `ApplyImpulseWR`, `SetMomentumWR`, `ClearForcesAndTorques`, `ClearImpulses`, `SetPhysicsState`, `CollidedWithNew`, `Teleport`, the physics world's area load and unload and object-list calls, and the off-ground mover's `ImpactResponse` (none called in that frame). The only velocity write in that frame is the normal `SetVelocityWR` from `ComputeMovement` with the damped velocity. `GroundCheckForOffGroundMoverCollider` (the landing probe, only active after 0.4 s in the air) is called every frame up to the top of the jump and not afterwards until the landing. Next step would be to follow the physics world's contact handling inside `CPhysicsSimulationIsland::RunSimulation` for the player's off-ground mover at that frame. Rerun: `phys_table.py --rates 220,240 --scenarios jump --tag x`; the stall shows in `out/trace.jsonl` as a row inside the flight whose `pos[1]` equals the previous row's while `state` is 2.

Real time mode with a frame cap was tried too (`phys_table.py --real`, headless and in a hidden window with `fps_cap` set to the rate). In a scripted run every frame took longer than 1/30 s on this PC (the probes and the per-frame hash cost time), so the step sat at the 30 Hz clamp in every run and all four rates gave identical numbers. That says nothing about the physics; the step-exact `@rate` runs above are the measurement. Real-time stepping with a cap still needs a look in an unscripted window run.

## Keyboard beam and visor keys

Run in the game with `tools\.venv\Scripts\python tools\test\keys_check.py`: warp to `tallon_canyon_cavern`, grant the other beams and the other visors, press each key and read the game's own beam and visor numbers from the trace.

| Key | Result |
|---|---|
| 1, 2, 3, 4 | power (0), wave (2), ice (1), plasma (3): exactly the bindings' order |
| mouse wheel down, down, up | wave, ice, wave (cycles the beams the player owns) |
| 5, 6, 7, 8 | combat (0), scan (2), thermal (3), x-ray (1) |

The keys already existed (`beam_1` to `beam_4` are X plus the d-pad, `visor_1` to `visor_4` the d-pad alone); this run is the first check in the real game. `docs/CONFIG.md` has a section on them. Checked once, all twelve steps as expected. Not checked: missile key, charge combos, morph ball and menu contexts.
