# S32: the gun apart from the view, and a free lock-on

Branch `freelock`. Two options, both off by default, so the game plays as it does now:

| Setting | Default | What it does |
|---|---|---|
| `[camera] gun_drives_view` | `1` | `1`: the arm cannon is fixed to the view, so the idle drift, the walking bob and the landing dip move the whole view. `0`: the view follows only the mouse and the stick. Those movements move the gun on screen instead. |
| `[aim] lock_mode` | `classic` | `classic`: the game's lock-on, the view turns to the target. `free`: the lock starts the same way, then the view is yours. |
| `[aim] free_lock_margin` | `0.15` | With `free`: the part of the screen kept free along every edge (0 to 0.4). The locked target never leaves the middle 70 percent of the screen. |

Both are on the F1 page and in the launcher's Controls tab, and are described in `docs/CONFIG.md`. Both apply at once.

## What the game does

* The camera is built from the player's heading and pitch, then turned by a "camera bob" transform (idle wander of up to about 5 degrees, the walking bob, the landing dip). The arm cannon is computed from the finished camera, so it sits still on screen and the world sways around it.
* In a lock-on the game turns the body to face the target every frame (`CPlayerMP1::UpdateOrbitOrientation`, called after the camera), points the pitch target at it (`ComputeFreeLook`), makes the first-person camera look at it (`CFirstPersonCameraMP1::UpdateTransform`), ignores the right stick (`TurnInput`) and lets go of the lock when the body has been turned away from the target by more than a tweak angle (`ValidateCurrentOrbitTargetId`, reason 5).
* A lock first lets the camera ease onto the target. When the view is within 1 degree the game sets a "reached" flag (`CPlayerMP1+0x550`). Only then does the body follow the target.
* Walking and strafing in the lock are the game's dash code (`ComputeDash`). It moves the player on a circle around the target by position, so it does not read the body's heading. That is why strafing needed no change.
* The aiming cursor, and with it the arm cannon, only goes to the locked target when the game has the target as the "aim target" and its command 75 is held. In the normal lock neither is needed: the view centres the target and the cursor is in the middle anyway. The lights of the hangar's force fields are lock targets but not aim targets.

## What the free lock-on does

Hooks in `src/gfx/play/play_lockcam.cpp`, active only while `free_lock_active` is true: lock mode `free`, the ordinary object lock (orbit state 1, not a grapple point), not the scan visor, and the game's own "reached" flag set. Before that point everything is the game's, so a new lock starts exactly like a classic one.

1. `UpdateOrbitOrientation` is skipped. The body keeps the heading the mouse gave it.
2. `ComputeFreeLook`, `TurnInput` (from `ComputeMovement`) and the camera's `UpdateTransform` run with the orbit state read as 0, so the right stick turns the view and the camera follows the body and the pitch like without a lock.
3. `ValidateCurrentOrbitTargetId` still breaks the lock for every reason except "the view turned away".
4. The view is held inside the margin (`keep_target_in_view`, `keep_in_view` in `play_aim.cpp`). The target's place on the screen is worked out from the eye position, the camera's vertical field of view (55 degrees, plus the display FOV offset) and its aspect. Where the view would let the target pass the margin, it is turned back just far enough. This runs in the mouse aim, before the game reads the new heading, and again after the camera for the stick and for the player moving around the target. The pitch is held the same way.
5. The right stick turns the view in the lock with the game's own turn speed (`tweak + 304` times `tweak + 152`). The game only applies that speed through physics when there is no lock, so it is applied directly here.
6. The aim target is set to the locked object when the game left it empty (combat visors only), and the aiming cursor is told that command 75 is held while it updates. The cursor then eases onto the target and the arm cannon follows it. Shots home as in the normal lock.
7. Releasing the lock returns to the normal mouse aim.

Hook sites (recomp `games/mpr/main.sites`): `UpdateOrbitOrientation`, `ComputeFreeLook`, `TurnInput`, `ValidateCurrentOrbitTargetId`, `CFirstPersonCameraMP1::UpdateTransform`, `CPlayerMP1::UpdateAimTarget`, `CAimingCursorMP1::Update`, `CCommandFrame::GetDigitalHeldInput` and `CPlayerGunMP1::Update`. The module needs a new lift; without the sites the options do nothing.

## What the decoupled gun does

The camera Think hook (`play.cpp`) puts the camera back on the transform the game keeps before the bob is applied (`CFirstPersonCameraMP1+660`), so the view carries nothing but the mouse and the stick. The difference between the camera with the bob and without it is kept, and after `CPlayerGunMP1::Update` the gun's transform is moved by that difference. The gun then sways on screen by the amount the whole view used to sway.

## Scan visor

The scan visor keeps the classic lock. Scanning needs the object to sit in the middle of the scan reticle for the length of the scan, and the game ends the scan when the object leaves it. A free view would make every scan a fight with the margin, and a scan is not combat, so the gun has nothing to point at. This was a design decision. It was not tried in the game, because the hangar has nothing to scan with a lock.

## Verified in the game

Frigate hangar, lock on the force field lights, `lock_mode = free`, margin 0.15, `gun_drives_view = 0`. Screenshots are in `work/shots_wip/freelock_*`: `freelock_lock_before_classic_sheet.jpg` against `freelock_lock_after_free_sheet.jpg`, and `freelock_idle_before_vanilla_sheet.jpg` against `freelock_idle_after_decoupled_sheet.jpg`.

| Check | Result |
|---|---|
| Classic lock (before) | The mouse does nothing while locked, the target stays centred. |
| Free lock, the lock starts | Same as classic: the view centres the target (yaw 3.13 against a target bearing of 3.13), then the mouse is live. |
| Mouse right and left | The view follows the mouse and stops 0.58 rad (33 degrees) from the target on both sides. The margin predicts 32.9 degrees (55 degree vertical field, 16:9, 70 percent). |
| Mouse up and down | The view stops at 0.35 rad (20 degrees) either way, the target stays inside the top and bottom margin. |
| Right stick, both ways | Turns the view and stops at the same limits. |
| Gun and reticle | The reticle sits on the target at the edge of the margin and the arm cannon turns toward it (left when the target is left, right when it is right, up and left when it is high on the left). |
| Shot | The charge-less shot leaves toward the target and hits the light; the lock ends when the target is hit, as in the normal game. |
| Strafing | Left stick sideways moved the player 11.4 units along the circle around the target at 26.6 units distance (the displacement matches the arc), with the view turned 14 degrees off. |
| Release | Releasing the lock returns to the normal mouse aim. |
| Idle, vanilla | 30 samples over 15 s standing still: camera heading max 4.15 degrees, rms 2.09 degrees; the gun moves exactly with it (rms 2.09). |
| Idle, `gun_drives_view = 0` | Camera heading max 0.000, rms 0.000 degrees; the gun's heading max 4.44, rms 2.18 degrees. The world is still in the six frames, the gun moves. |

## Not verified, not done

* A lock on a real enemy was not tried: the hangar lights were the only lockable things reachable by script. The cursor path was checked there with the aim-target hook, which is what a light needs. An enemy goes through the game's own aim-target code and should behave the same.
* The scan visor, walking with `gun_drives_view = 0`, the landing dip and a gamepad in the free lock were not run in the game. The decoupling is one mechanism for the whole bob.
* Pad vertical look does not work in the mouse-aim build even without a lock (right stick up/down changes nothing; the aim code writes its own pitch every frame). It exists on main too, so the free lock's stick only turns the view sideways. The mouse does both.
* After a target switch inside a lock the game keeps its "reached" flag, so the free view stays on; if the new target is outside the margin, the view is turned just enough to bring it in.
* The right stick in the free lock turns at the full speed at once (the game ramps it up through physics).
* The display FOV offset is read from the camera's own field of view (`+0x25c`, in degrees). The display hook that adds the offset reads another field (`+0x460`), which is 0 on the first-person camera; whether the offset reaches the picture there was not checked, so with a non-zero offset the margin may be off.

## Decisions

* One setting, `gun_drives_view`, covers the idle drift, the walking bob and the landing dip, because one mechanism handles all three and the gun has to receive what the view gives up. (Separate `idle_sway` and `walk_bob` keys were considered and never shipped.)
* The free lock starts only after the game's own lock-on has centred the target, so the start matches the classic lock.
* The locked object is made the aim target in the free lock so that the reticle and the gun follow it. It is only done while the lock is on and the combat visor is in use.
* Strafing needed no hook (see above).
