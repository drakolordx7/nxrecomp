# S20 Stability and the full-game sweep

Branch `stab` of the runtime, with branches of the same name in the recompiler and the tools. Goal: find out why the full-game sweep ended in hangs, boot deadlocks and one crash, fix what has a known cause, and finish the sweep.

## What came out

| Item | Result |
|---|---|
| Hangs after a warp (`CGraphicsFrameToken::WaitUntilFinished`) | The frame token is signalled. The game's load did not finish because the loader thread was starved of CPU. Reproduced on demand, fixed by the starvation guard (debug note 422). |
| Boot deadlocks (`CScopedSceneTransferLock`) | Same cause. The boot was slow, not stuck; the kernel's wait queues show no lost wake-up (debug notes 421, 422, `kernel_lightevent` tests). |
| `frigate_air_lock` crash | Narrowed, not reproduced (below). |
| Guest-wait stalls during warp loads | Same cause as the hangs: wake-ups and slices that a busy host processor does not give (debug notes 180, 221, 422). |
| `wfe` and `yield` in the recompiler | They now call a hook that gives the host processor away (debug note 420). Oracles unchanged and green. |
| Sweep | 275 of 275 areas reached: 258 OK (4 of them after a rerun at the end), 17 visual issues (owner: NVN back end) (table in `docs/mpr/SWEEP.md`). |

## What was wrong with the "hangs"

Of the 8 runs the sweep had called hangs or deadlocks, the watchdog (no presented frame for 60 s) fired once, in `phendrana_canyon_entryway`: the render thread was transcoding textures into a cold BC7 cache, 1.2 to 2.5 s each, and it went on for minutes. That was slow work, not a freeze. Texture transcodes now count as progress for the watchdog (`diag_progress`), so a cold cache gives no freeze report.

The sweep's own stall detector killed the other 7 (300 s without progress in the script, 420 s for the boot). In all of them the game was still running: 2,395 to 81,667 presented frames, and the main loop was alive. The load never finished. A thread dump captures one moment of a live system, which is why each run looked like a different deadlock (main in the frame token wait, main in the scene transfer lock, main in an audio call).

The resource loader and the file workers run in the lowest priority band of the console core model, pinned to one host processor. When other programs keep that processor busy, those threads stay ready and get almost no CPU time. Six busy-loop programs at normal priority on the three processors of the game's console cores reproduce this on the stab build and the S15 build:

| Setup | Result |
|---|---|
| no spinners | 110 of 110 areas OK (the sweep of Phendrana, the mines and the crater) |
| normal priority class | the boot never reaches the Frigate (6 of 6 areas not reached after 1,231 s), or the first warp never arrives |
| above normal class | 6 of 6 not reached |
| high class | 6 of 6 OK in 356 s |
| normal class with the starvation guard | 6 of 6 OK in 596 s; with the spinners from "boot ready" on, 6 of 6 in 455 s |

In the stalled runs' dumps, the loader sits in `CBufferedCompression::DecompressBuffer`, ready to run, with 30 ms of CPU between two dumps taken 4 s apart. A yield costs it most of each slice it does get: `SwitchToThread` hands the slice to a spinner even when the spinner has lower priority (debug note 422 has the numbers).

The fix is in `src/kernel/starvation_guard.cpp`. Every 150 ms a poller asks Windows which of the process's threads are ready. A guest thread that has been ready for 300 ms with no context switch is raised to Windows' top normal priority for 450 ms, and its yields stop handing the processor over. Then it drops back to its band. Healthy runs never meet this condition. Config: `[sched] starvation_guard` (default on), `starvation_ms` (300). For a scripted run on a machine where nothing else matters, the high priority class (`NXRT_SCHED_PRIORITY_CLASS=high`) is still the cleaner setting, and play mode in a window already uses it.

Checks for lost wake-ups in the kernel:

- `tests/test_kernel_lightevent.cpp` runs the SDK's own light event protocol (ported from the decompiled `sdk.nso`) on `WaitForAddress` and `SignalToAddress`: 20,000 auto-clear round trips with one waiter and with four, and 5,000 manual-clear rounds with four waiters, with a count of waits that really slept in the kernel. All pass.
- The mutex and condition variable keep their existing stress tests (`kernel_sync`).
- The kernel waiter dump in every stalled run shows waiters on words that say "waiting".

One part is unproven. Some S15 dumps show the loader waiting on its own event with everything else idle. A thread that was woken but is still waiting for its processor shows its kernel wait in the stack too, so those dumps fit the same cause. They carry no CPU times, though. The S15 build, rerun without spinners, did not stall in two chains and 110 further area loads. Dumps written now include the ready state, each thread's CPU time and a second sample, so the next case can be told apart.

## The crash in `frigate_air_lock`

The crash is a read of address 8 in `CParticleStaticRenderState::CParticleStaticRenderState`, called from `CParticleDescription::InitRenderState` on the resource loader thread, 2 s after the first warp of the run and 5 s after the Frigate became playable. The instruction is `ldr x8, [x0, #8]` right after `CToken::GetObj()`: the token for the particle's material format returned no object. `GetObj` locks the reference and reads the object at once, so the object is there only if the dependency was loaded earlier.

Six more attempts at the same first warp did not crash: two with spinners and the guard, two with spinners and no guard (these stalled, as above), and two with two games on the same three processors. So the crash did not come from starvation or from sharing processors. The likely cause is that the practice warp tears down the hangar's assets while the loader is still building a particle that depends on one of them. That race exists in the game itself, and the test warp makes it likely. This is not confirmed. The sweep reruns the area with the final build (below).

## wfe and yield

See debug note 420. The lifter emits `nx_spin_hint(1)` for `wfe` and `nx_spin_hint(0)` for `yield`; the runtime hook gives the host processor to another ready thread (`[sched] spin_yield`). The SDK module has 4 `wfe` and 65 `yield`. The host stand-in for `LockBusyMutex` stays. With `NXRT_SCHED_BUSY_MUTEX_HLE=0`, the SDK's own loop now runs without the old starvation (a boot and three warps passed).

Recompiler oracle results for the final tree: run `.weaver/stab_oracles.cmd`. This note does not record the numbers.

## Other changes

- The freeze and stall dumps now include the NVN back end state, the CPU time of every thread, and, for a requested dump, a second sample taken after `[diag] freeze_resample_s`.
- `tools/test/sweep.py` (tools branch `stab`) adds `MPR_ROOT` to run a copy of the script, a stall reason that says when the game kept presenting frames and which threads were starved, and a 14 s wait for the two dumps.
- New runtime tests: `kernel_lightevent` (4), `kernel_starvation` (1), three in `kernel_busy_mutex`, one in `watchdog`.

## Running it

```
pwsh .weaver\stab_build.ps1                                  # mpr.exe of the stab branch (game-build-stab, libraries from work\build\mpr_stab)
.weaver\stab_sweep.sh --resume --jobs 2                      # the sweep, own folder work\sweep_stab
python .weaver\stab_hog_run.py G2 --hogs 6 --mask 15000 --env NXRT_SCHED_HOST_CPUS=15000   # one chain with spinners on the game's processors
pwsh .weaver\stab_tests.ps1                                  # runtime tests of the stab worktree
.weaver\stab_oracles.cmd                                     # recompiler oracles of recomp-wt\stab
```

The runtime branch needs the recompiler branch of the same name (`nx_spin_hook` is in its `ctx.h`).
