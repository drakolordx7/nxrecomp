# S20 Stability and the full-game sweep

Branch `stab` of the runtime (with branches of the same name in the recompiler and in the tools). Goal: find out why the sweep of the whole game ended in hangs, boot deadlocks and one crash, fix what has a cause, and finish the sweep.

## What came out

| Item | Result |
|---|---|
| Hangs after a warp (`CGraphicsFrameToken::WaitUntilFinished`) | The frame token is signalled. The game's load did not finish because the loader thread was starved of CPU. Reproduced on demand, fixed by the starvation guard (debug note 422). |
| Boot deadlocks (`CScopedSceneTransferLock`) | Same cause. The boot was slow, not stuck; the kernel's wait queues show no lost wake-up (debug notes 421, 422, `kernel_lightevent` tests). |
| `frigate_air_lock` crash | Narrowed, not reproduced (below). |
| Guest-wait stalls during warp loads | Same cause as the hangs: wake-ups and slices that a busy host processor does not give (debug notes 180, 221, 422). |
| `wfe` and `yield` in the recompiler | They now call a hook that gives the host processor away (debug note 420). Oracles unchanged and green. |
| Sweep | 275 of 275 areas reached: 254 OK, 17 visual issues (the NVN stream's), 4 failures re-run at the end (table in `docs/mpr/SWEEP.md`). |

## What was wrong with the "hangs"

Of the 8 runs the sweep had called hangs or deadlocks, the watchdog (no presented frame for 60 s) fired once, in `phendrana_canyon_entryway`: the render thread was transcoding textures into a cold BC7 cache, 1.2 to 2.5 s each, and it went on for minutes. That is slow work, not a freeze. Texture transcodes now count as progress for the watchdog (`diag_progress`), so a cold cache gives no freeze report.

The other 7 were killed by the sweep's own stall detector (300 s without progress in the script, 420 s for the boot). In all of them the game was running: 2,395 to 81,667 presented frames, the main loop alive. The load did not end. A thread dump shows a live system at one instant, which is why each of them looked like a different deadlock (main in the frame token wait, main in the scene transfer lock, main in an audio call).

The resource loader (and the file workers) run in the lowest priority band of the console core model, pinned to one host processor. With ordinary programs busy on that processor those threads stay ready and run for almost nothing. Six busy-loop programs at normal priority on the three processors of the game's console cores reproduce it on the stab build, and the S15 build:

| Setup | Result |
|---|---|
| no spinners | 110 of 110 areas OK (the sweep of Phendrana, the mines and the crater) |
| normal priority class | the boot never reaches the Frigate (6 of 6 areas not reached after 1,231 s), or the first warp never arrives |
| above normal class | 6 of 6 not reached |
| high class | 6 of 6 OK in 356 s |
| normal class with the starvation guard | 6 of 6 OK in 596 s; with the spinners from "boot ready" on, 6 of 6 in 455 s |

The dumps of the stalled runs show the loader in `CBufferedCompression::DecompressBuffer`, ready and with 30 ms of CPU between two dumps 4 s apart. A yield costs it most of every slice it does get: `SwitchToThread` hands the slice to a spinner even when the spinner ranks lower (the numbers are in debug note 422).

Fix: `src/kernel/starvation_guard.cpp`. A poller asks the system every 150 ms which of the process's threads are ready. A guest thread that stayed ready for 300 ms with no context switch gets Windows' top normal priority for 450 ms and its yields stop handing the processor over, then goes back to its band. Healthy runs never meet the condition. Config: `[sched] starvation_guard` (default on), `starvation_ms` (300). The high priority class (`NXRT_SCHED_PRIORITY_CLASS=high`) is still the cleaner setting for a scripted run on a machine where nothing else matters, and play mode in a window already uses it.

Checks that no wake-up is lost in the kernel:

- `tests/test_kernel_lightevent.cpp` runs the SDK's own light event protocol (ported from the decompiled `sdk.nso`) on `WaitForAddress` and `SignalToAddress`: 20,000 auto-clear round trips with one waiter and with four, and 5,000 manual-clear rounds with four waiters, with a count of waits that really slept in the kernel. All pass.
- The mutex and condition variable keep their existing stress tests (`kernel_sync`).
- The kernel waiter dump in every stalled run shows waiters on words that say "waiting".

One part is not proven. Some S15 dumps show the loader waiting on its own event with everything else idle. A thread that was woken and is waiting for its processor still shows its kernel wait in the stack, so those dumps fit the same cause, but they carry no CPU times and the S15 build, run again without spinners, did not stall in two chains and 110 further area loads. The dumps of the stalls written now carry the ready state, the CPU time of every thread and a second sample, so the next one can be told apart.

## The crash in `frigate_air_lock`

The crash is a read of address 8 in `CParticleStaticRenderState::CParticleStaticRenderState`, called from `CParticleDescription::InitRenderState` on the resource loader thread, 2 s after the first warp of the run and 5 s after the Frigate became playable. The instruction is `ldr x8, [x0, #8]` right after `CToken::GetObj()`: the token of the particle's material format returned no object. `GetObj` locks the reference and reads the object at once; the object is there only if the dependency was loaded before.

Six more attempts at the same first warp did not crash: two with spinners and the guard, two with spinners and no guard (these stalled, as above), two with two games on the same three processors. So the crash did not follow from starvation or from sharing processors. The likely reading is the practice warp tearing down the hangar's assets while the loader still builds a particle that depends on one of them; that race exists in the game itself and the test warp makes it likely. It is not confirmed. The sweep reruns the area with the final build (below).

## wfe and yield

See debug note 420. The lifter emits `nx_spin_hint(1)` for `wfe` and `nx_spin_hint(0)` for `yield`; the runtime hook gives the host processor to another ready thread (`[sched] spin_yield`). There are 4 `wfe` and 65 `yield` in the SDK module. The host stand-in for `LockBusyMutex` stays; with `NXRT_SCHED_BUSY_MUTEX_HLE=0` the SDK's own loop now runs without the old starvation (a boot and three warps passed).

Recompiler oracles on the final tree (`stab_oracles.cmd`): see the numbers at the end.

## Other changes

- The freeze and stall dump gained: the NVN back end state, the CPU time of every thread, and for a requested dump a second sample after `[diag] freeze_resample_s`.
- `tools/test/sweep.py` (tools branch `stab`): `MPR_ROOT` to run a copy of the script, a stall reason that says when the game kept presenting frames and which threads were starved, a 14 s wait for the two dumps.
- New runtime tests: `kernel_lightevent` (4), `kernel_starvation` (1), three in `kernel_busy_mutex`, one in `watchdog`.

## Running it

```
pwsh stab_build.ps1                                  # mpr.exe of the stab branch (game-build-stab, libraries from work\build\mpr_stab)
stab_sweep.sh --resume --jobs 2                      # the sweep, own folder work\sweep_stab
python stab_hog_run.py G2 --hogs 6 --mask 15000 --env NXRT_SCHED_HOST_CPUS=15000   # one chain with spinners on the game's processors
pwsh stab_tests.ps1                                  # runtime tests of the stab worktree
stab_oracles.cmd                                     # recompiler oracles of recomp-wt\stab
```

The runtime branch needs the recompiler branch of the same name (`nx_spin_hook` is in its `ctx.h`).
