# S24: no pipeline-creation hitches on a player's first run

Branch `warm2`, cut from main at 3ce3ef8. Same method as S18 and S21: one `mpr.exe`, every change behind a setting, the Frigate route from the landing to the hangar (cap 60, window 1280x720, shader cache on), frame trace on, one run at a time.

On a first run there is no pipeline cache file, no key file and no graphics driver cache. Every pipeline the game needs is built on the render thread at its first draw. On this machine that took 2 seconds for 104 pipelines over the route, with 13 to 18 frames of 50 ms or more.

## Result

A cold run means a new shader hash for the driver on every run (see "Measuring a cold start"), an empty pipeline cache file and an empty key file. Three runs each. The table shows the median, with the lowest and highest in brackets, over the 140 s window of the route.

| | whole pipelines (`gpl = false`, the old behaviour) | pipeline libraries (new default) | libraries after a shader preparation |
|---|---|---|---|
| pipeline creation on the render thread, ms | 1,964 [1,826-2,764] | 18 [14-19] | 19 [17-20] |
| worst single creation, ms | 85 [55-111] | 6.8 [5.3-7.1] | 7.2 [7.1-7.8] |
| frames over 50 ms that are mostly pipeline work | 15 [13-18] | 0 [0-0] | 0 [0-0] |
| background compile time on worker threads, s | none | 49 [35-55] | 3.7 [3.3-4.1] |

The target was a cold first run with no pipeline-creation frame over 50 ms on this route. The result meets it with and without the preparation. Time spent creating pipelines on the render thread fell by a factor of 100.

The table leaves out frame pacing (p99, intervals over 50 ms). Other programs were using the GPU during these runs. The intervals the trace blames on `gpu.exec` and `submit` came and went from run to run regardless of the setting (stall attribution of the nine runs: 0 to 54 GPU-wait stalls per run). The cost of the background threads themselves is in the next comparison.

### What the background threads cost

Compile threads can take CPU time from the game. Six alternating cold runs compared libraries with the compile threads at below-normal priority (as before) against the same threads in Windows efficiency mode (`compile_eco`, now the default). Stalls whose dominant zone was the compile threads, per run: 65, 65, 12 against 21, 21, 13. Intervals over twice the median: 168 [101-184] against 145 [82-153]; over 50 ms: 62 [45-70] against 43 [31-48]. Frame rate 58.7 and 59.0. On the 12900K the threads then run on the efficiency cores (their total compile time rises from 39 s to 54 s). Two threads at idle priority (the first matrix) were no better than four at below-normal: 8, 15 and 33 compile-attributed stalls per run against 11, 15 and 18.

Not measured: a CPU without separate efficiency cores, AMD GPUs and Intel GPUs. `gpl_threads` and `compile_priority` remain the settings to adjust.

## Measuring a cold start

A warm driver cache hides every compile, which is why the first runs of S21 could not be repeated. Findings:

* The NVIDIA Windows driver keeps its Vulkan shader cache in `%LOCALAPPDATA%\NVIDIA\GLCache` (packs of `.bin` and `.toc`; `DXCache` is the Direct3D one).
* `__GL_SHADER_DISK_CACHE=0` does nothing for it on Windows. Whole pipelines with the variable set cost 300 ms for the route, close to the 277 ms with the cache left on and the app cache empty. The variable is only documented for the Linux driver.
* The driver cache belongs to the user and was not touched. `[nvn] spirv_salt` (environment `NXRT_NVN_SPIRV_SALT`) adds a text to every shader module so the driver sees new shaders and compiles them from scratch. With a new text each run, the same 104 whole pipelines cost 1.6 to 2.8 s, against 0.28 s warm and 12 ms with the key file and app cache. The test runs for this work added about 2 GB of such entries to the driver cache. They are harmless, but they stay on disk.

## What was built

### Pipeline libraries (`src/gfx/nvn/nvn_gpl.cpp`)

A pipeline is linked from four parts (VK_EXT_graphics_pipeline_library): vertex input, pre-rasterisation shaders, fragment shader and fragment output. The two shader parts carry the compile time and depend only on the shaders, the program's layout and three raster flags. The other two depend only on state and are cheap. When the game sets a program's shaders (long before its first draw), the two shader parts go to background threads. A program that a command buffer records with moves to the front of the queue. A draw links the four parts in about 0.4 ms. A part that is not ready is built or waited for by the draw, so the worst case is one part, not a whole pipeline.

The first attempt, on branch `warm` (e238c2a), started this work and its design stayed. This work adds or changes the following:

* Pipeline layouts are shared by content (`prog_layout`): programs with the same descriptors get one `VkPipelineLayout`, so a part compiled for one is found again for another.
* Integer vertex attributes. A vertex shader that reads integer attributes (skinned meshes) runs as a patched variant that depends on the vertex formats of the draw. The shader's code shows where the integers go (`spirv_predict_int_inputs`: an input read only through bitcasts to a 32-bit integer; it follows a value through a local variable and ignores computed indexes), so the variant is compiled ahead. Without this, 12 pre-raster parts per route run were built at the draw (14 to 45 ms each, in bursts of five or so). With it, there are zero to one. A first attempt learned the patterns from draws instead. It queued 7,687 jobs, cost frame rate, and was removed.
* A pipeline made this way is not optimised across stages. The key file records it, so the second run builds the whole pipeline in the background as before (S10 prewarm).
* The log names any part that took over 8 ms at a draw, with whether its program had been set and what integer slots the draw and the prediction had.
* `[nvn] compile_eco`: the threads run in efficiency mode (see above). `compile_priority`, `gpl_threads`, `gpl_lto` and `gpl` are the other settings from the first attempt, and they were checked against the code.
* A small note, "Preparing shaders (N left)", appears at the bottom of the screen once the background queue has had work waiting for 1.5 s. It disappears 1 s after the queue empties. `[nvn] compile_note = false` turns it off. It shows in screenshots when the frame counter does (`[fps] in_screenshots`). The first Frigate run shows it on the loading screens: `work/shots_wip/warm_preparing_shaders_note.png`.

### Shader preparation

The setup tool now writes `shader_cache\programs.bin`. It lists every shader program in the player's own game files: the vertex, fragment and geometry code hashes of each program set in `MaterialArchive.arc` and in every pak's MTRL assets (`tools` branch `warm2`, `setup/src/programs.cpp`; the scan reads 778 assets and takes under a second, 28,805 programs). Nothing from the game is shipped or committed. The list is made on the player's machine, the same way as the texture cache.

`mpr.exe --prepare-shaders [--if-needed] [--threads N] [--programs FILE]` starts a Vulkan device without a window, reads the list, and builds the shader parts of every program on all threads but two (batches of 192; modules and SPIR-V of a batch are released after it), discarding each part. It prints `prepare: <done> <total>` lines and ends with `prepare: done ...`, `prepare: ready` (already prepared for this GPU and driver) or `prepare: error ...`. Exit 0 means done or ready, 1 error, 3 cancelled. It writes `shader_cache\prepare.state`. The key in that file holds the GPU name, driver version, Vulkan version, pipeline cache UUID, program count and the scheme version, so a driver update means the next run prepares again.

On this machine, the whole list (28,805 programs, 28,477 prepared, 328 skipped because a stage has no translated shader in the cache, 56,954 parts) takes 107 to 250 s on 22 threads, depending on what else the PC is doing.

The driver's disk cache does not keep the result. On repeated runs of the same list, the parts that came back from it in under 2 ms were 1,581, then 5,370, then 8,949 of 56,954. A 1,000-program list was kept almost completely, but a 6,000-program list was not (3,025 of 11,862 on the second pass). So the preparation keeps its result in the app's own pipeline cache file (`pipeline_cache.bin`, `[nvn] prepare_cache`, default on). The file is about 700 MB for the whole game. A game run with it has 3.7 s of background compile instead of 49 s.

A file this size changed how the cache is handled (`nvn_pipeline.cpp`):

* It is read in one `fread` call. The old stream iterator took 4 s on 700 MB; the new read finishes about 2 s into startup.
* It is rewritten only after 3,000 new pipelines or parts that really took a compile (over 2 ms), and at the end of a session only after 300. A small cache behaves as before.

The launcher (`apps/launcher`) runs `mpr.exe --prepare-shaders --if-needed` after a first-time setup. It asks before Play when `programs.bin` exists and the state says not done ("Prepare shaders now? ... Yes / No / Cancel"), and it has a "Prepare shaders" button on the Extras tab. The progress row shows "Preparing shaders: 1,257 of 6,000" with a Cancel button. Cancel ends the child process, and the next run starts over. Launcher options for scripts: `--auto-prepare`, `--no-prepare`. Screenshots: `work/shots_wip/warm_launcher_prepare_progress.png` and `warm_launcher_prepare_done.png`.

## What is left

* A cold unprepared run still builds about one part at a draw (30 to 40 ms). Which ones: a fragment shader variant the prediction does not know (a pass without colour attachments, dual-source blending, the HDR tone map), or a slot the prediction missed.
* The preparation does not compile the variants that depend on draw state: those fragment variants, integer slots the prediction missed, and raster flags other than the default. The key file covers them from the second run.
* The preparation depends on the game's shader cache. 328 programs, among them gun shaders, have a stage the shipped cache has no translation for. They are skipped, and the game would skip them too.
* The 700 MB cache file costs something at every start (the read, plus the memory it takes). If a player does not want it, `prepare_cache = false` keeps nothing, and the game compiles on demand in the background.
* Not tested: AMD and Intel GPUs, a CPU without efficiency cores, a driver update between preparation and play (the state key says "not prepared", nothing more), and a run longer than the Frigate route.
* Linked pipelines are not optimised across stages. With no frame cap (a 1080p window, the same route, 88 s window), whole pipelines gave 266, 226 and 239 fps in three runs. Libraries after a preparation, with the compile threads idle, gave 223 fps, about 7 to 9% lower. Cold libraries gave 221 and 170 fps, because the compile threads compete with a game that is CPU bound at 250 fps. The route is not comparable second by second between runs at different speeds, only in total. At a cap of 60 none of this shows. The key file makes the second run build the whole pipelines, so only the first run pays. `gpl_lto` asks the driver for the optimised link and is off by default; it was not measured.
