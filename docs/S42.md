# S42 The two rare crashes: frigate_air_lock and magmoor_workstation

Branch `crashes` of the runtime and of the recompiler. Offline work only: IDA on `main`, the crash reports that are still on disk, and the runtime source. No game was run for this note, so neither fix has been seen working in the game yet. "Running it" below has the runs that would check them.

## What came out

| Crash | What it is | Fix |
|---|---|---|
| `frigate_air_lock`, the "loader crash" | The resource loader thread builds a particle (`CParticleStaticRenderState`) whose material has no object. Every known case came seconds after a scripted `@warp` issued during the opening Frigate's loads. | The test tools' `@warp` now waits until the game's resource loader is idle (`[test] warp_wait_loader`, default on). Test tooling only: nothing changes for players. |
| `magmoor_workstation`, `BoxInFrustumPlanes` | A decal render query reads the bounding box of a model scene node that is already in the scene's lists but whose model data has not loaded yet. The pointer is null and the box address is 0x190. This is a gap in the game's own code that our timing makes wider. | Entry hooks on the two `ProcessRenderQuery` functions skip such a node, which is what the game's draw path already does (`[game] modcon_query_guard`, default on). Two hook sites in `main.sites`. |

Neither crash came from the lifter, an HLE service answer or the memory mapping. The evidence follows.

## Crash 1: a particle built without its material

The soak report gives the whole chain. Guest addresses minus 0x7100000000 are offsets in `main`:

```
CParticleStaticRenderState::CParticleStaticRenderState   +0x124   ldr x8, [x0, #8]   x0 = 0, read of address 8
CParticleDescription::InitRenderState                    +0x50
CParticleDataFactory::CreateGPSM                         +0x6144
CParticleDataFactory::LoadGeneratorDesc / ElementGenFactory
CParticleResourceLoader::LoadObject                      +0x578
CResourceLoaderManager::LoadFromFactory / ProcessLoadList / ThreadMain   (the loader thread, guest-84)
```

What the code does (checked in IDA):

- The constructor builds the tag `MTRL` plus the particle's material id (`NMaterialFormat::build_tag`), gets a token from the build context (`CBuildContext::GetToken`) and reads `GetObj()->+8` at once. `CToken::GetObj` locks the reference and returns the object of its container (`CObjectReference::GetObject`: `*(ref + 56)` then `*container`). The object is null while the container is still loading. A reference whose container was taken away also gets a fresh, still-loading container on the next lock. So the read of address 8 means the material object was not there at that moment.
- `CParticleResourceLoader::LoadObject` builds in three stages. Stage 0 reads the GPSM's metadata and locks every dependency it lists. Stage 1 waits until each of those dependencies has an object. Stage 2 builds. The loader therefore never builds a particle while the dependencies it knows about are still loading.
- Of the 14 callers of `CBuildContext::GetToken`, only this constructor dereferences `GetObj` straight away. The others keep the token. So the crash has one site.
- `CObjectReference::Unlock` and `RemoveReference` take the container off a reference as soon as its lock or reference count reaches zero, and queue the object's destruction on the loader thread (`CResourceLoaderManager::Destroy`).

What the runs say: all known cases (sweep run001 and the three in S34) came a few seconds after the first `@warp` of a run, while the opening Frigate was still loading. Sweep run001 crashed 2 s after the warp and 5 s after the Frigate became playable. None came in play, in a later warp, or with 8 s more wait. S20 also ruled out CPU starvation and shared processors: six more first warps did not crash.

The warp is the practice mod's sequence (`tt_probe.cpp`). Its last call is `CGameInstanceState::QuitGame(7)`, which only records the reason. The game then tears the instance down through `CGameUnloaderIOWin` and `CStateManagerUnloader::TickShutdown`. That first finishes a state manager that is still initialising, then shuts it down and drops it, which unlocks every token the old world held. Meanwhile the loader thread keeps working through its load list, including particles the old world asked for.

Mechanism (inferred, not proven): the warp's teardown releases the last lock on a material while the loader is between stage 1 and stage 2 of a particle that uses it, or for a particle whose metadata does not list that material because the world kept it loaded anyway. The constructor then finds no object. The game's own transitions do not get here: the unloader finishes initialisation first, and a player cannot start a teardown during the opening loads. This needs a dump with the material reference in it to confirm. No dump of this crash has been kept.

What it is not:

- Not a lifted atomic. `ldar`/`stlr` are lifted as acquire/release atomics and `stxr` as a sequentially consistent compare-and-swap, and the loads that matter here come after those. (`ldaxr` is lifted as a plain read. That is a gap in general and is listed below, but it is not on this path.)
- Not a file read that failed. A failed load sets the container's failure state, and stage 1 would never let the build start. It would be a stall, not a null in stage 2.
- Not CPU starvation (S20, six tries).

Fix: `@warp` waits for the loader. Before the warp sequence runs, the runner reads `CResourceLoaderManager::IsThreadWorkDone` from memory: the load list, request queue and two other counts at +0xe8, +0xa4, +0x138 and +0x110 must be 0, and the byte at +0x144 must be 0. The manager is found through `TOneStatic<CGameGlobalObjects>` at main+0x4578710, then `CResourceFactory` at +0x00, then the manager at +0x10 (read from the constructors of all three). The warp starts once the loader has been idle for 10 frames in a row. If it is still busy after `warp_loader_max_ms` (30 s), the warp goes ahead with a warning in the log. If the loader cannot be read (no game yet, or a test rig), the warp starts at once, as before. The log shows `warp gate: ...` lines when the gate held a warp.

## Crash 2: a decal query on a model node that has not loaded

From debug note 444 (the run026 dump): `CFrustumPlanes::BoxInFrustumPlanes` read address 0x190 on the render thread. The caller chain was `CShadowDecalManager::SubmitNewStreamOutRequests` -> `CScene::ProcessRenderQueryFromList` -> `CModConSceneNodeMP1::ProcessRenderQuery` -> `CModConSceneNode::GetBounds`, which returns `*(node + 0x80) + 0x190`. The crash came on the first frame after a 250 s load on a starved machine.

What the code does (checked in IDA):

- The constructor of `CModConSceneNode` zeroes `+0x80`. Only `UpdateTokenReadiness` sets it, once the node's model and all its materials are loaded. In the same step it sets bit 0 of byte `+0x32` ("ready"). Until then the pointer stays null. `ReleaseRenderDataShare`, the one other function that clears it, has no callers.
- The node joins the scene's render lists in `CRenderSceneNode::PullTransferData` as soon as its proxy is visible, and that sets bit 0 of byte `+0x31` ("listed"). Nothing there waits for the model data.
- The draw path, `CModConSceneNode::PreRenderForContextConcurrent`, tests the ready bit before it touches the bounds.
- `CModConSceneNode::ProcessRenderQuery` (0x1b57ac) and `CModConSceneNodeMP1::ProcessRenderQuery` (0xfba8b8) test only the listed bit. They then read the bounds through `+0x80`.
- `ProcessRenderQueryFromList` has four callers, all decal generation: `CShadowDecalManager::SubmitNewStreamOutRequests` and `ProcessDynamicGeometryRequests`, `NDecal::submit_new_stream_out_requests` (geometry decals) and `NRenderDecalMPT::CDecalRenderGen::GenerateDecalGeometry`. They run when a new decal needs geometry, not every frame.

So the game crashes whenever a decal query meets a model node that is listed but not loaded. On the console that window is a frame or so, because the node's data loads right behind it. Here a busy or starved loader thread stretches it, by minutes in run026. The ready test is missing in the game itself. Our timing only makes it reachable.

Fix: entry hooks on both functions (`src/gfx/play/play_scenefix.cpp`, sites in `recomp/games/mpr/main.sites`). For a node that is listed and either not ready or has a null `+0x80`, the hook returns before the function's prologue. That has the same effect as the function's own "not listed" path: nothing is added to the query result and x0 is left as the node. Every other node runs the game's code unchanged. The decal then simply does not land on that model for the frame, which is also what happens to a node the draw path skips. The log line `render query skipped a ModCon scene node that is listed but not loaded yet` (at counts 1, 2, 4, 8 and so on) shows when the window was hit.

The same pattern elsewhere: every other `ProcessRenderQuery` override reads a box stored inside the node (`+0x34`, `+0x54`, `+0x60`, `+0x68`, `+0x1f8`), which is always valid. The one exception is `CParticleSceneNode`, whose `GetBounds` reads `*(node + 0x48) + 0xb8`. Its constructor zeroes `+0x48`, so it could have the same window. I found no case of it, and it carries its own draw flags (`+0x40`), so the shadow decal filter (flag 16) may never select it. Not guarded.

The guard does not cover a node that is destroyed while a query still walks the list (a use after free). Note 444 mentions that as the other possible reading. The destructor nulls `+0x80`, so a query that reads the node before its memory is reused is skipped too, but that is not a fix for the race itself.

## Running it (needs the GPU)

Build the exe: `pwsh crashes_game.ps1` gives `work\build_crashes\game\mpr.exe` (after `build_mpr_crashes.cmd`).

Crash 1, A/B, about 3 minutes a run:

```
python -I crash42.py warp gate0 --exe C:\mpr\work\build_crashes\game\mpr.exe --runs 6 --gate 0
python -I crash42.py warp gate1 --exe C:\mpr\work\build_crashes\game\mpr.exe --runs 6 --gate 1
python -I crash42.py warp air0  --exe ...\mpr.exe --runs 6 --gate 0 --target frigate_air_lock
```

Expected: some `crash1(particle)` with `--gate 0` (S34 saw three), none with `--gate 1`, and `warp gate:` lines in the log. If `--gate 0` gives no crash in 12 runs, the repro is too weak to judge the fix.

Crash 2 stress, about 5 minutes a run:

```
python -I crash42.py modcon g1 --exe ...\mpr.exe --runs 3 --guard 1 --hogs 6 --guardsched 0
python -I crash42.py modcon g0 --exe ...\mpr.exe --runs 3 --guard 0 --hogs 6 --guardsched 0
```

The spinners and the starvation guard set to off are how S20 stretched loads to minutes. `guard_skip_lines > 0` with `--guard 1` shows the window was hit and handled. A `crash2(frustum)` with `--guard 0` reproduces the crash. This is a stress test, not a deterministic repro: the window depends on how long the model data of a listed node takes to load. A deterministic version would need a test hook that delays one resource type on the loader thread.

## Open

- Crash 1's exact path from teardown to the missing material is inferred. A full memory dump at the crash would show the material's reference and lock count. The runtime's crash handler writes only the text report (`mpr_crash.txt`), so the `--gate 0` runs would need a debugger attached (cdb from the WinDbg tools) or a `MiniDumpWriteDump` call added to `src/diag/crash.cpp`.
- `ldaxr` is lifted as a plain read with no acquire ordering. Where a loop leaves through the `clrex` path without a store (for example `CObjectReference::Lock`'s "already has a container" exit), the host compiler is free to move later plain loads above it. On x86 hardware loads stay in order, so the only risk is the compiler. No crash is tied to it. A fix would make the `ldaxr` read an acquire load. That is a lifter change and needs the oracles and a full relift.
- `CParticleSceneNode` may have the same window as crash 2 (above).
