# S30: fixes before a first public release

Branch `polish2` in the runtime, tools and root repositories. Seven items: full screen in gameplay, the setup tool and the shader pack, build paths in the release, launcher gaps, mouse menu gaps, the morph ball speed, and one flaky test. Each item below says what was found, what changed and what could not be checked.

## 1. Full screen in gameplay

This PC runs the game inside the player's disconnected Windows session. The game sees a display called "WinDisc" at 2496x1664 (3:2) and no foreground window. The 3840x2160 monitor belongs to the console session. So a real 4K screen, exclusive mode, Alt+Tab and mouse capture could not be tried. The rest was run in gameplay (Frigate hangar, Normal difficulty) with the real game and checked on the pictures the game itself saves (`work/shots_wip/polish2_fs_*`).

| Check | Result |
|---|---|
| Borderless from the start (`window_mode = borderless`) | The window covers the display. The picture is the window size, 2496x1664. The HUD and the aim work. |
| Windowed, then borderless, then Alt+Enter twice in gameplay | Every switch lands in the right mode. The swapchain follows the window (1280x720, 2496x1664). The picture stays at its start size and is scaled with bars when it does not fit (`keep_aspect`). |
| 4K picture: `render_width = 3840`, `render_height = 2160`, borderless | The 16:9 picture is scaled into the 3:2 screen with bars above and below. The HUD is complete. The median over 28 s in the hangar was 56 fps on the RTX 3080 (one slow second at 0.3 fps, best second 91). This is a scripted idle run, not a benchmark. |
| Exclusive mode | Windows refused the mode change ("ChangeDisplaySettingsEx() failed") because of the session. Not checked on a real display. |
| Alt+Tab, mouse capture | Not checked (no foreground window here). By code: the mouse is captured only while the window has focus and the game is running, and a focus loss releases every key (`play.cpp`). |

Found and fixed:

* The HUD and the front-end menus were cut off on screens narrower than 16:9 (this screen is 3:2; 16:10 and 4:3 are the same case). The HUD cameras were made as wide as the screen, which is right for wide screens, but on a narrow one the sides of a 16:9 frame fell outside the picture (the radar and the map ran off the screen edge on 3:2). Now a narrower picture keeps the full 16:9 width and shows more above and below. The perspective HUD camera widens its vertical angle by the same ratio, the orthographic cameras (ball HUD, front end) grow in height, and the menu pointer maps through the same shape (`play_display.cpp`, `menu_mouse_math.cpp`; unit tests in `test_play_display.cpp` and `test_menu_mouse.cpp`). Pictures: `polish2_fs_a_s2_game.png` (3:2 HUD), `polish2_title_3x2_fps_bottom_right.png` (title at 3:2).
* Exclusive mode, when refused, left the game windowed. It now falls back to borderless and says so in the log.

Left as it is: the picture size is fixed at start. Starting windowed and pressing Alt+Enter on a 4K screen shows the start size scaled up. `docs/CONFIG.md` says to set the mode before starting (the launcher does) or to give a fixed size.

Aids added: the self-test steps `gate:NAME` (wait for a file) and `report` (log the window state), `fs_session.py` (walk the window modes in one gameplay run), `winctl.py` (window facts by process id, no global input). PrintWindow captures of a Vulkan window were stale after a mode change, so the pictures come from the game's own capture.

## 2. Setup and the shader pack

Setup used to say "the game compiles shaders as it needs them" when no pack was found. That is wrong: nothing draws without the translated shaders. Now:

* The pack is looked for next to the setup program (`shader_cache.mprshc` or a `shader_cache` folder) and with `--shader-pack <file or folder>` (`--shader-cache` still works). The launcher passes `--shader-pack` when the pack sits next to it. The setup window accepts the same option.
* With no pack, setup stops before it reads the dump, with exit code 2 and this text: "Shader pack not found. Put shader_cache.mprshc in the same folder as the setup program (...), or give its path with --shader-pack. The game cannot draw anything without it." The setup window shows the same text and keeps Start disabled.
* A folder that already holds a finished shader install needs no pack on a second run.
* `--no-shaders` is a developer option that restores the skip, with an honest log line.
* Tests: four new cases in `test_pipeline.cpp` (pack file installs, no pack refuses, `--no-shaders`, kept install). Setup tests: 14 of 14.

Not shown on the real dump: no `.nsp` file is on this PC (only the extracted folder), so the message was checked by the unit test and the program's help text only.

## 3. Build paths in the release

Measured on the exe the user played: 25 strings with `D:\AI...` (24 in the audio renderer's `__FILE__` asserts, the default `game/exefs` folder, the PDB path). The release flavour (`MPR_RELEASE=ON`) was already clean: 0 hits in `mpr.exe`, the launcher and both setup programs, which is what the packager now requires.

* `make_release.py` now fails on a local path by default (`--allow-local-paths` for development builds; `--strict-paths` is still accepted). Its default exe is `game-build/build/relpkg/mpr.exe`.
* `game-build/scripts/build.ps1 -Release` builds that folder (package flavour plus `mpr_launcher.exe`).
* Every build now maps `__FILE__` to paths relative to the checkout (`-fmacro-prefix-map`). The development exe is down to two strings (the default `game/exefs` folder and its PDB path); the release flavour has none.
* Real run: `make_release.py` with the polish2 `mpr.exe`, launcher, setup programs and the 250 MB shader pack: "RELEASE OK", 34 files, 404 MiB, zip 289.5 MiB. The same run on the development exe is refused with the two path hits. Unit tests: 34 of 34.

## 4. Launcher

* Press a button (Controller tab). "Find a button..." opens a small window: press a button or pull a trigger on the controller and the matching row's combo gets the focus and opens. It says so when no controller is connected and Escape closes it. Pad polling uses SDL's gamepad API, like the game (`pad_capture.cpp`). A test attaches a virtual gamepad in SDL and presses A, Start and both triggers (4 of 4 pass). No physical controller was used. A real pad press has still not been seen in the window.
* Keyboard tab Reset now resets only the keys that tab shows (the all-contexts layer). The menu, map, gameplay, morph ball and scan keys are left alone, and the confirmation says so. Unit tests cover it.
* Folder picker. Driven through the real dialog: "Change..." opens it, the folder is typed and accepted, the folder box and the status update ("Ready to play."), and `mpr_launcher.ini` keeps the choice. A full path with forward slashes is not accepted by the dialog's own box; with backslashes it is.
* DPI change. A `WM_DPICHANGED` sent from another process did not reach the launcher's window code in a test (the cause was not looked into), so the launcher has a test message that runs the same code (`change_dpi`). The window was taken to 144, 192 and 96 dpi: the pages are rebuilt, buttons and combo boxes scale (Play 42, 56, 28 px), a changed value survives, Save still writes the file. Pictures: `polish2_launcher_dpi_192.png`.
* Frame rate counter. The default corner was already top left and never bottom right. The title screen's copyright line sits at the bottom right, so the bottom corners overlap it (the earlier test picture used bottom right). Top left was checked on the title, the menus and the hangar HUD. The launcher's hint now says which corners keep clear.
* The e2e script (`launcher_e2e.py`) has new modes `dpi`, `folder` and `pad`, and no longer ends launchers by image name (it only stops the ones it started).

## 5. Mouse in menus

* Inventory and Log Book lists. The categories (left) and the items or entries (right) are two tables of which one is active. A pointer over a row of the other list now presses A (into the right list) or B (back to the left list) once, the game's own way, and then selects the row under the pointer. Checked in the Inventory with three beams granted: hovering Wave Beam and Plasma Beam selects them, hovering Morph Ball on the left goes back. The Log Book uses the same code but had no entries to show (nothing scanned), so it was not seen with items. Pictures: `polish2_inventory_right_list_hover_wave.png`, `polish2_inventory_back_to_left_list.png`.
* Front-end sliders (HUD Opacity, SFX, Music) can be clicked and dragged. The slider widget has no box; its component is the game's `CUISliderGOC`. The pointer is mapped onto the knob's travel (-3.02 to 1.28 UI units) on the row of the slider and sets the value with the game's own `SetTickCount`, which also tells the options code. Checked: a click at the left end gives 0, a drag gives 12, 41, 73 and 100, and on the Sound page the Music slider moves and SFX does not. Pictures: `polish2_frontend_slider_drag_*.png`, `polish2_frontend_sound_music_slider.png`.
* `controls.ini` migration. The file now has `[meta] defaults_rev = 2`. An older file (no section) that has binding sections gets the new factory bindings added at the next start, only where the key is still free in that context. Today that is `X = btn_x` in `[bindings.map]`. A key the player bound to something else keeps their choice. A rev 2 file is never touched again, so a binding the player removed stays removed. The first migration copies the old file to `controls.ini.bak` and saves. Seven new tests.
* Map footer Rotate and Move icons. They are two ordinary 36x36 textures (`TXTR_LStickIdle`, `TXTR_RStickIdle`; the same size and format as the 17 button icons), placed by the map's footer text. The prompt pack now replaces them too: in keyboard style on the map they show the left and middle mouse buttons (drag with the left button rotates, with the middle button moves). Elsewhere and in the pad styles the game's own stick icons stay. Not looked at in the game: the footer picture with the new icons was not taken. Unit tests cover the table and the rule.
* Save station prompt and message boxes. Not reached. The scripted warp into `tallon_save_station` puts Samus on the pad, but no save prompt appeared after walking and pressing A. The prompt is built from the same table frame as the Quit Game question, which the pointer already handles.

## 6. Morph ball speed

The earlier measurement (S26: +0.3 to +1.7 % at 120 to 240 steps per second, not monotonic) was taken in `tallon_canyon_cavern`, a sloped, uneven floor. The new measurement uses the Frigate hangar's flat floor and a straight roll with the same start, camera and stick for every rate, deterministic steps (`ball_flat.py flat1`). Speed from the position (units per second):

| Steps per second | 0.5 to 1.0 s | 1.0 to 1.5 s | 1.5 to 2.0 s |
|---|---|---|---|
| 30 | 13.763 | 16.409 | 16.904 |
| 45 | 14.140 | 16.551 | 16.916 |
| 60 | 14.105 | 16.570 | 16.956 |
| 90 | 14.127 | 16.598 | 16.951 |
| 120 | 14.139 | 16.612 | 16.979 |
| 144 | 14.145 | 16.619 | 16.954 |
| 180 | 14.152 | 16.626 | 16.962 |
| 240 | 14.158 | 16.633 | 16.971 |

From 60 to 240 steps the ball is 0.4 % faster while it accelerates and 0.1 % faster at the end of the run. The values rise with the rate and flatten out (the second column is monotonic), which is what a first-order integration error does. This is the same effect as the walking start-up time in S22. The roll force (`CMorphBallMP1::ComputeMarioMovement`) steers the speed with a proportional controller and the physics applies it with explicit steps; friction is a fixed deceleration times the step. The top speed does not depend on the step in the continuous model, and the measured top speed is within 0.1 %.

The S26 numbers are not reproduced on flat ground. In the cavern the ball's path leaves the straight line differently at each rate (the sideways position after 3 s differs by up to 5 units between 60, 120, 144 and 240) because it rolls over bumps and the contact solver samples the geometry at different times. The speed on a slope then differs by chance, not by a rule. There is nothing in the runtime to fix; matching the 60 step values would mean changing the game's own integrator.

Decompiled code read: `ComputeMarioMovement`, `ComputeMaxSpeed`, `ApplyFriction`, `CalculateSurfaceFriction`, `UpdateBallDynamics` (the friction line is `speed -= friction * dt`; the fixed factors 0.99, 0.6 and 0.49 sit in the boost branch of `ComputeMarioMovement`).

## 7. `gfx_nvn_gpl` failing now and then

Mechanism: `triangle_through_libraries` waited until the workers had built two shader parts ("parts built ahead >= 2") and then checked that the draw made at most two parts itself. The draw needs the vertex input and fragment output parts (made at the draw) and, because the test's raster flags differ from the default ones the workers know, a third part. The workers learn those flags only when the draw asks (`learn_raster`) and then queue that part, so the draw and a worker race for it: the draw either waits for the worker or builds it first. When it builds it first, the check sees three parts. That is the 1.5 s failure (2 failures in the first 16 runs alone).

Fix, in the test only except for one counter: `GplStats` now has `jobs_pending` (jobs queued or running, read under the same lock the workers use), the test waits until that is zero instead of counting finished parts, and the check allows the third part (at most 3, at least 2). Result: 0 failures in 30 runs alone and 0 in 32 runs with four copies at once.
