# S30: fixes before a first public release

Branch `polish2` in the runtime, tools and root repositories. This round covers seven items: full screen in gameplay, the setup tool and the shader pack, build paths in the release, launcher gaps, mouse menu gaps, morph ball speed, and one flaky test. Each section covers what was found, what changed, and what could not be checked.

## 1. Full screen in gameplay

This PC runs the game inside the player's disconnected Windows session. The game sees a display called "WinDisc" at 2496x1664 (3:2) and no foreground window, while the 3840x2160 monitor belongs to the console session. That means a real 4K screen, exclusive mode, Alt+Tab and mouse capture could not be tested. Everything else was run in gameplay (Frigate hangar, Normal difficulty) and checked on the pictures the game saves itself (`work/shots_wip/polish2_fs_*`).

| Check | Result |
|---|---|
| Borderless from the start (`window_mode = borderless`) | The window covers the display. The picture is the window size, 2496x1664. The HUD and the aim work. |
| Windowed, then borderless, then Alt+Enter twice in gameplay | Every switch lands in the right mode. The swapchain follows the window (1280x720, 2496x1664). The picture stays at its start size and is scaled with bars when it does not fit (`keep_aspect`). |
| 4K picture: `render_width = 3840`, `render_height = 2160`, borderless | The 16:9 picture is scaled into the 3:2 screen with bars above and below. The HUD is complete. The median over 28 s in the hangar was 56 fps on the RTX 3080 (one slow second at 0.3 fps, best second 91). This is a scripted idle run, not a benchmark. |
| Exclusive mode | Windows refused the mode change ("ChangeDisplaySettingsEx() failed") because of the session. Not checked on a real display. |
| Alt+Tab, mouse capture | Not checked (no foreground window here). By code: the mouse is captured only while the window has focus and the game is running, and a focus loss releases every key (`play.cpp`). |

Found and fixed:

* The HUD and the front-end menus were cut off on screens narrower than 16:9. This screen is 3:2, and 16:10 and 4:3 have the same problem. The HUD cameras were sized to the full width of the screen. That suits wide screens, but on a narrow one the sides of a 16:9 frame fell outside the picture, so the radar and the map ran off the screen edge on 3:2. Now a narrower picture keeps the full 16:9 width and shows more above and below. The perspective HUD camera widens its vertical angle by the same ratio, the orthographic cameras (ball HUD, front end) grow in height, and the menu pointer maps through the same shape (`play_display.cpp`, `menu_mouse_math.cpp`; unit tests in `test_play_display.cpp` and `test_menu_mouse.cpp`). Pictures: `polish2_fs_a_s2_game.png` (3:2 HUD), `polish2_title_3x2_fps_bottom_right.png` (title at 3:2).
* When Windows refused exclusive mode, the game stayed windowed. It now falls back to borderless and logs that it did.

Not changed: the picture size is fixed when the game starts. If you start windowed and press Alt+Enter on a 4K screen, you see the starting size scaled up. `docs/CONFIG.md` says to set the window mode before starting (the launcher does this) or to set a fixed size.

Test helpers added: the self-test steps `gate:NAME` (wait for a file) and `report` (log the window state); `fs_session.py` (local test script) (walks through the window modes in one gameplay run); and `winctl.py` (reads window details by process id, with no global input). PrintWindow captures of a Vulkan window were stale after a mode change, so the pictures come from the game's own capture.

## 2. Setup and the shader pack

Setup used to say "the game compiles shaders as it needs them" when no pack was found. That was wrong: nothing draws without the translated shaders. Now:

* Setup looks for the pack next to the setup program (`shader_cache.mprshc` or a `shader_cache` folder), and also accepts `--shader-pack <file or folder>` (`--shader-cache` still works). The launcher passes `--shader-pack` when the pack sits next to it. The setup window accepts the same option.
* With no pack, setup stops before it reads the dump. It exits with code 2 and prints this text: "Shader pack not found. Put shader_cache.mprshc in the same folder as the setup program (...), or give its path with --shader-pack. The game cannot draw anything without it." The setup window shows the same text and keeps Start disabled.
* A folder that already has a finished shader install does not need the pack on a second run.
* `--no-shaders` is a developer option that restores the skip. The log line says that shaders were skipped.
* Tests: four new cases in `test_pipeline.cpp` (pack file installs, no pack is refused, `--no-shaders`, kept install). Setup tests: 14 of 14.

Not tested on a real dump: this PC has no `.nsp` file, only the extracted folder. The message was checked by the unit test and the program's help text only.

## 3. Build paths in the release

The exe that was played had 25 strings with the build machine's project folder in them: 24 in the audio renderer's `__FILE__` asserts, the default `game/exefs` folder, and the PDB path. The release flavour (`MPR_RELEASE=ON`) was already clean, with 0 hits in `mpr.exe`, the launcher and both setup programs. The packager now requires that.

* `make_release.py` now fails on a local path by default. Use `--allow-local-paths` for development builds; `--strict-paths` is still accepted. Its default exe is `game-build/build/relpkg/mpr.exe`.
* `game-build/scripts/build.ps1 -Release` builds that folder (package flavour plus `mpr_launcher.exe`).
* Every build now maps `__FILE__` to paths relative to the checkout (`-fmacro-prefix-map`). The development exe is down to two strings (the default `game/exefs` folder and its PDB path); the release flavour has none.
* Full run: `make_release.py` with the polish2 `mpr.exe`, launcher, setup programs and the 250 MB shader pack printed "RELEASE OK": 34 files, 404 MiB, zip 289.5 MiB. The same run on the development exe was refused, with the two path hits. Unit tests: 34 of 34.

## 4. Launcher

* Press a button (Controller tab). The "Find a button..." control opens a small window. Press a button or pull a trigger on the controller, and the matching row's combo gets focus and opens. If no controller is connected, the window says so. Escape closes it. Pad polling uses SDL's gamepad API, as the game does (`pad_capture.cpp`). A test attaches a virtual gamepad in SDL and presses A, Start and both triggers (4 of 4 pass). No physical controller was used, so a real pad press has not yet been seen in the window.
* The Keyboard tab's Reset now resets only the keys that tab shows (the all-contexts layer). Menu, map, gameplay, morph ball and scan keys are left alone, and the confirmation says so. Unit tests cover this.
* Folder picker. Tested through the real dialog: "Change..." opens it, the folder is typed and accepted, the folder box and status update ("Ready to play."), and `mpr_launcher.ini` keeps the choice. The dialog's own box does not accept a full path with forward slashes. It accepts one with backslashes.
* DPI change. A `WM_DPICHANGED` message sent from another process did not reach the launcher's window code in a test. The cause was not investigated. So the launcher now has a test message that runs the same code (`change_dpi`). The window was taken to 144, 192 and 96 dpi. The pages are rebuilt, buttons and combo boxes scale (Play 42, 56, 28 px), a changed value survives, and Save still writes the file. Picture: `polish2_launcher_dpi_192.png`.
* Frame rate counter. The default corner was already top left and was never bottom right. The title screen's copyright line sits at the bottom right, so the bottom corners overlap it. (The earlier test picture used bottom right.) Top left was checked on the title screen, the menus and the hangar HUD. The launcher's hint now says which corners to leave clear.
* The end-to-end script (`launcher_e2e.py`) has new modes `dpi`, `folder` and `pad`. It no longer ends launchers by image name; it only stops the ones it started.

## 5. Mouse in menus

* Inventory and Log Book lists. The categories (left) and the items or entries (right) are two tables, and only one is active at a time. Hovering over a row in the other list now presses A (to move into the right list) or B (to go back to the left list) once, the way the game does it, then selects the row under the pointer. Checked in the Inventory with three beams granted: hovering Wave Beam and Plasma Beam selects them, and hovering Morph Ball on the left goes back. The Log Book uses the same code but had no entries to show (nothing had been scanned), so it was not checked with items. Pictures: `polish2_inventory_right_list_hover_wave.png`, `polish2_inventory_back_to_left_list.png`.
* Front-end sliders (HUD Opacity, SFX, Music) can now be clicked and dragged. The slider widget has no box of its own; the work is done by the game's `CUISliderGOC` component. The pointer is mapped onto the knob's travel (-3.02 to 1.28 UI units) across the slider's row. It sets the value with the game's own `SetTickCount`, which also tells the options code. Checked: a click at the left end gives 0, and a drag gives 12, 41, 73 and 100. On the Sound page the Music slider moves and SFX does not. Pictures: `polish2_frontend_slider_drag_*.png`, `polish2_frontend_sound_music_slider.png`.
* `controls.ini` migration. The file now carries `[meta] defaults_rev = 2`. An older file (one with no `[meta]` section) that has binding sections gets the new factory bindings added at the next start, but only where the key is still free in that context. Today that is `X = btn_x` in `[bindings.map]`. If the player has bound a key to something else, their choice stays. A rev 2 file is never touched again, so a binding the player removed stays removed. The first migration copies the old file to `controls.ini.bak` and then saves. Seven new tests.
* Map footer Rotate and Move icons. These are two ordinary 36x36 textures (`TXTR_LStickIdle`, `TXTR_RStickIdle`, the same size and format as the 17 button icons), placed by the map's footer text. The prompt pack now replaces them too. In keyboard style on the map, they show the left and middle mouse buttons: drag with the left button to rotate, and with the middle button to move. Elsewhere, and in the pad styles, the game's own stick icons stay. Not checked in the game: no footer picture with the new icons was taken. Unit tests cover the table and the rule.
* Save station prompt and message boxes. Not reached. The scripted warp into `tallon_save_station` puts Samus on the pad, but no save prompt appeared after walking and pressing A. The prompt is built from the same table frame as the Quit Game question, which the pointer already handles.

## 6. Morph ball speed

The earlier measurement (S26: +0.3 to +1.7 % at 120 to 240 steps per second, not monotonic) was taken in `tallon_canyon_cavern`, which has a sloped, uneven floor. The new measurement uses the flat floor of the Frigate hangar and a straight roll, with the same start, camera and stick input for every rate and fixed steps (`ball_flat.py flat1`). Speed from the position, in units per second:

| Steps per second | 0.5 to 1.0 s | 1.0 to 1.5 s | 1.5 to 2.0 s |
|---|---|---|---|
| 30 | 13.763 | 16.409 | 16.904 |
| 45 | 14.140 | 16.551 | 16.916 |
| 60 | 14.105 | 16.570 | 16.956 |
| 90 | 14.127 | 16.598 | 16.951 |
| 120 | 14.139 | 16.612 | 16.979 |
| 144 | 14.145 | 16.619 | 16.954 |
| 180 | 14.152 | 16.626 | 16.962 |
| 240 | 14.158 | 16.633 | 16.971 |

From 60 to 240 steps, the ball is 0.4 % faster while it accelerates and 0.1 % faster at the end of the run. The values rise with the rate and then level off, and the second column is monotonic. That is the pattern a first-order integration error produces. It is the same effect as the walking start-up time in S22. The roll force (`CMorphBallMP1::ComputeMarioMovement`) steers the speed with a proportional controller, and the physics applies it in explicit steps. Friction is a fixed deceleration times the step. In the continuous model the top speed does not depend on the step, and the measured top speed is within 0.1 %.

The S26 numbers are not reproduced on flat ground. In the cavern, the ball's path leaves the straight line differently at each rate. The sideways position after 3 s differs by up to 5 units between 60, 120, 144 and 240 steps. The ball rolls over bumps, and the contact solver samples the geometry at different times. So the speed on a slope differs by chance, not by a rule. There is nothing in the runtime to fix. Matching the 60-step values would mean changing the game's own integrator.

Decompiled code read: `ComputeMarioMovement`, `ComputeMaxSpeed`, `ApplyFriction`, `CalculateSurfaceFriction` and `UpdateBallDynamics`. The friction line is `speed -= friction * dt`. The fixed factors 0.99, 0.6 and 0.49 sit in the boost branch of `ComputeMarioMovement`.

## 7. `gfx_nvn_gpl` failing now and then

Cause: `triangle_through_libraries` waited until the workers had built two shader parts ("parts built ahead >= 2"), then checked that the draw itself made at most two parts. The draw needs the vertex input and fragment output parts, which it makes itself. Because the test's raster flags differ from the defaults the workers know, it also needs a third part. The workers only learn those flags when the draw asks (`learn_raster`), and then they queue that part. The draw and a worker race for it: the draw either waits for the worker or builds the part first. When the draw builds it first, the check sees three parts. That is the 1.5 s failure (2 failures in the first 16 runs alone).

Fix: the change is in the test, apart from one counter. `GplStats` now has `jobs_pending` (jobs queued or running, read under the same lock the workers use). The test waits until that count reaches zero instead of counting finished parts, and the check allows the third part (at most 3, at least 2). Result: 0 failures in 30 runs alone, and 0 in 32 runs with four copies running at once.
