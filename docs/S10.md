# S10: display options and frame-time performance

Part S10 of the Metroid Prime Remastered recompilation: why the title screen stalled and fell short of high frame caps, and the display options of play mode (internal resolution, aspect ratio, field of view, filtering, post effects). Branch `display`. Debug notes 220 to 223.

## Result

* The title stalls and the 120 and 144 fps shortfall had three causes, all fixed: a page-table walk inside the host's memory queries (`MapMemory` took 215 ms, debug 220), woken guest threads waiting for the host scheduler under background load (debug 221), and a pipeline cache that was never written (debug 222). A fourth cost, importing memory pools into Vulkan on the render thread, is moved to a background thread (debug 223).
* Display options: internal resolution (window size by default, a scale, or a fixed size, up to 16384 per side), aspect ratio 16:9 to 32:9 and beyond with the 3D view widened, HUD kept 16:9, vertical FOV offset, dynamic resolution off by default, anisotropic filtering, texture LOD bias, bloom and chromatic aberration switches. All of them are in `controls.ini` `[display]` and on the F1 page.
* Title and menu were verified on screen at 1280x720, 1920x1080, 2560x1440, 3840x2160, 2560x1080 and 3840x1080. The camera, HUD and FOV hooks only run in gameplay, which the game cannot reach yet: their arithmetic and hook paths are covered by unit tests and are marked "needs gameplay verification" below.

## Performance

### How it was measured

`[prof] trace = file` turns on a frame trace (`include/nxrt/ftrace.h`, `src/diag/ftrace.cpp`): one mark per presented frame, zones on the render path (submit, replay, texture upload, pipeline and pool creation, limiter, present, GPU time per submission from timestamp queries), every SVC and HLE call above 100 us with its thread, and, with `[prof] stall_ms`, a stack dump of every thread plus each thread's CPU time whenever a frame is late. `scripts/prof/prof_run.py` runs the game in a window with a cap and a size and prints the report; `ftrace_report.py` and `stack_report.py` analyse a trace; `oracle_matrix.py` runs the before / after matrix; `oracle_shots.py` takes the picture oracle. Superluminal was not used: capturing needs an elevated prompt and the `llm` and `mcp` modes need the licence activation that is still open in `STATUS.md`.

### Causes and fixes

| Cause | Evidence | Fix |
|---|---|---|
| `MapMemory` (thread stacks) took 215 ms, up to 1.5 s under load: `VirtualQuery` over the 3 GiB section view walks every page, and `is_mapped` and `protect` call it | Zones inside the SVC: checks 74 ms, protect 148 ms. About 45 slow calls in the first 20 s | Per-page table of the heap in `mem::`, `is_mapped` and `protect` answer heap ranges from it (`[memory] fast_query`). 12 ms for the first call, under 1 ms after (debug 220) |
| Woken guest threads wait for the scheduler: the console core model pins threads to three E-cores with the wake boost off | A submit that replayed in 1.6 ms returned 87 ms later with no thread running. With 24 spinner processes: 34 fps, p99 61 to 83 ms | High priority class while playing in a window (`[sched] priority_class`). Same test: 59.9 fps, p99 16.8 ms. Pinning to P-cores or no pinning made no difference, so the console core model stays (debug 221) |
| Pipeline cache file never written (the process is ended by TerminateProcess), every pipeline built at its first draw every run | No `pipeline_cache.bin` in any run folder | Saver thread (2 s) and flush on window close; key file and prewarm on worker threads (debug 222) |
| Pool import 10 to 80 ms on the render thread at the first draw | 38 imports, 965 ms in 40 s | Import on a background thread when a buffer is created over a pool (`[nvn] pool_prefetch`); 336 ms left on the render thread (debug 223) |

Other things measured and left alone: the title frame costs 1.6 ms on the render thread (replay) and 0.35 ms on the GPU; about 0.6 ms per frame is spent re-preparing one texture the game rewrites every frame (`tex.prepare`); GPU stalls of 10 to 20 ms appear when other processes use the same GPU (`nvnSyncWait` waiting for a 0.3 ms submission), not something this runtime controls.

## Display options

| Option | `controls.ini` `[display]` | How it works | Verified |
|---|---|---|---|
| Internal resolution | `render_scale` (25 to 400 %), `render_width` + `render_height` (fixed), default: the window's client size at start | `COsContext::GetScreenWidth` and `GetScreenHeight` return the size; the game builds its graphics context, render targets, viewports and text panes from them. The handheld getters stay (the touch screen maps through them). Applies at the next start: the game creates its targets once | On screen, six window sizes up to 3840x2160, and a 2x scale (2560x1440 internal in a 1280x720 window); no validation errors |
| Dynamic resolution | `dynamic_resolution` (default off) | `CDynamicResolutionControl::GetResolutionScale` returns 1.0 unless on | Title (scale 1.0 hook called every frame); needs a heavy scene to see the game's own controller |
| Aspect ratio | `aspect` (0 = the internal ratio; 16/9, 21/9, 32/9 ...) | `CDisplayManager::UpdateCameraNodes` builds the world projection from the aspect at `[[this + 16] + 152]`; the hook writes it (and the cached default aspect at 0x20e7a7c) first. The game's FOV is vertical, so a wider aspect widens the view | The title and menu at 21:9 and 32:9 keep their proportions and layout (they are a 3D scene); the projection of the gameplay camera needs gameplay verification |
| HUD proportions | none (follows the aspect) | `CGuiCamera::GetProjectionState`: the frame files store a 65 degree perspective camera with aspect 16:9 (ball HUD: orthographic, left 8, right -8, top 4.5, bottom -4.5; read from `GuiSysMP1.pak`). The hook sets the aspect, or widens the orthographic width and keeps its order, so frames keep their 16:9 shape, centred | Arithmetic and hook path in unit tests (`play_display`); needs gameplay verification |
| Field of view | `fov_offset` (-30 to +40 degrees) | `CGameCamera::GetVerticalFOV` (radians at `this + 0x460`) adds the offset; every game camera, the ball camera and cinematics included | Unit tests; needs gameplay verification |
| Anisotropic filtering | `anisotropy` (0, 2, 4, 8, 16) | The NVN sampler cache raises `maxAnisotropy` on linear mip-mapped samplers; the cache key includes it, so it changes live | Unit test (`gfx_nvn_texgpu.sampler_tuning`) |
| LOD bias | `lod_bias` (-2 to +2) | Added to the bias of every mip-mapped colour sampler, live | Same test |
| Bloom | `bloom` | `CRenderPass_Bloom::Render` is skipped when off (it composites into the frame in place) | Hook test; needs gameplay verification |
| Chromatic aberration | `chromatic_aberration` | The pass still runs but its strength fields are zeroed when off | Hook test; needs gameplay verification |

The settings page shows each of them; the first four need a restart and say so. Tonemap, FXAA, volumetric fog and the deferred passes have no switch: their passes feed each other and skipping one would leave a target undefined (`docs/mpr/hooks.md` lists them for the HDR work).

## Decisions

* Resolution follows the window at start and does not change while the game runs. The window can still be resized; the present pass letterboxes to the internal aspect when `keep_aspect` is on.
* The GUI camera hook only changes cameras whose own ratio is 16:9 (or already the display ratio), so other cameras are untouched.
* FOV is an offset in degrees on the vertical angle, applied to every camera; a multiplier per camera type would need gameplay to tune.
* The priority class is `auto`: high only when play mode has a window. Tests, the boot loop and headless runs stay at normal.
* The pool import prefetch is triggered by buffer creation, not pool creation: most pools hold textures or shader code and are never read by the GPU as buffers.

## Gaps

* Aspect, HUD, FOV, bloom and chromatic aberration have not run in gameplay (the game does not get there yet). Expect to adjust the GUI camera rule if a frame turns out not to be 16:9 authored, and to check that skipping the bloom pass leaves the frame as the tonemap expects.
* No change of internal resolution while running; the game has a resize path (`CGraphicsContext_NVN::Resize`) that was not tried.
* The pipeline prewarm only helps from the second run, and only for programs whose pipelines were recorded; its effect on a level is not measured. A fresh install builds everything at the draw once.
* Importing a memory pool still costs 10 to 80 ms in the driver; 13 of 38 imports at the title still land on the render thread.
* After merging `nvn2`: `nvn_pipeline.cpp` conflicts (its shader variants must take the same module lock as `shader_module` because the prewarm workers call `build_graphics_pipeline`); the branch `display-nvn2` has the resolution.
