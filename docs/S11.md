# S11: high refresh rate

Part S11 of the Metroid Prime Remastered recompilation. Branch `hifps` (worktree `runtime-wt/hifps`). Code: `src/timestep/timestep.cpp`, `include/nxrt/timestep.h`, one change in `src/gfx/play/play.cpp`, tests `tests/test_timestep.cpp`. Host tools: `tools/test/hifps_timing.py`, `tools/test/hifps_probe.py`. Debug notes 300 to 302.

## Result

The game's step is now the measured frame time instead of the constant 1/60 s, and it stays correct at 60, 120, 144 and 240 steps per second. The retail game runs one tick of 1/60 s for every call of `CGameArchitectureSupport::Update`, so rendering at 240 fps made it run four times too fast; with the new step the same front end consumes exactly one game second per second at every rate (table below). Gameplay is not reachable yet (S4e), so the player physics could only be checked on paper, and the fixes for the few per-frame counters are untested in the game.

Chosen approach: variable timestep (lowest latency), not 60 Hz logic plus interpolation. The evidence is in "What depends on the step" below: the engine passes `dt` into every system that matters, the community 120 and 240 fps patches touch the same handful of places, and the one physics step that holds a constant is set from `dt` every tick. The interpolation route stays the fallback for one system, if the probe finds one that cannot be made correct.

## The timestep map (main module, v1.0.0, offsets in IDA's address space)

`CGameArchitecture::Update` (0x3c6f3c) calls `CGameArchitectureSupport::Update(float*)` (0x3c81c8) once per rendered frame. That function:

1. reads the real elapsed time with `nn::os::GetSystemTick`, clamps it to at most 1/60 and adds it to an accumulator (`this+0xa0`);
2. runs `do { ... } while (accumulator >= 1/60)`. The body subtracts 1/60 but floors the accumulator at -1/60, so at any frame rate faster than 60 Hz the loop runs exactly once per call and the accumulator never grows. That is why rendering faster speeds the game up: one tick of 1/60 per call, however short the frame;
3. per iteration queues `BeginSimulationTick(1/60)`, `CInputGenerator::Update(1/60)`, `TimerTick(1/60)`, `UpdateAreaLoadState` (`ExtraProcessingTick(0.0005)`), `EndSimulationTick`, then `UpdateRenderState(sum of the steps)`;
4. spends what is left of a hard-coded 14 ms on `ExtraProcessingTick(budget)` and the scene-node graveyard.

## What depends on the step

Checked in the disassembly (all take `dt` and scale by it, `x * 60` or `powf(base, dt * 60)` where the original per-frame value is kept):

- player walk: `CPlayerMP1::GetDampedClampedVelocityWR` (0xcee29c) uses `friction * dt * 60` in its main branch;
- morph ball: `CMorphBallMP1::UpdateBallDynamics` (0xce5a4c, `powf(0.95, dt * 60)`, timers minus `dt`), `DampLinearAndAngularVelocities` (0xce6f20, `powf(1 - f, dt * 60)`);
- physics: `UpdatePhysicsState` above; `CPhysicsEulerIntegrator::PredictMotion` takes a step argument;
- the same `dt * 60` pattern appears in 125 `60.0f` immediates across `CPlayerMP1`, `CPlayerGunMP1`, `CMorphBallMP1`, `CSamusHudMP1`, `CScanDisplayMP1`, `CGuiSliderGroup::Update` (site 0xbe2f94), the camera code and the map screens. Only the functions named above were read line by line; the others were judged from their `float dt` argument and the constant's use;
- particles: `CElementGen::InternalUpdate(double dt, …)` converts seconds to frames with a double 1/60 (0x245f60), so it follows real time;
- no per-frame HUD-memo counter turned up in `CStateManagerGameLogicMP1`: the fields behind `IsHudMessageActive` (+0xb20, +0xbec) hold message ids that `GameMainLoop` copies once.

Per-frame values that are not driven by that `dt`, and what was done:

| Item | Address | Retail | Done |
|---|---|---|---|
| In-air walk friction, branch "state 1" of `GetDampedClampedVelocityWR` | `fmov s1, #3.5` at 0xcee3e8 | subtracts `speed / mass * 3.5` every tick | mid hook at 0xcee3ec sets `s1 = 3.5 * dt / (1/60)`. The community 120 and 240 fps patches rewrite the same instruction. |
| Render timings | `NRenderUtilMPT::TickRenderTimings`, 0xc32890 | frame counter + 1 per call, seconds = counter / 60, wraps at 53000 frames | entry hook replaces it: the counter advances by `dt * 60` frames, the float seconds at 0x459cc14 and the counter at 0x459cc10 are written the same way. |
| Texture streaming age | 0xfe264, 0xff2f4 | 1/60 per call | mid hooks load the step (twice the step on the 30 fps path). |
| Background-work budget | Update, four sites | 14 ms | scaled by `dt / (1/60)`: a 4 ms frame gets 3.5 ms. |
| Movie clock | `CMovieList::Update` | the step | entry hook hands real elapsed time (at most 0.5 s per call): a frame longer than the step clamp no longer makes the picture trail the sound. |

Per-tick systems the GameCube audit names (friction, projectile tick period, decals, AI frame counters, the HUD message countdown) have no counterpart that needs a change: MPR keeps seconds everywhere the GameCube code kept frames. The decal, particle-seed and AI-counter items of the GameCube list could not be matched one to one; the probe below is what would show a deviation.

## What was built

Runtime module `nxrt::timestep` (`[time]` keys in `docs/CONFIG.md`):

- an entry hook on `Update` measures the frame (QueryPerformanceCounter, or the virtual clock in deterministic test mode), applies the policy and publishes the step;
- mid hooks load it into the registers the immediates used (`recomp/games/mpr/main.sites`, listed below);
- `mode = real` (default): step = mean of the last 4 frame times, clamped to 1/480 .. 1/30, a frame more than 50 % off the mean restarts the window; with `pace` the frame is held until 1/480 s has passed, so an unlimited frame limiter cannot run the game faster than 480 steps per second. `mode = fixed`, `rate = N`: the lock, one constant step and the frame held to it. `mode = off`: the retail 1/60 (plus `off_rate`, a diagnostic that paces to N while keeping the retail step);
- deterministic test mode (`[test] deterministic = 1`): the step is `clock_step_ticks / 19.2 MHz`, nothing sleeps. A scripted run at 60, 120, 144 or 240 steps per second is the same script with `clock_step_ticks` 320000, 160000, 133333, 80000.

Sites added to `recomp/games/mpr/main.sites` (the main module was lifted again into `work/lift_hifps`, libraries in `work/build/mpr_hifps`; the shared `work/lift` and `work/build/mpr` were not touched):

| Kind | Addresses |
|---|---|
| entryhook | 0x3669ec (`CMovieList::Update`), 0xc32890 (`TickRenderTimings`) |
| midhook | 0x3c8238, 0x3c830c, 0x3c8354, 0x3c8634, 0x3c8648, 0x3c86f4, 0x3c8708 (Update); 0xcee3ec (friction); 0xfe268, 0xfe274, 0xff2fc, 0xff308 (streaming) |

The existing entry hooks on `Update` (0x3c81c8) and `ProcessInput` (0xc70334) are used as before. A lifted game built without the new sites keeps working (the hooks are simply never called), at the retail step.

## Measurements

Method: `tools\.venv\Scripts\python tools\test\hifps_timing.py`. The game runs headless on the title screen and the front end (movies, menus; no gameplay), a per-frame CSV comes from the module, and the table is computed over the steady part of the run. "movie x" is the number of video frames the movie player consumed per second divided by 60 (the title movies are 60 fps). In deterministic mode time is virtual, so the run is as slow as the machine and the game's clock is exact. With `movie_real=0` the movie clock is the game's own `TimerTick` dt, which proves the whole path (Update immediates -> message -> IOWin -> `CMovieList`).

| Case (deterministic, `movie_real=0`) | Steps/s | game seconds per virtual second (step sum) | movie x |
|---|---|---|---|
| fixed step, retail game (`mode=off`) | 60 / 120 / 144 / 240 | 1.000 / 2.000 / 2.400 / 4.000 | 1.004 / 2.008 / 2.409 / 4.014 |
| new step (`mode=real`) | 60 / 120 / 144 / 240 | 1.000 / 1.000 / 1.000 / 1.000 | 1.003 / 1.001 / 1.000 / 1.000 |

Retail baseline on the real clock (headless, paced to N): 60 -> 0.93, 120 -> 1.89, 240 -> 2.79 (the pipeline delivered 55, 113 and 167 fps while other builds ran on the machine). New step on the real clock, `max_rate` 60 / 120 / 240: movie x 1.002 / 1.002 / 1.000 (52, 74 and 164 fps delivered). The step sum falls behind wall time by the stalls longer than 1/30 s that the game now clamps (0.91 to 1.01), which is the intended slow motion rather than one giant step. Fixed 60: movie x 1.001.

What these runs do not show: the in-game fixes (friction, render timings, streaming, budget) run only in gameplay or are idle in the front end. The render-timing hook is only reached from `CGameIOWinMP1::UpdateRenderState`, which the front end never runs; it, the friction hook and the streaming hooks are covered by unit tests (`timestep`: 17 cases) and the front-end runs prove the mid hooks of Update and the streaming hooks do not break anything.

## Physics probe

`tools\.venv\Scripts\python tools\test\hifps_probe.py [--rates 60,120,144,240] [--scenarios menu,walk,jump,turn]`. Each scenario is a script template in seconds; the generator turns seconds into frames per rate and runs `mpr.exe` deterministically at `clock_step_ticks = 19.2e6 / rate`. Metrics come from the S5 trace (position, yaw, movement state per frame) and are compared against the 60 Hz run.

| Scenario | Measures | Tolerance | State |
|---|---|---|---|
| `walk` | steady speed, distance in 3 s, time to 95 % speed, slide after release | 1 %, 2 %, 6 %, 6 % | ready; needs gameplay (the run stops at the Frigate warp today: harness reports "gameplay not reachable", exit 3) |
| `jump` | peak height, airtime of a 0.4 s jump press | 2 %, 3 % | ready; needs gameplay |
| `turn` | yaw of 1000 mouse counts spread over 0.2 s | 1 % | ready; needs gameplay |
| `menu` | screenshots of the title and the attract movie at equal game times | informational | runs; shots differ in phase by design (debug note 301) |

The analysers are tested on synthetic traces (`tools/test/tests/test_hifps_probe.py`, 11 cases: exponential walk, ballistic jump, linear turn at 60/120/144/240; the tightest margin is the slide at 240 Hz, 4.3 % of its 6 % allowance, from the per-frame decay discretisation). Not scripted, because the probes do not read the quantity yet:

- morph-ball roll and friction: needs the ball item in the save and the ball's velocity (the trace velocity is a position difference, which works once the ball is the tracked object);
- projectile range: needs an entity probe for `CProjectileWeapon` positions;
- the HUD message timer: needs a read of the HUD state or a screenshot pair at known game times.

## Aim

Mouse look is applied once per rendered frame at every rate. With the step equal to the frame time, `Update` runs exactly one tick per call (see the loop above), so the first `ProcessInput` after each frame boundary happens every frame and takes that frame's mouse counts; there is no rate at which the view steps slower than the frame. A unit test (`update_loop_runs_one_tick_per_frame`) runs the loop arithmetic with the values the mid hooks load at 60 to 480 Hz. In addition, `[play] late_sample` (default on) pumps the window's events again right before the counts are taken, so the aim includes what the mouse did between the frame boundary and the tick. No camera-level hook was needed.

## Gaps

- Gameplay: nothing that needs a player has run. The in-air friction fix, render timings and the streaming age are written from the disassembly and the community patches; the probe scenarios are ready for the first gameplay run, and per-rate deviations beyond the tolerances above are the signal to look at `CPlayerMP1` and `CMorphBallMP1` first.
- `CDynamicResolutionControl::Update` still gets 1/60 as its target (0xb30428). With dynamic resolution on it keeps judging the frame against 60 Hz; the display stream owns that option, and a fixed resolution scale makes it moot.
- Smoothing: the default window of 4 frames was not tuned against real jitter at 240 Hz (the front-end runs are too irregular to say). `smooth = 1` gives the raw step.
- The limiter of the play mode (frame cap, vsync) is not changed: it still holds frames on the presenting thread. `max_rate` is the cap of the logic when the limiter is off.
- Loading uses the real-time budget of `ExtraProcessingTick`; the scaled budget keeps the same share of the frame, but loading speed at 240 Hz was not compared on a gameplay load.
- Deterministic runs are as slow as the machine renders (about 100 to 160 fps here); 240 steps per second is a game-time rate there, not a wall-clock one. A real 240 Hz run needs the display stream's pipeline work.
