# 002: BC7 encoder changes alpha of opaque textures (alpha 254, alpha 244..253)

**Symptom.** First transcode of `Bricks113A_Color` (opaque RGBA, alpha 255 everywhere): alpha PSNR 51.7 dB, 44% of
pixels decoded with alpha 254. The oracle's alpha check (source alpha 255 must stay 255) failed on six
`Ground110_NormalGL` files with a few pixels at alpha 244..253.

**Cause.** bc7e treats a block whose source alpha is all 255 as opaque and uses modes 4, 5, 6 as well as 0..3.
Mode 6 stores alpha in 7 bits plus the p-bit it shares with the colour, so alpha is 255 only when the p-bit is 1 and
254 otherwise. Modes 4 and 5 can rotate a colour channel into the alpha slot, which moves colour error into alpha
(the 244..253 pixels on a normal map).

**Fix.** `a2b_encode_bc7` splits each chunk of blocks into opaque blocks and blocks with real alpha. Opaque blocks are
compressed with mode 6 off and channel rotation off; the others use the full preset. Preset 0 (mode 6 only) ignores the
mode switch, so its mode-6 opaque blocks are patched to alpha endpoints 127 and p-bits 1. Cost: about 2 dB of RGB PSNR
on opaque content (52.0 to 49.8 dB on one 6x6 sRGB albedo at preset 4). `--allow-opaque-mode6` restores the old
behaviour. Rationale: an alpha channel that silently drifts on opaque textures can trip alpha tests and blend paths.
